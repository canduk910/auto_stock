## 0. 요약 (먼저 읽을 것)

의뢰서의 결함 서술은 정확하다. 다만 **손상 크기와 경로가 의뢰서 추정보다 크고, 방향이 다르다.**

| 의뢰서 가정 | 실측 결과 |
|---|---|
| 평시 스텁 30~70건 = 거래정지·무거래 종목의 정상 봉 | **틀림.** 09-03 스텁 61건 중 **59건이 같은 결함의 잔재**(그날 아침에 쓰인 스텁이 유니버스 이탈로 영영 안 덮인 것). 진짜 무거래봉은 **하루 1~8건** |
| 스텁이 전략 prepare 를 오염시킨다 | **맞다. 단 오염 경로는 "오늘 스텁"이 아니라 "어제 스텁"이다.** 7 전략 전부 `prev_idx` 가드로 *오늘* 봉은 이미 잘라낸다. 아침 `_boot` prepare 는 daily load 보다 **4분 먼저** 돌기 때문에, 그 시점 DB 헤드는 *어제* 날짜의 스텁이고 `bas_dd ≠ today` 라 가드를 **그대로 통과**해 "전일봉"으로 소비된다 |
| 손상은 조용하다 | **아니다. 로그에 이미 찍혀 있었다.** 아침에 prepare 가 두 번 도는데(07:51 오염 / 08:02 정상), 두 결과가 매일 크게 다르다. LTV 09-03 `10/90 → 90/90`, 09-04 `5/32 → 32/32` |
| donchian 은 창이 한 칸 밀린다 | **아니다. 창은 안 밀린다**(스텁은 추가 행이 아니라 같은 날짜 행의 값이 틀린 것). 대신 donchian 의 **신고가 게이트와 거래대금 게이트가 수학적으로 통과 불가**가 된다 (§1.2 증명) |

그리고 **아무도 안 본 상시 손상이 하나 더 있다**: `stock_master_daily.get_atr()` 에는 오늘봉 가드가 없어서 VCP 의 ATR 이 **평균 6.3% 과소**(중앙값 6.3%, 최악 29.3%, 1,805종목 중 272종목이 10% 이상 과소)로 계산된다. 이건 2차 prepare 로도 안 지워지고 매일 상시다. VCP/BFB 터틀 전환(Phase 2 대기) 전에 반드시 닫아야 한다 — 6.3% 낮은 ATR = **6.7% 큰 유닛 수량**.

## 1. ① 결함의 매매 영향 — 무엇이 얼마나 바뀌는가

### 1.1 실제 인과 사슬 (로그 실측, 2026-09-04)

```
07:45:01  scheduler.start()  →  await self._boot()
07:51:13~07:51:52  _boot 안에서 7 전략 prepare()          ← ★ 오염 지점
                   (이 시점 DB 헤드 = 09-03 자 스텁, 09-03 아침에 쓰인 것)
          _boot() 반환 후에야 daily load task 가 create_task 된다
                   (scheduler.py:678, boot_manager.py:124 순서)
07:55:56  [stock_master_daily_load_begin] candidates=1015   (= boot+240s, initial_delay_secs)
07:57:55  [stock_master_daily_load_summary] fetched=1015 upserted_rows=7897 skipped_fresh=0
                   → 여기서 09-03 실봉 + 09-04 스텁이 동시에 쓰인다
07:59:00  사전 구독 104종목                                 ← ★ 오염된 후보로 구독 슬롯 배분
08:00     NXT 프리 개장 (LTV tradable_boards = main,pre_nxt)  ← ★ 오염 상태로 매매 개시
08:01:57~08:02:34  evening_funnel_capture 의 immediate run 이
                   7 전략 prepare() 를 **다시** 돌린다 (= boot+600s)  ← ★ 우연한 복구
```

핵심은 두 가지다.

**(a) `_boot` 의 prepare 가 daily load 보다 먼저 돈다.** `start()` 는 `await self._boot()` 를 먼저 끝내고 나서야 데이터 적재 task 들을 만든다. 그래서 아침 첫 prepare 는 항상 "어제 아침에 쓰인 어제 날짜 스텁"을 헤드로 읽는다. 그 스텁의 `bas_dd` 는 오늘이 아니므로 `prev_idx = 1 if candles[0]["stck_bsop_date"] == today_str else 0` 은 **0** 을 주고, 스텁이 그대로 **"전일봉"** 이 된다.

**(b) 손상을 지우는 것은 설계가 아니라 우연이다.** 08:02 의 2차 prepare 는 `evening_funnel_capture_task_loop` 의 `immediate_first_run` (`initial_delay_secs=600`) 이다. 이름 그대로 *관찰용 funnel 캡처* 이지 prepare 보정 장치가 아니다. 이게 daily load(boot+240s, 소요 119초) 보다 늦게 끝나는 것은 **360초 여유에 기댄 우연**이다. 유니버스가 커지거나 KIS 가 느려서 load 가 360초를 넘기면 2차 prepare 도 같이 오염되고, 그날은 하루 종일 오염된 후보로 돈다. 이 task 를 끄거나 옮기면 결함이 전면화한다.

### 1.2 전략별 크기 — 실측 + 코드 증명

**로그 실측 (같은 날 아침 두 prepare 의 결과 차이).** 이게 손상의 직접 측정치다.

| 전략 | 09-03 07:51 (오염) | 09-03 08:02 (정상) | 09-04 07:51 (오염) | 09-04 08:02 (정상) |
|---|---|---|---|---|
| volatility_breakout | 65/65 | 65/65 | 55/55 | 55/55 |
| **long_tail_volatility** | **10/90** | **90/90** | **5/32** | **32/32** |
| **donchian_swing** | 1/108 (d=1 v=1) | 2/108 (d=2 v=2) | 1/111 (d=5 v=1) | **4/111 (d=9 v=4)** |
| **bull_flag_breakout** | **52/569** | **22/570** | **42/595** | **25/596** |
| vcp_breakout | 1/669 | 0/670 | 0/688 | 0/689 |
| **kojiro** | **32/662** (band=248) | **14/663** (band=214) | 15/680 (band=254) | 18/681 (band=231) |

읽는 법: BFB 와 kojiro 는 오염 상태에서 후보가 **더 많다**. 즉 이 결함은 "매수를 줄이는" 방향이 아니라 **양방향**이다 — 거짓 후보를 만들기도 하고 진짜 후보를 죽이기도 한다. 트레이더 관점에서 이게 더 나쁘다. 거래량 0 + 시가=고가=저가=종가인 봉은 BFB 눈에는 **완벽하게 조용한 눌림 하루**로, kojiro 눈에는 **밴드가 좁아진 하루**로 보인다. 실체는 데이터 결손인데 지표는 "수축"으로 읽는다.

**LTV / VB (동일 코드).** `prev = candles[prev_idx]` → `prev_range = prev_high - prev_low`. 스텁은 고가=저가라 `prev_range = 0` → `range_excluded` 로 **전량 탈락**. LTV 가 정확히 그 모습이다(90→10, 32→5).

- **VB 가 왜 멀쩡한가**: DB `strategy_config` 에 VB 만 `k_period = 15` 로 덮여 있다(LTV 는 20). prepare 는 `days = k_period + 2 = 17` 로 조회하는데 `min_required = 22` 는 **하드코딩**이다. `get_recent_daily` 는 최대 `days` 행만 주므로 `17 < 22` → **VB 는 항상 KIS 폴백**을 탄다. KIS 는 장 시작 전에도 오늘(D) 날짜 스텁을 헤드로 주므로 `prev_idx = 1` 이 걸려 스텁이 잘리고, `candles[1]` = 진짜 전일봉이 쓰인다. **VB 는 사이클 173 의 DB 일봉 전환이 아예 적용된 적이 없다** — 매 prepare 마다 종목당 KIS 를 1회씩 때리고 있다. 별건 결함(§8 D-4).

**donchian — 게이트가 수학적으로 통과 불가 (증명).**
오염 상태의 창은 `candles = [스텁(D-1), 실봉(D-2), 실봉(D-3), ...]` 이고 스텁의 종가·고가·저가는 전부 **D-2 의 종가**다.

- 신고가 게이트: `prior_high = max(highs[1:21])` 는 인덱스 1..20, 즉 **D-2 부터**의 고가다. `prev_close = closes[0]` = D-2 의 종가. 종가 ≤ 고가 이므로 `prev_close = close(D-2) ≤ high(D-2) = highs[1] ≤ prior_high`. 따라서 `if prev_close <= prior_high: continue` 가 **항상** 참이다.
- 거래대금 게이트: `today_turnover = closes[0] * vols[0]` 에서 `vols[0] = 0` → `today_turnover = 0` → `0 < avg × 1.5` **항상** 참 → 전량 탈락.

즉 오염된 prepare 에서 donchian 이 후보를 만드는 유일한 경로는 **락 게이트로 KIS 폴백을 탄 종목**뿐이다(락 발생률 실측: 최근 22행 창 기준 대형주 코호트의 약 17%). 09-04 의 `donchian=5 → volume=1` 이 정확히 그 잔여다. 이건 P0-1(`acml_vol` 유령 키)과 **같은 계열의 구조적 차단**이다 — 시장이 조건을 안 준 게 아니라 코드가 통과를 못 하게 되어 있었다.

**VCP — 2차 prepare 로도 안 지워지는 상시 손상 (get_atr).**
`stock_master_daily.get_atr()` 에는 `prev_idx` 같은 오늘봉 가드가 **없다**. `get_recent_daily(ticker, days+1)` 결과를 그대로 쓴다. 그래서 08:02 prepare(오늘 스텁이 헤드)와 16:20 prepare(오늘 스텁이 헤드) 양쪽에서 헤드 봉의 True Range 가 **0** 으로 계산된다.

실측(현재 DB, 1,805종목):

| 지표 | 값 |
|---|---|
| 스텁 포함 ATR ÷ 스텁 제외 ATR — 평균 | **0.9368** (6.3% 과소) |
| 중앙값 | 0.9372 |
| 최소 (최악) | 0.7067 (29.3% 과소) |
| 10% 이상 과소인 종목 | **272 / 1,805** |

그리고 `vcp_breakout.py:453~` 의 교차검증은 `diff_pct <= 10.0` 이면 **DB 값을 채택**한다. 6.3% 편향은 그 문턱 아래라 `[vcp_atr_mismatch]` 가 **한 번도 안 울린다**. 계통 편향은 이렇게 조용히 통과한다.

트레이더 관점 위험: VCP 는 지금 `sizing_mode = position_ratio` 라 ATR 이 수량을 정하지 않는다. 그러나 Phase 2 로드맵의 **VCP/BFB 터틀 전환**을 켜는 순간 `unit = floor(예산 × risk_pct ÷ ATR)` 의 분모가 6.3% 작아져 **모든 유닛이 6.7% 과대**가 된다. 리스크 정규화가 진입 시점에 조용히 6.7% 뚫린다. **터틀 전환 전에 이 결함부터 닫아야 한다.**

**market_regime (ETF 레짐 관찰).** `_compute_single_etf_stage` 도 오늘봉 가드가 **없다**(`market_regime.py:674`). EMA 5/20/40 시리즈의 마지막 점이 전일 종가의 복사본이라, `is_two_day_defensive(stages[-2:])` 의 "2일 히스테리시스"가 실질적으로 1일 + 복제 1일이다. 관찰 전용(매수 가드는 사이클 I 에서 제거)이라 매매 직접 영향은 0 이지만, **자문 payload 와 대시보드에 들어가는 신호**다. 시정 후 자동으로 정상화된다(§4).

**VB RS/RSI 관찰 훅** (`volatility_breakout.py:604,619`, `get_recent_daily(days=30)`) — 동일. 기본 OFF(`rs_filter_enabled=False`) 라 배제 0, 스코어만 오염. 시정 후 자동 정상화.

### 1.3 실제 손해가 난 자리 (2차 prepare 가 못 막는 구간)

08:02 의 2차 prepare 가 `_targets` / `_candidates` 를 통째로 다시 만들기 때문에, **09:00 이후 KRX 매매는 대부분 정상 후보로 돈다.** 남는 구멍은 셋이다.

1. **07:59 사전 구독** — 104종목을 요청하지만 `MAX_SUBSCRIPTIONS = 41` 이다. 어느 41개가 뽑히느냐를 **오염된 후보 집합**이 정한다. 2차 prepare 는 구독을 다시 짜지 않는다(`_scan_loop` 5분 주기가 나중에 보정).
2. **08:00~08:02 NXT 프리 매매** — LTV 의 `tradable_boards = main,pre_nxt` 다. 이 2분 동안 LTV 는 5/32 짜리 유니버스로 돈다. 실측: 최근 4개월 08:00~08:30 매수 16건 중 15건은 08:03 이후라 실제 체결 피해는 작지만(08:00 정각 1건), **0 은 아니다**.
3. **VCP 의 ATR 6.3% 과소** — 위에서 본 대로 2차 prepare 로도 안 지워진다.

그리고 잊지 말 것: **2차 prepare 가 결함을 가려 왔기 때문에 이 결함이 3개월 넘게 안 보였다.** 그 우연이 깨지는 날(load 가 360초 초과, funnel task 비활성화, initial_delay 조정) 하루치 매매 전체가 오염된다. 이게 시정의 진짜 이유다.

## 2. ② 시정 위치 — (A) 를 권고

| 안 | 평가 |
|---|---|
| **(A) `scanner._stock_master_daily_load_once` 에서 upsert 직전 필터** | **권고.** 이 함수만이 (i) 지금이 몇 시인지 (ii) 왜 fetch 했는지 (아침 immediate / 16:00 정기 / 수동 force) 를 안다. 판정에 필요한 문맥이 전부 여기 있다. `fetch_daily_candles` 와 `fetch_daily_candles_backfill` 두 분기가 합류하는 지점이라 필터 1곳으로 양쪽을 덮는다. 8영역이지만 승인 완료 |
| (B) `stock_master_daily.upsert_batch` 에서 필터 | **반대.** ① DB 계층이 "장 마감 전 잠정봉"이라는 업무 규칙을 알게 된다 — `src/db/` 는 KST 변환·JSONB 코덱 같은 저장 규약만 아는 계층이다 ② `upsert_daily`(단건)에도 같은 규칙을 복제해야 한다 ③ 호출자를 구분할 수 없어서, 미래에 생길 *의도적* 백필/보정 경로까지 조용히 막는다 ④ 8영역을 피하는 대가로 **모든** 쓰기 경로에 규칙을 박는 것은 blast radius 를 넓히는 거래다 |
| (C) 멱등 규칙을 "실봉일 때만 skip" | **불충분.** 이건 16:00 실행을 되살릴 뿐, 스텁이 테이블에 남는 것은 그대로다. 그런데 **손상의 본체는 스텁이 테이블에 남아 다음날 아침 prepare 가 그걸 전일봉으로 읽는 것**이다(§1.1). 이 안은 진짜 문제를 안 건드린다 |
| (D) 16:00 만 `force=True` | **불충분 + 비용.** (C) 와 같은 이유로 스텁은 남고, 매일 전 종목 재fetch 비용만 추가된다 |
| (E) `_boot` 순서를 바꿔 prepare 를 load 뒤로 | **이번엔 반대.** 근본적으로 옳은 방향이지만 `scheduler.py`(라인 상한) + `boot_manager.py` 를 건드리고, 07:59 사전 구독 마감까지의 예산(07:45~07:59 = 14분)에 119초짜리 적재를 끼워 넣게 된다. 토큰 사전 발급이 이미 07:45~07:51 을 먹는다. **(A) 를 하면 이 순서 변경이 불필요해진다** — (A) 이후 아침 prepare 가 읽는 헤드는 "전일 16:00 에 쓰인 전일 실봉"이 되어 순서와 무관하게 정확하다 |

### (A) 를 넣었을 때 각 실행이 어떻게 되는가

| D 18:45 재시작 | `latest = D ≥ D` → skip | `latest = D ≥ D` → skip (이미 실봉) |
| D+1 07:51 prepare | 헤드 = **D 스텁** → 전일봉으로 오독 ❌ | 헤드 = **D 실봉** → 정상 ✅ |
| D+1 08:02 prepare | 헤드 = D+1 스텁 → `prev_idx=1` → D 실봉 사용 ✅ | 헤드 = D 실봉 → `prev_idx=0` → D 실봉 사용 ✅ (**동일**) |
| D 16:20 저녁 funnel | 헤드 = D 스텁 → `prev_idx=1` → D-1 사용 | 헤드 = D 실봉 → `prev_idx=1` → D-1 사용 (**동일**) |

**행위가 바뀌는 곳은 오직 아침 07:51 의 첫 prepare 하나다.** 08:02 와 16:20 은 byte 수준으로 같은 입력을 받는다. 시정 범위가 이렇게 좁은 것이 (A) 의 가장 큰 장점이다.

### 배치 위치 — 정확히 어디에

`src/engine/scanner.py:2236` 의 `summary["fetched"] += 1` **다음**, `:2240` 의 `upsert_batch` **직전**.

이 자리여야 하는 이유:
- `if not candles: summary["failed"] += 1` (2230행 근방) 보다 **뒤** — 필터 결과가 빈 리스트여도 그건 KIS 실패가 아니다. 앞에 두면 `failed` 카운터의 의미가 오염된다.
- `summary["fetched"] += 1` 보다 **뒤** — `fetched` 는 "KIS 응답을 받았다"는 뜻이고, 필터는 그 뒤 단계다. 순서를 바꾸면 `fetched` grep 이력이 끊긴다.
- VCP 220일 분할 backfill 분기와 일반 7일/100일 분기가 **합류한 뒤**라 한 곳으로 둘 다 덮는다.

### fail-open 원칙 (P0-1 재현 금지)

필터 계산 자체가 예외를 던지면 **현행 유지(전량 upsert)** 여야 한다. "판정에 실패하면 안 쓴다"는 fail-closed 는 P0-1 유령 키가 두 전략을 전 기간 체결 0건으로 만든 바로 그 방향이다. 시각 판정(`datetime.now(KST)`)과 `bas_dd` 파싱은 둘 다 실패 가능하다 → `try/except` 로 감싸고 예외 시 원본 `candles` 를 그대로 넘긴다 + `[daily_load_today_filter_skipped]` WARNING 1행.

## 3. ③ 판정 기준 — 시각 기준 단독 (15:40 KST)

### 규칙

> 함수 진입 시점에 `now_kst` 를 **한 번** 계산한다.
> `now_kst.time() < 15:40` 이면 → `bas_dd >= today_kst()` 인 캔들을 버린다.
> `now_kst.time() >= 15:40` 이면 → `bas_dd > today_kst()` 인 캔들만 버린다(시계 왜곡 방어).
> 그 외는 전부 기록한다.

시각은 **루프 밖에서 1회** 결정한다. 15:39 에 시작해 15:42 에 끝나는 실행이 중간에 규칙을 바꾸면 종목마다 다른 기준이 적용된다.

### 왜 데이터 기준(거래량 0 ∧ OHLC 평탄)이면 안 되는가 — 두 가지 반증

**반증 1 — 장중 부분봉을 통과시킨다.** 배포·재시작은 장중에도 일어난다(cycle248 이후 frontend 전용 push 는 backend 무접촉이지만 full 모드는 재시작한다). 14:00 재시작이면 immediate run 이 14:04 에 돌고, 그때 KIS 가 주는 오늘봉은 **거래량 > 0, OHLC 비평탄인 진짜 부분봉**이다. 데이터 기준은 이걸 "정상 봉"으로 보고 **확정봉인 척 DB 에 박는다.** 그러면 다음날 아침 prepare 는 "14:00 까지만의 고가/저가/종가"를 전일봉으로 읽는다. 지금 결함보다 더 나쁘다 — 지금은 최소한 눈에 띄게 평탄하기라도 하다. **시각 기준은 이걸 자동으로 막는다.**

**반증 2 — 진짜 무거래봉을 죽인다.** 거래정지·무거래 종목의 확정 일봉은 실제로 거래량 0 · OHLC 평탄이다. 데이터 기준으로 16:00 에 이걸 버리면 그 종목은 **그 날짜 행을 영원히 못 갖는다**(다음날 T-7 재fetch 때도 같은 이유로 또 버려진다). 100일 창에 구멍이 뚫리고, `count_by_ticker` 가 줄고, 어느 시점엔 `min_required` 게이트에 걸려 상시 KIS 폴백으로 떨어진다.

### 진짜 무거래봉은 얼마나 되는가 — 실측

의뢰서가 지키라고 한 "평시 스텁 30~70건"을 `updated_at` 기록일로 갈라 봤다. `bas_dd` 와 기록일이 **같으면** 그건 그날 아침에 쓰인 스텁(= 이 결함의 잔재)이고, 기록일이 **더 나중이면** 장 마감 후 fetch 로 확인된 진짜 무거래봉이다.

| bas_dd | 스텁 계 | 당일 기록 (결함 잔재) | 후일 fetch (진짜 무거래봉) |
|---|---|---|---|
| 08-18 | 56 | 50 | 6 |
| 08-19 | 108 | **102** | 6 |
| 08-24 | 71 | 66 | 5 |
| 08-28 | 16 | 13 | 3 |
| 09-01 | 31 | 29 | 2 |
| 09-02 | 42 | 41 | 1 |
| 09-03 | 61 | **59** | 2 |
| 09-04 | 1,082행 중 1,015 | **1,015** | 0 |

**진짜 무거래봉은 하루 1~8건**이고, 나머지 11~102건은 전부 같은 결함이 남긴 흉터다(그날 아침 스텁이 쓰였는데 그 종목이 다음날 유니버스에서 빠져 덮이지 않은 것). 시각 기준 필터는 **후일 fetch 로 들어오는 진짜 무거래봉을 정의상 100% 보존**한다(15:40 이후 실행이므로). 그리고 당일 기록 흉터는 더 이상 쌓이지 않는다.

### 커트오프를 왜 15:40 으로

- KRX 정규장 마감 15:30(15:20~15:30 마감 동시호가 포함). 마감 흡수 10분 마진 = 15:40. 코드에 이미 `TIME_POST_NXT_OPEN = time(15, 40)` 이라는 같은 감각의 상수가 있다.
- 다만 **매매 시각 상수를 재사용하지 말고 `scanner.py` 안에 전용 상수**(`_DAILY_LOAD_TODAY_BAR_CUTOFF = time(15, 40)`)로 둘 것. 매매 보드 시각을 바꾸면 적재 규약이 딸려 바뀌는 커플링은 `tradable_boards` ↔ 청산 규약 커플링을 끊어 놓은 기존 원칙과 같은 이유로 피한다.
- 여유 폭 검증: 유일한 정기 소비자는 16:00 실행이라 20분 마진이 있다. 15:30~15:40 사이에 시작되는 실행은 오늘봉을 버리지만, 그 봉은 16:00 실행이 다시 채운다.

### NXT 애프터 / 시간외 거래는 어떻게 되나

의뢰서가 물은 경계 문제다. **16:00 스냅샷은 시간외 종가매매(15:40~16:00)와 NXT 애프터(~20:00)의 누적거래량 일부를 놓칠 수 있다.** 그런데 이건 (A) 안에서 **자기 치유된다**:

다음날 아침 07:56 실행은 `latest = D` vs `today = D+1` → `D >= D+1` 거짓 → **skip 하지 않고 재fetch**한다. 그때 KIS 가 주는 D 봉은 최종본이고, `upsert_batch` 의 `ON CONFLICT DO UPDATE` 가 16:00 판을 최종본으로 덮는다. **낭비처럼 보이던 아침 재fetch 가 사실은 최종값 보장 장치가 된다.** 이 이유로 아침 immediate run 의 멱등 규칙은 **손대지 말 것**을 권고한다.

(KIS FHKST03010100 스펙 자체는 "일봉이 몇 시에 확정되는가"를 명시하지 않는다 — MCP 조회 결과에도 없다. 위 판단은 실측 근거다: 07:56 호출은 평탄 0거래량 봉을, 18:45 호출은 실봉을 준다.)

## 4. ④ 부작용 — "낮 동안 오늘 행이 없다"가 무엇을 깨뜨리는가

의뢰서 지시대로 게이트를 **숫자로 계산**했다.

### (a) `get_recent_daily_normalized` 신선도 게이트 — 유일한 실질 위험

`DAILY_STALENESS_DAYS = 4`, 조건 `(today - max_bas_dd(ticker)).days > 4` → **전 종목 KIS 폴백**.

시정 후 아침~16:00 구간의 `max_bas_dd` = **직전 거래일**. 그래서 거래일 간격이 5일 이상이면 게이트가 그날 하루(16:00 전까지) 켜진다.

2026-02-01 이후 연속 거래일 간격 실측:

| 달력일 간격 | 횟수 | 마지막 사례 |
|---|---|---|
| 1 | 112 | 09-04 |
| 2 | 2 | 06-04 |
| 3 (주말) | 24 | 08-31 |
| 4 (연휴+주말) | 5 | 08-18 |
| **6** | **1** | **2026-02-19 (설 연휴)** |

- 시정 후 게이트가 발화했을 날: **144회 전이 중 1회**(2026-02-19). 나머지는 전부 ≤4 라 무발화.
- **다음 발화 예정: 추석 연휴(2026년 9월 하순).** 목·금 휴장이면 직전 수요일 → 다음 월요일 = 간격 5 → 발화. 정확한 날짜는 KRX 휴장일 달력으로 확인 필요.
- **비용 계산**: 발화하면 `_kis_fallback` 이 `fetch_daily_candles(ticker, days=<전략별>)` 을 부른다. 캐시 키가 `(ticker, days)` 라 전략마다 days 가 다르면(VB 17 / LTV 22 / donchian 66 / kojiro 100 / VCP·BFB 각각) **종목당 최대 5~6회** 별개 호출이 된다. 1,000종목 기준 최대 5,000~6,000 호출 ≈ 20/s 세마포어에서 **250~300초**. prepare 가 그만큼 늘어진다(현재 아침 prepare 총 39초).
- **판단**: 폴백이 주는 데이터는 *더 정확한* 것이므로 위험이 아니라 지연 비용이다. 연 2~3일, 07:51/08:02 prepare 두 번에 국한된다. **이번 사이클에서 `DAILY_STALENESS_DAYS` 는 손대지 말 것**을 권고한다(그 상수는 별개 리스크 결정이고, 올리면 "D-1 미적재 감지"라는 원래 목적이 더 무뎌진다). 대신 추석 전에 이 예상 신호를 운영자에게 미리 알린다 (§8 D-3).

### (b) `count_by_ticker` 임계 (백필 50 / VCP 120) — **영향 0 (증명)**

`count_by_ticker` 는 **fetch 하기 전** 에 호출된다. 그 시점의 행 집합을 비교하면:

- 현재, D 07:56: 행 = {D-1(스텁), D-2, D-3, ...}
- 시정 후, D 07:56: 행 = {D-1(실봉), D-2, D-3, ...}

**날짜 집합이 동일**하다. 스텁은 *추가 행* 이 아니라 같은 날짜 행의 값이 틀린 것이기 때문이다. 16:00 실행도 마찬가지로 D-1 까지를 세고 나서 D 를 쓴다. 따라서 카운트는 어느 시점에도 바뀌지 않는다.

(경계값 참고 — 정확히 50행인 종목 **0개**, 정확히 120행인 종목 **20개**. 만약 카운트가 1 줄었다면 이 20종목이 7일 증분 대신 120일 분할 백필로 튈 뻔했다. 위 증명으로 해당 없음.)

### (c) `purge_old_rows` (16:15) — 영향 0
`cutoff = today - DAILY_RETENTION_DAYS(230)`. 오늘 행의 존재와 무관.

### (d) `count_all()` (scheduler 3003, 저녁 funnel 게이트) — 영향 0
`cnt > 0` 만 본다.

### (e) UI `GET /api/stock-master/stats` → `last_daily_load_at` — **보이는 변화**
`max_bas_dd()`(전체 MAX). 시정 후 **낮 동안 어제 날짜**가, 16:00 이후 오늘 날짜가 뜬다. `frontend/src/pages/StockMaster.tsx:1089` 의 "마지막 일봉 적재" 카드다.
- 크래시 없음(문자열 날짜 그대로 포맷).
- 의미상 오히려 정확하다 — "마지막으로 **확정된** 일봉"이 어제인 것이 맞다.
- 다만 운영자가 아침에 보고 "적재 실패했나?" 오해할 수 있다. **알려두거나 라벨 보완**을 결정 항목으로 올린다 (§8 D-6).

### (f) `GET /api/stock-master/daily/{ticker}` 차트 — 낮 동안 마지막 점이 어제. 무해.

### (g) `market_regime._compute_single_etf_stage` — **개선 (그러나 행위 변화)**

## 5. ⑤ 09-04 실봉 결손의 소급 보정

### 자동 치유되는가 — **된다. 단 한 박자 늦다**

월요일 09-07 07:56 의 immediate run 이 `max_bas_dd = 09-04(스텁) < 09-07` 을 보고 전 종목 재fetch → KIS 가 주는 **09-04 실봉**으로 덮는다. **별도 force 는 불필요하다.**

문제는 그게 **07:51 의 첫 prepare 보다 5분 늦다**는 것이다. 시정 코드를 지금 배포해도 그 순서는 안 바뀐다(§2 (A) 표의 "D+1 07:51" 행은 D 16:00 에 실봉이 쓰였다는 전제 위에 성립하는데, 09-04 16:00 에는 아직 시정이 없었다). 따라서 **월요일 아침 첫 prepare 는 시정 배포 여부와 무관하게 09-04 스텁을 전일봉으로 읽는다.** 화요일 07:51 부터 구조적으로 정상이 된다.

### 한 번의 클린 월요일을 원한다면 (선택)

**일요일(오늘) 중에** `POST /api/stock-master/daily/refresh?force=true` 를 1회 실행한다.

- 오늘은 `today_kst() = 09-06(일)` 이고 KIS 는 주말 봉을 주지 않는다 → **새 스텁이 생길 여지가 없다.** 09-04 실봉만 깨끗이 채워진다.
- 실행 후 `max_bas_dd = 09-04(실봉)` → 월요일 07:51 prepare 가 `prev_idx = 0` 으로 **진짜 09-04 봉**을 전일봉으로 읽는다. 시정 코드가 없어도 성립한다.
- 그 뒤 월요일 07:56 immediate 는 `09-04 < 09-07` 이라 또 전 종목을 fetch 한다(시정 전이면 09-07 스텁을 또 쓴다 — 그건 그날 16:00 skip 을 부르지만, 시정을 같이 배포하면 그것도 안 생긴다).

**비용/위험**
- KIS 호출 ~1,015건 × 50ms ≈ **2분**. VCP 유니버스 중 120행 미만 종목은 분할 backfill(3회 호출)이라 실제로는 조금 더. 세마포어가 20/s 로 직렬화하므로 LMS 한도 위험은 없다.
- 쓰기는 앱 자신의 멱등 경로(`ON CONFLICT DO UPDATE`)뿐이고, 결과는 **데이터가 더 정확해지는 방향** 한쪽이다. DDL·DELETE 없음.
- 주말이라 스케줄러는 "월요일 09-07 07:45까지 대기" 상태(로그 실측)라 매매와 경합 없음.
- **단, 이것은 운영 조치이므로 사용자 승인 사안이다.** 본 자문은 실행하지 않았다.

**적기**: 일요일 중 아무 때나. 월요일 07:45 이후는 무의미하다(이미 첫 prepare 가 지나감).

**하지 않아도 되는가**: 된다. 지난 3개월 매일 있던 것과 같은 상태의 월요일이 하루 더 있는 것뿐이고, 08:02 prepare 가 09:00 전에 보정한다. 노출은 §1.3 의 세 구멍(구독 41슬롯 배분, 08:00~08:02 LTV 프리장, VCP ATR)이다.

## 6. ⑥ 관측 — 무엇이 어떻게 보여야 성공인가

### 의미가 바뀌는 기존 마커 — `skipped_fresh`

| 실행 | 시정 전 | 시정 후 |
|---|---|---|
| 아침 07:56 | `fetched≈total`, `skipped_fresh≈0` | 동일 |
| **16:00** | `fetched=0`, **`skipped_fresh≈total`** | **`fetched≈total`, `skipped_fresh≈0`** |

`skipped_fresh` 의 뜻이 "오늘 스텁이 이미 있어서 건너뜀"에서 "이미 오늘 실봉이 있어서 건너뜀"으로 바뀐다. **배포 전후 로그를 같은 grep 으로 합산하지 말 것.** 사이클 228 이 `[*_vol_gate_observe]` 의 `would_pass` 의미 반전 때 세운 규약과 같다.

부수적으로 `upserted_rows` 총량이 하루 ~7,900 에서 ~15,800(아침 + 16:00) 으로 두 배가 된다. KIS 일봉 호출도 하루 ~1,015 → ~2,030. 이건 결함이 아니라 16:00 실행이 비로소 일을 하는 것이다.

### 새 마커 (1행/실행 — 종목당 로그 금지)

```
[daily_load_today_bar_filter] mode=drop|keep cutoff=15:40 now=07:56 today=2026-09-08 dropped_rows=1013 tickers_affected=1013
```
- 레벨 **INFO**, **실행당 1행** (요약 emit 과 같은 자리). 종목당 emit 은 하루 1,000행 폭주 — 사이클 237 donchian 청산 로그 폭주 시정의 교훈.
- fail-open 경로: `[daily_load_today_filter_skipped] reason=<...>` **WARNING**, `DailyEmitCap` 로 **1회/일** 상한(사이클 258 `KstDailyEmitCap` 재사용).

### D+1 성공 서명 (배포 다음 거래일에 확인할 것)

1. **16:00 요약이 일을 한다** — `[stock_master_daily_load_summary]` 에 `fetched≈total`, `skipped_fresh≈0`, `upserted_rows` 수천 대.
2. **스텁이 안 생긴다** — `SELECT count(*) FROM stock_master_daily WHERE bas_dd = <오늘> AND volume = 0 AND high_price = low_price AND (updated_at AT TIME ZONE 'Asia/Seoul')::date = bas_dd` 가 아침에 **0**.
3. **★ 두 prepare 가 수렴한다 (핵심 지표)** — 07:51 과 08:02 의 `준비 완료: N/M` 이 전략별로 거의 같아야 한다. 특히 **LTV 가 07:51 에 이미 `N/N` 에 가까울 것**(지금은 5/32, 10/90). donchian 은 07:51 의 `donchian=`·`volume=` 이 08:02 값과 일치.
4. **VCP ATR 편향 소멸** — `[vcp_atr_mismatch]` 는 여전히 0건이 정상이지만(±10% 안), `_candidates[atr14]` 가 평균 6.7% 커진다. 직접 관측하려면 배포 전후 같은 종목의 `db_atr` 값을 비교.
5. **신선도 게이트 무발화** — 평일 간격 1~3 이므로 `[prepare_db_fallback] reason=stale` 이 **안 나와야** 정상. 나오면 16:00 실행이 실패한 것이다(= 새 조기경보 신호로 쓸 수 있다).
6. UI "마지막 일봉 적재" 가 낮에 **어제 날짜** — 이건 정상이다.

### 하지 말 것

- 스텁을 집계에서 **빼서** 숫자를 좋게 만들기 (cycle252 의 `[tick_coverage] stale` 금기와 동형).
- `skipped_fresh` 급감을 "적재 실패"로 오탐하는 알람 추가 — 의미가 바뀐 것이다.

## 7. ⑦ 배포 창과 되돌리기

**오늘(일요일) 배포하면 월요일 07:45 부팅에 반영되는가 — 반영된다.**

- 스케줄러는 주말에 `start()` 를 하지 않는다(로그 실측: "주말 — 월요일 09-07 07:45까지 대기 (55시간)"). 배포 = backend 재생성 = 프로세스 재시작이고, 재시작해도 다시 월요일 07:45 까지 대기한다. 매매 무영향.
- 배포 창: `src/engine/scanner.py` 변경이므로 `tools/deploy/compose_up_changed.sh` 판정은 **full**(backend 재시작). 주말 종일은 승인된 장외 창이다. D6(보유 중 09:00~15:30 push 금지)는 장이 닫혀 있어 해당 없음. **20:00~20:15 회피 규칙만 지키면 된다**(자문·정산 task 는 주말에 안 도는 것으로 보이지만, 규칙은 규칙대로 지키는 편이 안전).
- 반영 시점: 월요일 07:45 `start()` → 07:56 immediate run 이 **첫 필터 적용**, 16:00 정기 run 이 **첫 실봉 기록**. 즉 **효과의 절반은 월요일 16:00 부터, 나머지 절반(아침 prepare 정상화)은 화요일 07:51 부터**다.

**되돌리기**
- 방법: 해당 커밋 revert 후 push → full 배포 → backend 재시작.
- 반영 시점: **재시작 즉시**(코드 경로라 DB/파라미터 반영 지연 없음). 단 cycle232 D6 때문에 **보유 중 장중에는 되돌릴 수 없다** — 15:30 이후 또는 익일 07:45 전.
- 되돌린 뒤 데이터 상태: 이미 기록된 실봉은 남고, 다음 아침 실행이 다시 스텁을 쓰기 시작한다. 데이터 파손은 없다(모든 쓰기가 멱등 upsert).
- **런타임 스위치가 필요한가**: 권고하지 않는다. 커트오프를 파라미터로 빼면 "적재 규약"이 AI 자문 튜닝 표면에 노출된다. 급하면 커트오프 상수를 `time(0, 0)` 으로 바꾸는 1줄 revert 가 사실상 동일한 다이얼이다.

## 8. ⑧ 반례 · 한계 · 사람이 정할 것

### 이 시정이 틀릴 수 있는 경우

1. **KIS 가 15:40 이전에도 확정봉을 주는 종목/상황이 있다면** 하루치 적재가 16:00 으로 미뤄질 뿐이다. 손실 없음.
2. **KIS 가 16:00 시점에 아직 시간외 물량을 반영 안 했다면** 16:00 판이 약간 덜 익은 값이 된다. → 다음날 아침 재fetch 가 최종본으로 덮는다(§3). **그래서 아침 immediate run 의 멱등 규칙을 절대 "직전 거래일이면 skip" 으로 최적화하지 말 것** — 그 최적화가 이 자기 치유를 없앤다.
3. **16:00 실행이 실패한 날**(KIS 장애 등) — D 봉이 다음날 아침까지 비고, 그날 07:51 prepare 는 D-1 실봉을 전일봉으로 읽는다. 하루 stale 하지만 **지금처럼 평탄 0거래량 가짜봉을 읽는 것보다는 명백히 낫다**. 그리고 이 상황은 §6-5 의 `reason=stale` 신호로 관측된다.
4. **연휴 5일 이상**에서 아침~16:00 동안 전 종목 KIS 폴백(연 2~3일, 250~300초 지연). §4(a).
5. **08:02 우연 복구에 대한 의존을 이 시정이 없애 주지는 못한다.** (A) 는 아침 첫 prepare 의 *입력* 을 고칠 뿐, "prepare 가 적재보다 먼저 돈다"는 순서 자체는 그대로다. 16:00 실행이 실패한 다음날에는 다시 08:02 가 유일한 보정이다. 순서 시정(안 (E))은 별도 사이클 의제로 남긴다.
6. **7 전략이 전부 `prev_idx` 가드를 갖고 있다는 전제** 위에서 "08:02·16:20 은 무변화"라고 판단했다. 새 전략을 추가할 때 이 가드를 빠뜨리면 전제가 깨진다 → 회귀 가드로 박아 둘 것(§9).

### 이 자문이 확인하지 못한 것

- KIS FHKST03010100 의 "일봉 확정 시각" 공식 스펙. MCP·문서 모두 명시 없음. 15:40 커트오프는 **실측 기반 추론**이다(07:56 평탄봉 / 18:45 실봉).
- 추석 2026 정확한 휴장일. KRX 달력으로 확인 필요.
- 시정 전후의 실체결 손익 차이. 오염된 후보로 실제 체결된 건은 08:00 정각 LTV 1건만 식별했다(최근 4개월). 나머지 손해는 **기회 손실**(진짜 후보를 못 산 것)이라 사후 측정 불가.

## 9. 후속 검증 권고 (tdd-engineer / tester)

**Red 로 먼저 잡아야 할 행위** (전부 순수 함수 수준으로 분해 가능):

1. `now < 15:40` + 캔들에 오늘 날짜 포함 → **오늘 캔들만** 제외, 나머지 순서·내용 byte 동일.
2. `now >= 15:40` + 오늘 캔들이 **거래량 0 · OHLC 평탄** → **보존**(거래정지 종목 회귀 가드). 이게 §3 반증 2 의 잠금.
3. `now = 14:00` + 오늘 캔들이 **거래량 > 0 · 비평탄**(장중 부분봉) → **제외**. 이게 §3 반증 1 의 잠금 — 데이터 기준으로 구현하면 이 케이스가 붉어진다.
4. 커트오프는 **함수 진입 시 1회** 결정 — 15:39 진입 후 시계를 15:41 로 진행시켜도 같은 규칙이 적용되는지(freezegun `tick`).
5. 시각 판정·`bas_dd` 파싱 예외 → **fail-open**(원본 전량 upsert) + `[daily_load_today_filter_skipped]` 1행. 예외를 전파해 ticker 루프를 끊지 않을 것.
6. `if not candles: failed += 1` 와 `summary["fetched"] += 1` 의 카운터 의미 불변 — 필터가 전량 제거해도 `failed`/`fetched` 는 안 움직인다.
7. 멱등 상호작용 시나리오 테스트: `07:56 → 16:00 → 익일 07:56` 3연속 실행에서 (i) 16:00 이 skip 되지 않고 (ii) 익일 아침이 D 봉을 최종본으로 덮는지.
8. **AST/회귀 가드 (영구)**: 7 전략 `prepare()` 에 `prev_idx = 1 if candles[0].get("stck_bsop_date") == today_str else 0` 형태의 오늘봉 가드가 존재한다는 것을 강제. 새 전략이 이걸 빠뜨리면 §8-6 전제가 깨진다.
9. 마커 서식 잠금 — `[daily_load_today_bar_filter]` 는 실행당 1행(종목 1,000개 입력으로 emit 횟수 == 1 단언).

**tester 통합 확인**: 배포 D+1 에 §6 의 서명 1~6, 특히 **3(두 prepare 수렴)**. 수렴하지 않으면 시정이 안 먹은 것이거나 다른 오염원이 있는 것이다.

| "야간·새벽으로 옮겨 한 번만 돌리면 되지 않나" | **결론은 옳고 수단은 불가** | 시각 이동은 스케줄러 수명 때문에 구조적으로 불가(§A-1 (나)). 그러나 "하루 한 번"은 (가) 한 줄로 달성된다 |

## A-1. ⑨ 아침 immediate run 폐지안 평가

### 먼저 확정한 코드 사실

1. **task loop 은 트레이딩 세션 안에서만 산다.** `run_periodic_task_loop` 의 본체는 `while scheduler._running` 이고, `scheduler.py:1035` 가 20:10 정산·정리 직후 `self._running = False` 를 세운다. `run_daily`(`:1040~`)는 그 뒤 다음 영업일 `TIME_AUTO_START(07:45)` 까지 `asyncio.sleep` 한다. task 들은 종료 시 cancel 목록(`:998/:1124/:1159`)에서 취소된다.
   → **`TIME_STOCK_MASTER_DAILY_LOAD` 을 23:00 이나 05:00 으로 바꾸면 그 시각에는 루프가 존재하지 않아 영원히 발화하지 않는다.** KIS 토큰(24h)·API 가용성은 걸림돌이 아니다. 걸림돌은 스케줄러 수명이다.
2. **`run_daily` 는 주말과 공휴일에 세션을 아예 열지 않는다**(`:1049` 주말, `:1090` `is_market_open`). 즉 비영업일에는 적재 자체가 없다.
3. **신선도 게이트는 이미 프로덕션에서 동작 중이다.** `system_config` 실측:

   | key | value |
   |---|---|
   | `task_last_success_stock_master_basics_refresh` | 2026-09-04T16:23:36+09:00 |
   | `task_last_success_stock_master_master_load` | 2026-09-04T16:30:13+09:00 |
   | `task_last_success_stock_master_financial_load` | 2026-09-04T16:40:01+09:00 |
   | `task_last_success_stock_master_daily_load` | **부재** (게이트 미적용이라 기록한 적 없음) |

   basics 는 D-1 16:23 → 익일 07:55 = 15.5h < 20h 로 실제로 immediate 를 건너뛰고 있다. **daily_load 에 같은 인자를 주면 같은 일이 일어난다.**
4. **마커는 `once_callable()` 이 예외 없이 반환하면 무조건 기록된다** — 전 종목 skip 도 "성공"이다(`task_loop_helper.py:139~148`). 뒤집으면 **16:00 이 실패(raise)하거나 프로세스가 죽어 있으면 마커가 갱신되지 않아 다음 아침 immediate 가 자동으로 되살아난다.** 이게 (가)의 안전망 보존 근거다.

## A-2. ⑩ 액면분할·병합 소급 정정 — 사용자 가설 정면 답변

### 전제는 맞다 — KIS 는 과거 봉을 소급 재조정한다 (실측 증명)

우리는 `FID_ORG_ADJ_PRC="0"`(수정주가)로 호출한다(`condition.py:530, 647`). 라이브 데이터가 소급 조정을 직접 보여준다.

**종목 210980, 2026-09-01 권리락 (`flng_cls_code=01`, `prtt_rate=-31.96`)**

| bas_dd | 종가 | 이 행이 DB 에 쓰인 시각 |
|---|---|---|
| 08-20 | 4,855 | **08-28 16:31** (락 이전 기록) |
| 08-21 | 4,500 | **08-28 16:31** |
| 08-24 | 4,445 | **08-28 16:31** |
| 08-25 | **3,054** | **09-02 07:57** (락 이후 재fetch) |
| 08-26 | 3,163 | 09-03 07:57 |
| 09-01 | 3,650 | 09-04 07:56 ← 락일 |

`4,445 × (1 − 0.3196) = 3,024 ≈ 3,054`. 08-25 행은 조정 후 값이고 08-24 행은 조정 전 값이다. **DB 안에 −33% 짜리 가짜 갭이 박혀 있다.**

### 그러나 결론은 틀리다 — T-7 창은 분할 정정에 구조적으로 불충분하다

락일 T-7 창은 08-25~09-01 만 덮었다. **08-24 이전은 지금까지도 미조정**이다. 하루 두 번을 돌든 한 번을 돌든 창은 7일이라 결과가 같다.

미조정 잔존 규모 (실측, 2026-07-08 이후 락 발생 종목 기준):

| 지표 | 값 |
|---|---|
| 락 발생 종목 (60일) | **271** (`flng_cls_code` 01/02/03/05 또는 `prtt_rate ≠ 0`) |
| 그중 락 이전에 기록되고 이후 한 번도 재기록되지 않은 행 | **26,844행 / 242종목** |

즉 **미조정 행은 이미 2.7만 행 존재한다.** 아침 실행이 이걸 막아준 적이 없다.

### 실제 방어는 사이클 173 락 게이트다 (적재 빈도와 무관)

`get_recent_daily_normalized` 가 요청 창 안에서 `flng_cls_code ∉ ("","00")` 또는 `prtt_rate ≠ 0` 인 행을 **하나라도** 보면 DB 를 버리고 KIS 를 강제 폴백한다. KIS 는 조회 시점 기준으로 전 구간을 일관되게 재조정해서 준다. 210980 은 09-01 행이 창(donchian 66 / kojiro·VCP 100) 안에 있는 동안 이 게이트에 걸려 KIS 로 간다. 락일이 창 밖으로 밀려날 때쯤이면 창 전체가 락 이후 구간이라 DB 도 일관된다. **설계가 정합하고, 적재 빈도와 완전히 독립이다.**

**⇒ 아침 실행을 없애도 액면분할 대응력은 조금도 줄지 않는다.** 사용자가 걱정한 사유는 이 결정의 제약이 아니다.

### 별건 발견 — 락 게이트를 안 타는 소비자 3곳

`get_recent_daily()` 를 **직접** 부르는 곳은 락 검사를 거치지 않는다.

| 호출부 | 창 | 위험 |
|---|---|---|
| `stock_master_daily.get_atr()` ← VCP `vcp_breakout.py:453` | 14일 | 락 후 14일 이내면 조정 전/후 혼재 → ATR 폭증. **다만 VCP 의 ±10% 교차검증이 뒤에서 잡는다** — `[vcp_atr_mismatch]` 실측 30일 **2건** 발화. 설계가 이 케이스는 잡고 있다 |
| `market_regime._compute_single_etf_stage` `:674` | 90일 | ETF(069500/229200)는 분할 희소. 관찰 전용 |
| VB RS/RSI 관찰 `:604, :619` | 30일 | 기본 OFF, 스코어만 |

대비가 중요하다: **락 편향은 크기가 커서 ±10% 문턱에 걸리고, 스텁 편향은 6.3% 라 문턱 아래로 샌다.** 그래서 스텁 결함만 3개월 동안 안 보였다.
