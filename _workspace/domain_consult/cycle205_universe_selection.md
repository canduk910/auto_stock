# 자문 주제 — 전략 유니버스 선별 기준 (refreshed_at 편향 시정)

**요청**: 자격 종목 >> max_scan_stocks 일 때, 5전략이 스캔할 N개를 고르는 매매적으로 올바른 기준.
**긴급도**: MEDIUM (실매매 — 매수 후보 집합 결정)
**작성일**: 2026-07-11 (사이클 205)

## 질문 요약

`list_by_filter` 가 `refreshed_at DESC` 정렬 후 `limit*2` 버퍼 fetch → Python-side 시총/거래대금 필터 → `len(filtered) >= limit` 절단. **정렬 키(refreshed_at)가 유동성/품질과 무관** → 자의적 부분집합만 스캔. 실측 스캔률 BFB 12% / VB·LTV 40% / donchian 59% / VCP 61%. 무엇을 N개로 고르느냐가 매수 후보를 결정하는데 현재는 사실상 "랜덤".

**코드 사실 확정** (`src/db/stock_master.py:614-655`):
```
.order("refreshed_at", desc=True).limit(max(limit*2, 1000))   # ← 선별 편향의 진원지
... Python-side 시총/거래대금 필터 ...
if len(filtered) >= limit: break                               # ← refreshed_at 순 절단
```
refreshed_at 은 16:10 basics refresh / lazy upsert 시각 → **종목 품질과 완전 무관한 축**. 최악의 경우 "가장 최근에 상세정보를 갱신한 종목 = 매수 후보"라는, 매매 논리상 의미 없는 선별.

## 트레이더 시각

### 1. refreshed_at 편향은 "무조건" 결함 — 이건 논쟁 대상이 아니다

트레이더 관점에서 refreshed_at 절단은 **selection이 아니라 noise**다. 스캔 유니버스를 좁힐 거면 좁히는 **축(axis)에 매매 의미가 있어야** 한다. refreshed_at 은 "이 종목 데이터를 언제 마지막으로 DB에 썼나"일 뿐, 오늘 이 종목이 돌파 셋업을 만들지와 0의 상관. 그러니 **어떤 매매적 정렬 축으로 바꿔도 현재보다 나쁠 수 없다.** 이건 순수 개선(strict improvement)이고, 1차 시정의 안전한 하한선이다.

증상(BFB 후보 42~143 요동, 주말 11)의 뿌리도 여기다. refreshed_at 은 배치 실행 타이밍/재시작에 따라 순서가 흔들리므로, 같은 시장에서도 스캔 대상이 매일 바뀐다. 매매 시스템이 "어제와 오늘 다른 종목을 본다"는 건 백테스트-실매매 괴리의 전형적 원인이다.

### 2. 핵심 딜레마: 거래대금 DESC 는 돌파류에 독(毒)이 될 수 있다 — 요청자 우려가 정확하다

이게 이 자문의 진짜 쟁점이다. "유동성 DESC top-N"은 직관적이고 체결 안전하지만, **돌파/모멘텀 전략의 알파 원천과 정면충돌**한다.

- **돌파류(BFB/VB/LTV/momentum)의 수익 구조**: 중형 급등주가 눌림(flag)을 만들거나 전일 변동폭을 돌파할 때 진입. 이 셋업을 잘 만드는 건 **시총 3,000억~2조 중형주**다. 이들은 유동성은 충분하되(거래대금 20억~수백억), 삼성전자·SK하이닉스처럼 하루 거래대금 조 단위는 아니다.
- **거래대금 DESC top-100 을 하면** 리스트 상단이 초대형주(삼성전자, SK하이닉스, 현대차, 카카오, 네이버…)로 채워진다. 이들은 **깊은 눌림도, 날카로운 돌파도 잘 안 만든다** — 기관/외국인/패시브 자금이 두껍게 받쳐 변동성 자체가 억눌려 있다. 정작 BFB 가 노리는 중형 플래그주는 거래대금 순위 100위 밖으로 밀려나 **스캔조차 안 된다.**
- 즉 거래대금 DESC 는 "체결은 안전하지만 셋업이 없는 종목"만 남기고 "셋업은 좋지만 순위가 낮은 종목"을 버린다. **이건 refreshed_at 랜덤보다 특정 방향으로 더 나쁠 수 있다** (초대형주 편향은 체계적 알파 손실).

반대로 **스윙류(donchian/VCP)**는 이야기가 다르다. 이들은 이미 index 제한(KOSPI200∪KOSDAQ150 ~348종목)으로 우량주 풀에 갇혀 있고, 멀티데이 보유라 유동성 높은 우량주가 오히려 적합하다. 여기선 거래대금 or 시총 정렬 무방하다.

### 3. 그럼 무엇으로 top-N 을 골라야 하나? — 축을 바꾸는 순간 "능동적 선별"이 되어버린다

여기가 함정이다. 거래대금 DESC 대신 "전일 등락률 DESC"나 "거래대금 급증률 DESC"로 고르면 돌파주 포착에 유리해 보인다. 하지만:

- **전일 등락률 DESC**: 이미 어제 급등한 종목만 본다 → 이미 터진 뒤 추격. BFB flag 는 "급등 후 눌림"인데 등락률 DESC top-N 은 눌림 중인(전일 하락) 종목을 배제 → **flag 셋업을 스스로 제외**하는 자기모순.
- **거래대금 급증률 DESC**: 오늘 데이터가 없으면(장 시작 전 prepare 시점) 어제 급증만 본다 → 선행성 없음. 게다가 급증률은 세력 개입/뉴스 스파이크에 민감 → 작전주 유입 위험.
- **어떤 모멘텀 지표로 top-N 을 고르든, 그 순간 "우리가 종목을 능동적으로 골랐다"는 뜻**이다. 그런데 각 전략의 진입 로직(prepare의 패턴 검출)이 이미 정교한 선별기다. 유니버스 단계에서 또 다른 선별을 얹으면 **이중 필터 → 셋업 다양성 손실 + 파라미터 튜닝 표면적 증가**. 트레이더는 이걸 "over-fitting the funnel"이라 부른다.

### 4. 결론적 통찰: 돌파류는 "선별하지 말고 전량 보라" — 요청자 가설이 맞다

돌파류의 올바른 답은 **선별 기준을 고르는 게 아니라, 선별 자체를 없애는 것**이다. 근거:

- **비용이 0에 가깝다**: 사이클 173으로 prepare 일봉이 DB source가 되어 KIS 호출 0. 패턴 검출은 오프라인 compute — 종목당 수십 candle 배열 순회 + 지표 계산. 821종목 전량 스캔해도 CPU 수백 ms 수준(장 시작 전 prepare 창에서 여유).
- **selection bias 를 원천 제거**: 자격 종목을 전량 보면 "어떤 축으로 골랐나" 질문 자체가 소멸. 각 전략의 진입 로직만이 유일한 선별기가 되어 백테스트-실매매 정합성이 올라간다.
- **min_market_cap / min_trade_amount 가 이미 하한 게이트**: BFB 500억/20억은 이미 작전주·유동성 부족 종목을 걸러낸다. 자격 821은 "매수해도 되는 종목"의 정의 그 자체 → 이걸 임의로 100개로 자르는 게 오히려 부자연스럽다.

단, 전량 스캔에는 **하류(downstream) 병목 2개**를 반드시 점검해야 한다 (아래 반례 참조).

### 위험 시나리오 (가설이 깨지는 경우)

1. **후보 폭증 → WebSocket 41슬롯 초과**: 전량 스캔으로 prepare가 매수 후보를 200~800개 뱉으면 scanner가 시세 구독을 신청 → 41슬롯(사이클 7-C) 압박. **단 이건 prepare 후보 수 ≠ 구독 대상 수**임을 확인해야 한다. scanner는 prepare 후보 중 가격필터/거래대금필터로 추가 축소하고, 실제 매수 신호가 임박한 종목만 HIGH로 구독한다. LOW 후보가 41을 넘으면 priority_drop 되므로 안전망은 있으나, **후보가 수백이면 LOW drop이 상시화 → 정작 좋은 셋업이 구독 슬롯 부족으로 시세 못 받는 역설**이 생길 수 있다. 이 경우 전량 스캔의 이득이 구독 병목으로 상쇄된다.
2. **패턴 검출 compute 실측 미검증**: "수백 ms"는 추정. BFB/VCP prepare가 821종목 × (DB일봉 fetch + 지표 계산)을 도는 실제 wall-clock을 측정하지 않으면, 장 시작 전 prepare 창(09:00 직전)을 넘길 위험. 특히 VCP는 100일 일봉 × 베이스/pullback 검출로 종목당 무겁다.
3. **저품질 진입 증가 우려는 과장**: "후보 많으면 저품질 매수"는 유니버스 단계 우려가 아니다. 진입 판단은 prepare 패턴 검출 + 실시간 돌파 확인이 하므로, 유니버스를 넓혀도 진입 임계가 낮아지는 게 아니다. 다만 max_positions(BFB/VCP 5) 슬롯 경쟁이 치열해져 "먼저 신호 뜬 종목"이 슬롯을 먹는 선착순 편향은 커진다 — 이건 유니버스와 무관한 별도 이슈(포지션 배분 정책).

## 정량 권고

### ① 전략군별 선별 기준

| 전략군 | 권고 기준 | 근거 |
|--------|-----------|------|
| **돌파류** (BFB/VB/LTV/momentum) | **전량 스캔** (선별 회피) — 불가 시 **시총 DESC** | 거래대금 DESC = 초대형주 편향 = 중형 셋업 배제. 시총 DESC도 편향 있으나 거래대금보다 중형주 잔존율 높음. 최선은 선별 자체 제거 |
| **스윙류** (donchian/VCP) | **거래대금 DESC** (전량 불필요) | 이미 index 제한 ~348. 멀티데이 보유 → 유동성 높은 우량주 적합. 거래대금 DESC = 체결 안전 + 슬리피지 최소 |

**핵심**: 돌파류와 스윙류는 기준이 달라야 한다. 요청자 직관이 정확하다.

### ② max_scan_stocks 상향값 (전략별)

전량 스캔 지향이되, **위험 시나리오 1(구독 병목) 미검증 상태이므로 단계적 상향** 권고. 한 번에 821로 열지 말 것.

| 전략 | 자격 | 현재 | **1차 권고** | 최종 목표 | 비고 |
|------|:---:|:---:|:---:|:---:|------|
| **BFB** | 821 | 100 | **300** | 500~전량 | 가장 심한 편향(12%). 300으로 3배 확장 후 구독/compute 실측 |
| VB/LTV | 248 | 100 | **250** (≈전량) | 전량 | 자격 248 → 250이면 사실상 전량. min_trade_amount 200억이 이미 강한 게이트 |
| donchian | 341 | 200 | **350** (전량) | 전량 | index 제한이 이미 상한. 전량 스캔 자연스러움 |
| VCP | ~330 | 200 | **330** (전량) | 전량 | 단 compute 무거움 → prepare wall-clock 실측 필수 |

**BFB만 단계적(300)**, 나머지는 이미 자격이 작아 바로 전량 열어도 무방. BFB 300 근거: 현재 100 → 300은 3배로 selection 편향을 크게 완화하면서 구독 슬롯(41)·compute 리스크를 관리 가능한 범위로 확장. 300 스캔이 안정적이면 다음 사이클에서 500 → 전량.

### ③ 유동성 최소 하한 (min_trade_amount)

**현재 하한 유지로 충분** — 상향 불필요.

- BFB 20억 / VB·LTV 200억 / donchian 10억 / VCP 30억.
- 이 하한이 이미 "체결 가능성" 게이트다. 20억이면 하루 중 언제든 수백만 원 단위는 슬리피지 최소로 체결된다(종목당 매수금액이 순자산 × 전략비중 × position_ratio라 대개 수백만~수천만 원 규모).
- 유동성 하한을 올리면(예: BFB 20억→50억) 그건 유니버스를 좁히는 것 = 선별 편향 완화 취지와 역행. **하한은 "안전 바닥"으로 두고, 정렬/절단으로 위쪽을 자르지 않는 게 핵심.**
- 전량 스캔으로 가면 상단 절단이 없으므로 하한이 유일한 유동성 게이트가 되는데, 현재 값이면 충분하다.

### ④ 편향 시정의 순수 이득 — 최소 안전 1차 시정

**refreshed_at → 매매적 축으로 정렬 전환은 무조건 개선.** 최소 안전 1차 시정 2단 구성:

- **1-a (제로 리스크)**: `list_by_filter` 정렬을 `refreshed_at DESC` → **거래대금(acml_tr_pbmn) DESC**로 전환. 이것만으로 "랜덤 절단"이 "유동성 순 절단"으로 바뀌어 최소한 체결 안전한 종목이 스캔된다. **단 돌파류엔 초대형주 편향 부작용**이 있으므로 이건 어디까지나 max_scan_stocks 상향 전의 임시 하한.
  - 구현 주의: 현재 시총/거래대금 필터는 Python-side. 정렬을 거래대금으로 하려면 DB order 불가(JSONB string) → **Python-side에서 필터 후 거래대금 DESC 정렬 후 절단**해야 함. 아니면 사이클 168 생성 컬럼 `acml_tr_pbmn_won` DB order 활용.
- **1-b (본질 시정)**: max_scan_stocks 상향 (위 ② 표) → 절단 자체를 최소화. 전량에 가까워지면 정렬 축이 무의미해져 편향 소멸.

**가장 안전한 최소 1차 = 1-b 우선** (BFB 100→300, 나머지 전량). 정렬 축 논쟁(거래대금 vs 시총)은 절단이 사라지면 자동 해소되므로, **정렬을 바꾸기보다 절단을 없애는 게 근본적**이다. 1-a는 "전량이 구독 병목으로 막힐 때"의 폴백으로 남겨둔다.

## 현 코드와의 정합성

### 충돌 항목

- **`DEFAULT_PARAMS.max_scan_stocks` 변경** = 매매 파라미터 변경 → `_workspace/00_leader_trading_rules.md` 동기화 의무 (CLAUDE.md 규칙). BFB 100→300, VB/LTV 100→250, donchian 200→350, VCP 200→330.
- **`list_by_filter` fetch 버퍼 `max(limit*2, 1000)`**: limit이 300~350으로 커지면 fetch가 700개 → 여전히 1000 하한 안이라 무방. 단 전량(500+)로 가면 `limit*2`가 1000 초과 → PostgREST `db-max-rows` cap 점검 필요 (사이클 128/175 계열 silent cap 재발 위험). **전량 스캔 시 이 fetch 버퍼가 실제로 자격 전량을 담는지 반드시 검증.**
- **정렬 축 변경 시** (1-a 채택 시): `.order("refreshed_at", desc=True)` 를 건드리면 `list_paged_by_filter` (UI 페이징, refreshed_at DESC 영속)와 혼동 주의 — **scanner용 `list_by_filter`만** 변경, UI용 `list_paged_by_filter`는 불변.

### 변경 vs 유지 선택지

- **유지**: refreshed_at 정렬 그대로 두고 max_scan_stocks만 상향 → 절단이 줄어드니 정렬 축 무관해짐. **가장 단순, 정렬 코드 무변경.** ← **권고**
- **변경**: 정렬을 거래대금 DESC로 바꾸고 max_scan_stocks 유지 → 편향은 "유동성 순"으로 개선되나 돌파류 초대형주 편향 부작용. 절단 여전.
- **둘 다**: 정렬 거래대금 DESC + max_scan_stocks 상향 → 안전하나 정렬 코드 변경 리스크 추가.

**최소 리스크 정공 = max_scan_stocks 상향 단독(유지안).** 정렬을 안 건드리면 회귀 표면적이 파라미터 4개로 국한된다.

### 안전 제약 준수 확인

## 반례 / 한계

1. **거래대금 DESC 초대형주 편향은 "정도" 문제** — BFB min_trade_amount 20억 하한 덕에 거래대금 DESC top-100이 전부 초대형주는 아니다. 중형주도 일부 포함된다. 다만 **상단이 대형주로 쏠려 중형 셋업의 스캔 확률이 체계적으로 낮아진다**는 편향 방향은 확실. "완전 배제"가 아니라 "확률 저하".
2. **전량 스캔이 항상 우월한 건 아니다** — 만약 prepare compute가 실측상 무겁거나(VCP 821 × 100일봉) 구독 병목이 심하면, "전량"의 이론적 순수함이 운영 현실에서 깨진다. 이 경우 시총 DESC로 상위 500만 보는 게 실용적 타협. **compute/구독 실측 없이 전량으로 직행 금지.**
3. **momentum은 별개** — momentum은 실시간 scan(scanner.py) 기반이라 list_by_filter/max_scan_stocks 경로가 아닐 수 있음 (사이클 132 funnel 영구 제외 이력). momentum 유니버스는 별도 확인 필요 — 이 자문의 ①②는 prepare 기반 5전략(VB/LTV/donchian/BFB/VCP)에 적용, momentum은 스캔 경로 재확인 후 판단.
4. **"주말 11개" 요동**은 유니버스 선별과 별개 — 주말은 거래일이 아니라 basics refresh가 안 돌아 refreshed_at이 오래된 것. max_scan_stocks 상향으로 완화되나 근본은 "주말 prepare가 D-1 데이터로 도는" 별도 정상 동작.

## 후속 검증 권고 (tdd-engineer / tester)

1. **tdd-engineer** — `list_by_filter` limit 상향 시 fetch 버퍼(`max(limit*2, 1000)`)가 자격 전량을 담는지 회귀 테스트. 특히 limit 500+ 시 PostgREST db-max-rows 1000 cap 재발(사이클 128/175) 여부. 합성 시리즈: 자격 821종목 mock → limit=300/500/821 각각에서 반환 종목 수 정확성.
2. **tester** — **D+1 운영 실측 3축**: (a) BFB prepare 후보 수 변화(300 상향 후 실제 몇 개 나오나) (b) WebSocket 구독 LOW priority_drop 발생 빈도(41슬롯 병목 실증) (c) prepare wall-clock (특히 VCP 330종목 × 100일봉 검출 시간이 09:00 prepare 창 안인지).
3. **domain-expert(재자문 트리거)** — D+1 실측에서 구독 병목이 심하면(LOW drop 상시화) "전량 스캔 → 시총 DESC 500 절충"으로 후퇴할지 재판단. compute가 창 초과하면 VCP만 별도 취급.
4. **momentum 스캔 경로 확인** — momentum이 list_by_filter를 안 쓴다면 이 자문 범위 밖. 쓴다면 돌파류 기준(전량/시총 DESC) 적용.
