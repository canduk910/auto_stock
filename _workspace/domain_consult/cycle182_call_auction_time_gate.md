## 질문 요약

사이클 162 가 동시호가 시간대 stale 회피용으로 도입한 `is_call_auction_now()` 의 **코드 기반 분기(L209)** 가 시간창 게이트 없이 무조건 먼저 `return True` 한다. KIS H0UNMKO0 가 동시호가 *종료* 전환 코드를 reliably push 하지 않으면 `_last_nxt_mkop_code`("110" 또는 "121")가 영구 고착 → `is_call_auction_now()` 가 해당 코드 다음날 08:30 까지 영구 True → stale_watcher 가 **보유 종목 stale 탐지를 일절 안 함** → 손절/익일청산 틱 누락 위험.

권고 요청: (1) KIS push 행태 정본 확인 (2) 시정 방식 A(시간창 게이트)/B(전환 코드 리셋)/C(TTL) 택1 (3) stale-5 KST 처리 (4) 사이클 162 정당한 skip 보존.

## 트레이더 시각 — 동시호가와 stale 회피의 본질

### 시장 가설 (사이클 162 가 옳게 본 것)

동시호가(call auction)는 **체결이 누적만 되고 발생하지 않는** 시간대다. KRX 장전 동시호가(08:30~09:00)·장후 동시호가(15:20~15:30) 동안 호가는 쌓이지만 단일가 체결은 구간 끝(09:00:00.xx / 15:30:00.xx)에 한 번 터진다. 따라서 이 구간에 "체결 틱이 안 들어온다"는 것은 **정상**이고, 이를 WebSocket 끊김(stale)으로 오판해 강제 재구독하면 KIS LMS/앱키 정지 chain 위험만 키운다. 사이클 162 의 skip 자체는 트레이더 관점에서 정당하다.

### 위험 시나리오 (사이클 162 가 놓친 것 — 결함의 본질)

문제는 "동시호가가 *아닌데도* skip 이 켜진 채로 고착"되는 경우다. `is_call_auction_now()` 가 True 인 동안 stale 탐지가 **전면 중단**되므로, 동시호가가 아닌 정규장/NXT 애프터에 이 값이 True 로 고착되면 **보유 종목의 WebSocket 끊김을 영원히 못 잡는다.** 이건 단순 관찰성 문제가 아니라 **손절·익일청산 틱 누락 = 매매 안전성 직결**이다.

고착 시나리오는 두 갈래이고, **메인 세션 사고(stuck-110)가 사용자 보고한 NXT-after 사고(stuck-121)보다 더 위험하다**:

- **stuck-121 (사용자 보고)**: 15:20 장후 동시호가 "121" 수신 후 15:30 장마감 전환 코드(129) 미수신 → 15:30~20:00 NXT 애프터(보유 종목 NXT 거래 활발) 내내 stale 탐지 OFF. 다음날 08:30 "110" 까지 지속.
- **stuck-110 (더 위험, 자문 신규 지적)**: 08:30 장전 동시호가 "110" 수신 후 09:00 장개시 코드(112) 미수신 → **09:00~15:20 정규장(MAIN) 전체** stale 탐지 OFF. 보유 종목 거래가 가장 활발한 피크 구간에 손절 틱 누락 위험이 6시간 20분 지속. **MAIN 은 보유 포지션 손절이 실제로 일어나는 핵심 시간대**라 이쪽이 손익 충격이 더 크다.

두 시나리오 모두 "마지막으로 받은 동시호가 코드가 그날 마지막 push 라서 고착"될 때 발생한다.

### 결정적 발견 — KIS 정본은 "전환 종료 코드 push"를 보장하지 않는다

**KIS 공식 스펙(MCP `market_status_total` + 로컬 `docs/kis/domestic-stock-realtime.md`)은 다음을 *전혀 문서화하지 않는다*:**

1. **MKOP_CLS_CODE 전체 코드표** — KIS 공식 어디에도 110/112/121/129 의 값-의미 매핑표가 없다. 코드베이스 `session.py:224-227` 의 코드표("110 장전 동시호가 / 112 장개시 / 121 장후 동시호가 / 129 장마감 / 130-139 / 140-149 / 150-159")는 **코드베이스 자체 주석이지 KIS 정본이 아니다.** (사이클 162 docstring 의 "KIS MCP `market_status_total` 검증"은 *컬럼 레이아웃*만 검증된 것이고 *코드 값 의미*는 미검증.)

2. **push 트리거 의미론** — H0UNMKO0 가 (a) 장 상태 *전환 시점마다* 이벤트로 push 하는지, (b) 주기적 push 인지, (c) 동시호가 *종료* 시 별도 종료 코드를 push 하는지 **KIS 공식이 명시하지 않는다.**

### 트레이더/엔지니어 종합 판단 (a vs b)

실시간 장운영정보는 통상 **이벤트 드리븐**(장 상태 전환 시 push)이다. 따라서 *정상 작동 시*에는 110(08:30)→112(09:00)→...→121(15:20)→129(15:30) 순으로 전환 코드가 들어오고, 112/129 가 들어오는 순간 `on_h0nxmko0` 의 무조건 재대입(`self._last_nxt_mkop_code = mkop_cls_code`, L233)이 고착 코드를 **자동으로 덮어쓴다.** 즉 **정상 환경에선 결함이 발현 안 한다.**

결함은 **"전환 종료 코드가 들어오는 그 순간을 시스템이 놓치는" 좁은 창**에서만 터진다. 그리고 본 코드베이스는 그 창을 놓칠 구조적 취약점이 셋이나 있다:

- **취약점 ①** — `H0UNMKO0` 는 대표종목 005930 **단 1개**를 메인 WS 세션에 구독(`scheduler.py:560`), **실전 한정**(VTS 미지원). 단일 구독점이라 이 하나만 끊겨도 전체 장운영 신호가 끊긴다.
- **취약점 ②** — `websocket.py:486/548` 이 H0UNMKO0 를 **stale 검증/재구독 안전망에서 명시적으로 제외**한다(시세 TR 만 검증 대상). 즉 005930 H0UNMKO0 구독이 silent 하게 끊겨도 **재구독 복구 경로가 없다.** 09:00 의 112 push 가 이 끊김 창에 떨어지면 영구 미수신.
- **취약점 ③** — `_last_nxt_mkop_code` 는 init(`""`) → `on_h0nxmko0` 재대입 외에 **어떤 리셋/시간 게이트도 없다**(전수 grep 확정). 따라서 마지막 동시호가 코드가 그대로 박제된다.

**결론**: KIS push 신뢰는 *정상 시*엔 성립하나, 위 3 취약점이 결합하는 순간(특히 09:00·15:30 전환 코드를 단일 구독 끊김 창에서 놓칠 때) **전환 종료 코드 미수신 = 영구 고착**이 PLAUSIBLE 하게 발생한다. **시정 설계는 KIS push 신뢰에 의존해선 안 된다.**

## 의제 2 — 시정 방식 택1 권고: **방식 A (시간창 게이트), 단독 채택**

세 방식을 매매 안전성 관점에서 비교한다. 핵심 비대칭:

> **false-True(동시호가 아닌데 skip 유지 → 보유 손절/익일청산 틱 누락 = 손실 직결)가, false-False(진짜 동시호가에 불필요 재구독 → KIS LMS chain 위험)보다 훨씬 위험하다.** 보유 종목 stale 탐지 복원이 최우선이다.

### 방식 A — 시간창 게이트 (★ 권고)

코드 분기를 **그 코드의 유효 시간창**으로 감싼다. 고착 코드가 자기 시간창 밖이면 무시하고 시간 기반 폴백으로 떨어진다.

- **장점**:
  - **KIS push 신뢰 불요** — 취약점 ①②③ 무관하게 robust. 고착 코드는 시간창 밖에선 *구조적으로* 무시되므로 stuck-110(MAIN)·stuck-121(NXT-after) **양쪽 영구 차단**.
  - **사이클 162 의도 완전 보존** — 진짜 동시호가 창(08:30~09:00, 15:20~15:30)엔 시간 폴백 *그리고* 게이트된 코드 분기 양쪽이 True 유지.
  - **코드 분기의 잔존 가치 유지** — 게이트 마진(±5분)이 **임의연장(MRKT_TRTM_CLS_CODE)·VI 단일가 연장**으로 동시호가가 명목 시각을 살짝 넘기는 경우를 흡수(KIS 코드가 확인해주면 마진 구간에서 skip 연장). 이것이 코드 분기를 남겨두는 *유일한 정당 사유*.
- **단점**: 코드 실시간 우선 의미가 "명목창 ±마진"으로 한정됨 — 그러나 이게 정확히 **결함의 근원을 제거**하는 의도된 한정이다.

### 방식 B — 전환 코드 리셋

비-동시호가 코드(112/129 등) 수신 시 `_last_nxt_mkop_code` 갱신.

- **이미 구조적으로 구현돼 있음** — `on_h0nxmko0` L233 이 *무조건* 재대입하므로 112/129 가 들어오면 고착 코드가 자동으로 덮어써진다. **추가 코드 0.**
- **단독 채택 불가** — 의제 1 의 취약점 ①②③ 때문에 "112/129 가 reliably 들어온다"를 보장할 수 없다. push 가 끊긴 창에서 떨어지면 B 는 무력(고착 그대로). **B 의 실패 모드를 정확히 A 가 메운다.**

### 방식 C — TTL

코드 수신 시각 기록 → N분 경과 시 코드 무시 + 시간 폴백.

- **차선** — A 와 효과 유사하나 (a) 매직 타임아웃 N 도입 (b) 동시호가의 *실제 시간 경계*와 정렬되지 않음(예: 121 을 15:20 에 받고 TTL=30분이면 15:50 까지 skip → NXT-after 20분 누락). A 가 동시호가 창에 정확히 정렬되어 더 정밀하고 부수 위험이 적다.

### 최종 권고

> **방식 A 단독 채택. 방식 B 는 별도 구현 불필요(이미 무조건 재대입으로 내재)이며 A 가 그 실패 모드를 메운다. 변경 표면 최소(`is_call_auction_now` 함수 1개) + KIS push 신뢰 불요 + 사이클 162 의도 보존 + stuck-110/121 양쪽 영구 차단.**

## 정량 권고 — 시정 설계 (backend-dev 가 그대로 쓸 조건식)

### 시간창 값 근거

| 코드 | 명목 동시호가 창 | 게이트 유효창(권고) | 마진 사유 |
|------|----------------|--------------------|----------|
| "110" 장전 동시호가 | 08:30 ~ 09:00 | **08:25 ≤ t < 09:05** | 전(±5분): KIS 코드 조기 push 흡수 / 후(+5분): 개장 임의연장·VI 단일가 연장 흡수 |
| "121" 장후 동시호가 | 15:20 ~ 15:30 | **15:15 ≤ t < 15:35** | 후(+5분): 종가 단일가 **임의연장**(MRKT_TRTM, 통상 수십초~수분) 흡수. **15:40 NXT 애프터 개시 전에 종료** 보장 (보유 종목 stale 탐지 15:35 복원) |

마진 ±5분 근거: 한국 시장 임의연장은 분 단위(통상 ≤5분, 변동성 극단에서도 보통 수분 내)로 **유계**하다. +5분 마진이면 현실적 연장을 흡수하면서 stuck 영향을 **명목창+5분으로 봉쇄**한다. 특히 "121" 의 유효창 끝을 15:35 로 두는 것이 핵심 — 15:40 NXT 애프터(보유 종목 NXT 거래 시작) *전*에 stale 탐지를 반드시 복원시킨다.

### 권고 조건식 (`session.py::is_call_auction_now`)

```python
from datetime import datetime, time, timezone, timedelta

_KST = timezone(timedelta(hours=9))  # 모듈 상수 (stale-5 KST 강제, import 순환 회피 위해 로컬 정의)

def is_call_auction_now(self, now: datetime | None = None) -> bool:
    now = now or datetime.now(_KST)        # stale-5 시정: KST-aware (naive datetime.now() 금지)
    t = now.time()                          # tz-aware now 도 wall-clock KST time 반환 → 비교 안전

    code = self._last_nxt_mkop_code

    # 코드 기반 (시간창 게이트) — 고착 코드는 자기 유효 시간창 안에서만 신뢰.
    #   창 밖이면 무시 → 시간 폴백으로 강하 (stuck-110/121 영구 차단).
    #   마진 구간(명목창 ±5분)이 임의연장/VI 단일가 연장 흡수 = 코드 분기 잔존 가치.
    if code == "110" and time(8, 25) <= t < time(9, 5):
        return True
    if code == "121" and time(15, 15) <= t < time(15, 35):
        return True

    # 시간 기반 폴백 (코드 미수신 / 고착코드 시간창 밖 / VTS 모의) — 사이클 162 명목창 그대로 보존.
    if time(8, 30) <= t < time(9, 0):
        return True
    if time(15, 20) <= t < time(15, 30):
        return True
    return False
```

### 설계 포인트 (backend-dev 인계)

1. **코드 분기를 시간 폴백 *앞*에 두되 `and 시간창` 게이트 필수** — 게이트 없는 무조건 `return True`(현 L209)가 결함의 단일 근원.
2. **마진 구간이 코드 분기의 유일 가치** — 게이트 창이 명목창과 *정확히 같으면* 코드 분기는 시간 폴백과 완전 중복(무의미)이 된다. ±5분 마진이 있어야 "KIS 가 임의연장을 코드로 확인해줄 때만 명목창 너머로 skip 연장"이라는 정당한 의미가 산다.
3. **방식 B 별도 구현 0** — `on_h0nxmko0` L233 무조건 재대입 유지(변경 금지). 112/129 가 들어오면 자동 클리어, 안 들어와도 게이트가 봉쇄.

## stale-5 (LOW) — KST 강제

- **현 상태**: L213 `now = now or datetime.now()` = naive. 프로젝트 불변식 "모든 시각 데이터 KST 강제"(CLAUDE.md) 위반.
- **활성/잠재 판정**: **잠재(latent)**. 유일 production 호출자 `stale_watcher_core.py:196` 가 L130 `now = _dt_mod.now(_KST_TZ)` 로 **tz-aware KST 를 명시 전달**한다 → `now=None` 폴백은 production 에서 안 탐. 게다가 EC2 `TZ=Asia/Seoul` 라 naive `datetime.now()` 도 KST wall-clock 과 일치 → 현재 운영 영향 0. 다만 비-KST 환경(로컬 dev / TZ 미설정 컨테이너)에서 `now=None` 직접 호출 시 잘못된 창 판정 가능.
- **tz-aware 정합성 확인**: tz-aware `now.time()` 은 **wall-clock(타임존 제거) time** 을 반환하므로 `time(8,30) <= t < time(9,0)` naive 비교가 정확히 동작. tz-aware now 와 naive `time` 경계 비교는 **무해**(검증 완료).
- **권고**: `datetime.now(_KST)` 로 통일(위 조건식 반영). `_KST` 는 **모듈 로컬 정의** 권고 — `from src.engine.scanner import KST_TZ` 는 scanner↔session 순환 의존 위험, `src/db/_kst.py::KST` 도 가능하나 로컬 정의(scanner.py:32 / _kst.py:15 와 동일 패턴, 의존 0 추가)가 가장 안전. `timezone, timedelta` import 추가.
- **회귀 무영향**: 기존 cycle162 테스트는 모두 `now` 를 명시 naive 로 전달 → stale-5 폴백 미진입 → 영향 0.
- **번들 권고**: 같은 함수를 건드리므로 stale-1 과 **단일 사이클 동시 처리** 합리.

## 의제 4 — 사이클 162 정당 skip 보존 (충돌 검증)

## 반례 / 한계

1. **극단 임의연장(>5분)**: 시스템 장애·극단 변동성으로 동시호가가 명목창+5분을 넘겨 연장되면, 게이트가 연장 종료 *전*에 stale 탐지를 재활성 → 그 짧은 초과 구간에 불필요 재구독 몇 건(사이클 162 가 막던 바로 그것)이 발생할 수 있다. **그러나** (a) 한국 임의연장은 분 단위 유계라 5분 초과는 드물고 (b) 비용(재구독 몇 건)이 stuck 비용(보유 손절 탐지 수시간 OFF)보다 **압도적으로 작다**. 트레이드오프는 게이트 쪽이 명백히 우위. **운영 모니터링 권고**: `[stale_skip_call_auction]` 로그가 09:05·15:35 직후에도 반복 발화하면 실제 연장 신호 → 해당 코드 게이트 끝을 09:08/15:38(여전히 15:40 NXT-after 전)로 소폭 확대 검토.
2. **명목창 직전 조기 push**: KIS 가 "110" 을 08:23 에 push 하면(게이트 08:25 전) 그 2분은 코드 무시 → 시간 폴백도 False → stale 탐지 ON. 보유 종목 입장에선 08:23~08:25 에 진짜 끊김이면 잡아주는 게 오히려 안전하므로 **무해**(오히려 보수적으로 옳음).
3. **세 취약점 자체는 미해결**: 본 시정은 *고착의 영향*을 봉쇄할 뿐, H0UNMKO0 단일 구독 끊김(취약점 ①②)이나 코드표 정본 부재(의제 1)를 고치지 않는다. 게이트가 이들에 **무관하게 robust** 하므로 시급도는 낮으나, 별도 LOW 인계로 (a) H0UNMKO0 재구독 안전망 편입 또는 (b) 사이클 149 종목별 H0UNMKO0 monitor(`market_operation_monitor.py`)와의 신호 일원화 검토 가치 있음.
