## 0. 질문 요약

사용자(증권 도메인 전문가) 제안: "오늘 쓸 종목마스터는 거래소가 전일 22:00 배포 → 더 일찍 받아 funnel까지 미리 만들자."

메인 세션 실측으로 핵심 사실이 뒤집힘:

- **KIS `.mst` 실제 발행 시각 = 당일 아침 ~08:45 KST** (HTTP Last-Modified `2026-06-22 08:45:05`, KOSPI/KOSDAQ 동일).
- KRX→회원사 raw 피드는 전일 22:00이지만, **KIS가 가공해 다운로드용 `.mst`로 발행하는 건 당일 08:45 아침** (장 개장 09:00 직전).
- 즉 "전일 밤에 미리 받자"는 전제 자체가 성립 안 함 — 그 시점엔 *당일분이 아직 없음*.

따라서 6개 의제는 모두 "08:45 발행이라는 좁은 윈도우를 어떻게 다룰 것인가"로 귀결된다.

## 1. KIS `.mst` 발행 타이밍 일관성 (의제 1)

### KIS MCP 검증 결과 (인용)

- `mcp__kis-code-assistant__search_domestic_stock_api` 로 "마스터 파일 다운로드 발행 시각/갱신 주기"를 조회 → **`no_results`**. KIS 국내주식 API 카테고리(기본시세/순위분석/종목정보 26종 등)에 **`.mst` 발행 스케줄을 노출하는 정본 API/문서는 존재하지 않음**.
- 이유: `kospi_code.mst.zip` / `kosdaq_code.mst.zip` 은 **REST API가 아니라 정적 HTTPS 다운로드 파일** (`https://new.real.download.dws.co.kr/common/master/`). KIS OpenAPI 스펙 트리 밖이며, 발행 시각은 파일 서버의 HTTP 헤더(Last-Modified)로만 관측 가능.
- KIS 공식 샘플(`kis_kospi_code_mst.py`)도 발행 시각을 코드 코멘트로 명시하지 않음 (다운로드 → 파싱만 수행).

**결론: 발행 타이밍의 1차 정본 = 메인 세션의 HTTP Last-Modified 실측(08:45)이 맞다. KIS측 정본 문서로는 더 확인할 게 없다.** 단, 관측 1회분이므로 일관성은 *우리가 운영 모니터링으로 확보*해야 한다.

### 트레이더 시각 — 왜 08:45인가 (시장 가설)

이 시각은 우연이 아니다. 한국 거래소 일정과 정확히 맞물린다:

- **08:30 KRX 장전 동시호가 시작** — 이 시점에 당일 신규상장/거래정지/관리종목지정/지수정기변경 등 *당일 적용* 종목 상태가 거래소 시스템에 확정 반영된다.
- KIS는 이 확정분을 받아 가공 → **08:45경 `.mst` 재발행** → 09:00 개장 전에 회원사/API 사용자가 받을 수 있게 한다.
- 즉 08:45 발행은 "장전 동시호가 확정(08:30) + KIS 가공 지연(~15분)"의 자연스러운 결과. **08:30보다 더 이른 신뢰 적재는 거래소 구조상 불가능**하다. 그 전엔 당일 상태가 아직 거래소에 확정 안 됐기 때문.

### 위험 시나리오 (일관성이 깨지는 경우)

1. **반차일/특수 거래일** (수능일 10:00 개장, 연말 폐장일 등) — 개장 시각이 밀리면 `.mst` 발행도 밀릴 수 있음. 08:45 고정 가정 위험.
2. **거래소/KIS 시스템 지연** — 명절 연휴 직후 첫 영업일, 대량 신규상장일 등엔 가공 부하로 08:45을 넘길 수 있음 (08:50~09:00).
3. **주말/공휴일** — 휴장일엔 재발행 안 됨 (= 직전 영업일 파일 그대로). 우리 `run_daily()`가 휴장일 skip하므로 문제 안 되지만, 월요일 새벽 적재 시 "금요일 파일"을 받게 됨 — 이는 정상(월요일 장전 동시호가 전이므로).

### 정량 권고 (의제 1)

- **가장 이른 신뢰 적재 시각 = 08:46** (08:45 발행 + 1분 안전 마진). 그 이전 적재는 "전일자 마스터"를 받음.
- **일관성 검증을 운영 데이터로 확보** — 적재 task가 `.mst` 다운로드 시 HTTP `Last-Modified` 헤더를 파싱해 `[master_load] last_modified=... fetched_at=...` 1행 emit. 5영업일 누적하면 발행 시각 분포(요일별/특수일)가 잡힌다. **이건 후속 구현 권고이지 지금 코드 변경 아님.**
- 옵션 정렬:
  - **옵션 A (권고): 08:46 단일 적재 + Last-Modified 가드.** 다운로드한 파일의 Last-Modified가 *오늘 날짜*가 아니면 (= 아직 미발행) → 짧은 재시도(예: 5분 간격 × 3회, 09:00 직전까지) 후 graceful 포기(전일분 사용 + WARNING). 발행 지연일에도 안전.
  - 옵션 B: 08:46 고정 단일 적재 (Last-Modified 가드 없음) — 단순하나 발행 지연일에 전일분 silent 사용.
  - 옵션 C: 16:30 적재 유지(현행) — 17h lag 수용. 의제 2 결론에 따라 판정.

## 2. 마스터 신선도가 매매 정합에 미치는 영향 (의제 2) — **가장 중요한 판정**

이게 전체 재설계의 ROI를 결정한다. "17h lag가 실제로 매매를 그르치나?"

### 트레이더 시각 — D-1 마스터로 D 거래 시 무엇이 누락되나

마스터의 매매 활용 키는 두 부류다. lag 민감도가 완전히 다르다.

**부류 1 — 진입 차단 7~13건 (`_is_master_blocked_for_entry`)**: 거래정지/관리종목/공매도과열/이상급등/정리매매/시장경고/투자주의환기.

이건 **신선도가 매매 안전에 직결**된다. 구체 시나리오:

- **당일 신규 거래정지** — 어제 정상이던 종목이 오늘 아침 거래정지(불성실공시, 조회공시 답변 등). D-1 마스터엔 `trht_yn=N`으로 남아있음 → 우리 시스템이 후보로 올림 → 매수 주문 → **거래소가 거부**(주문 자체가 안 나감). 손실은 없지만 무의미한 주문 + 로그 오염.
- **당일 관리종목/투자경고 지정** — 장전 지정되면 증거금 100%, 신용 불가, 일부 시간대 단일가. D-1 마스터엔 정상으로 남음 → 후보 진입 → 진입했는데 변동성·단일가 슬리피지로 불리.
- **공매도과열/이상급등 (`ssts_hot_yn` / `stange_runup_yn`)** — 이건 *전일 장 마감 후 산출되어 당일 적용*되는 케이스가 많다. D-1 마스터(전일 08:45 발행분)엔 *전전일* 기준이 들어있을 수 있어 하루 밀림.

**부류 2 — 시총/지수편입/재무 (`prdy_avls_scal`, `kospi200_apnt_cls_code`, `roe` 등)**: lag에 거의 둔감.

- 시총은 하루 사이 후보 풀 경계(1,000억 컷 등)를 넘나드는 종목이 극소수. 하루 lag 무시 가능.
- 지수정기변경은 분기 1회(3·6·9·12월 동시만기 주간). 1년에 4일만 민감. 그 외엔 D-1로 충분.
- 재무는 분기 공시 — lag 무의미.

### 실전 통계/임팩트 추정

- 일평균 신규 거래정지/관리지정/경고지정은 한국 시장 전체에서 **하루 수 종목~십수 종목 수준** (장세에 따라). 이 중 우리 후보 풀(시총·거래대금 컷 통과 ~수십~수백 종목)에 걸리는 교집합은 **하루 0~2종목** 정도가 현실적.
- 임팩트는 대부분 "무의미한 주문 → 거래소 거부" (손실 0, 로그 오염)이고, 진짜 위험한 건 "관리종목/투자경고 종목을 모르고 진입 → 단일가/증거금 함정"인데 이건 **하루 0~1종목 빈도**.

### **핵심 반전 — 우리 시스템엔 17h lag를 메우는 이중 안전망이 이미 있다**

마스터 신선도 결함이 *치명적이지 않은* 이유는 코드에 이미 보강이 있기 때문이다:

1. **16:10 basics task (`_stock_master_basics_refresh_once`)** — 매일 16:10 KST에 KIS `inquire_stock_basics`(CTPF1002R + FHKST01010100) 매스 호출로 NXT거래가능/거래정지/관리종목/거래대금을 **장 마감 직후 갱신**. 이건 마스터(.mst)와 별개 경로로, **D-1 종가 기준이지만 16:10 = 당일 장 마감분**을 반영한다. 즉 "당일 장중에 거래정지된 종목"은 16:10 basics가 잡아낸다.
2. **`_is_master_blocked_for_entry`는 master_raw 우선 + raw 폴백 chain** (사이클 155/157) — master_raw(.mst)가 stale해도 raw(16:10 basics 갱신분)에 당일 상태가 있으면 차단된다.
3. **장중 H0UNMKO0 종목별 구독** (사이클 149) — VI/거래정지/종목상태를 실시간 수신. 보유·후보 종목이 장중 거래정지/VI 걸리면 즉시 인지.

즉 **마스터(.mst)의 17h lag는 "당일 아침 새로 지정된" 종목만 누락하고, 그것도 진입 차단 부류만 의미가 있는데, 그 부류조차 16:10 basics(전일 장 마감분) + 장중 H0UNMKO0가 상당 부분 메운다.** 순수하게 .mst만 잡고 다른 경로가 못 잡는 잔여 위험은 "오늘 08:30~08:45 사이 신규 지정 + 16:10 basics에도 없던 종목" = 하루 0~1종목 미만.

### 정량 권고 (의제 2)

**판정: 17h lag는 "무시 가능에 가깝다. 단, 0은 아니다."**

- 후보 풀 구성(부류 2, 시총/지수)엔 **사실상 영향 없음**.
- 진입 차단(부류 1)엔 **하루 0~1종목 잠재 임팩트**가 있고, 그마저 16:10 basics + H0UNMKO0가 대부분 메운다.
- **따라서 "08:45 아침 적재"의 매매 정합 ROI는 낮다.** 아침 적재를 새로 만드는 가치는 "당일 08:30~08:45 신규 지정 종목 차단"이라는 *얇은 잔여 위험* 하나뿐이고, 이건 거래소 주문 거부로도 사실상 방어된다.
- **반대로 비용은 명확하다** — 08:46~09:00의 14분 윈도우에 ~3,000종목 마스터 재적재 + (옵션에 따라) prepare 재실행을 욱여넣는 개장 전 시간 압박. 이건 새 silent 결함의 온상이다 (의제 3 참조).

### 현 코드와의 정합성

- **충돌 없음.** 현행 16:30 적재(17h lag 수용)는 사이클 129 domain-consult 의제 5 옵션 A의 명시적 결정이었고, 그 결정의 *근거(매매 정합 영향 미미)는 위 분석으로 재확인된다*. 단, 그 자문은 08:45 발행 사실을 몰랐을 뿐 — 결론은 동일하게 유효하다.

## 3. 최적 적재/prepare/funnel 윈도우 (의제 3) — 개장 전 시간 압박

08:46 발행 ~ 09:00 개장의 **14분 윈도우**에 (a) 마스터 재적재 (b) prepare (c) funnel을 다 끝낼 수 있나?

### 각 단계 소요 실측/추정

- **(a) 마스터 재적재** (`_stock_master_master_load_once`): `.mst` ZIP 다운로드(정적 HTTPS, 수 초) + cp949 파싱(메모리, 수 초) + `upsert_master_raw` 배치(~3,000행). 운영 실측 패턴상 **1~3분**. 14분 윈도우 내 OK.
- **(b) prepare** — **여기가 병목이자 함정.** 현재 5개 돌파/스윙 전략의 `prepare()`는 일봉을 **`fetch_daily_candles`(KIS REST)로 fetch**한다 (코드 확인: `volatility_breakout.py:122,186` / `donchian_swing.py:124,210`). 후보 수십~수백 종목 × KIS 호출 + Rate Limit semaphore 직렬화. 후보가 많으면 **수 분~10분+**. 14분 윈도우에 욱여넣으면 **09:00 개장까지 prepare 미완 → 시가 target 미계산 → VB/LTV 매수 신호 0건** (= 사이클 153/164에서 이미 겪은 그 사고 패턴).
  - **단, 탈출구가 있다**: 일봉은 16:00 일봉 task가 `stock_master_daily` DB에 이미 적재해 둠. prepare가 `fetch_daily_candles`(KIS) 대신 `get_recent_daily`/`get_donchian_high`(DB) 우선 사용하면 **KIS 호출 0 + 수 초 완료**. donchian은 이미 `get_donchian_high`(DB) 부분 사용(`donchian_swing.py:285`). **prepare를 DB 일봉 우선으로 전환하면 prepare가 14분은커녕 수십 초로 끝난다.** (이건 별도 사이클의 구현 과제 — 의제 4와 직결)
- **(c) funnel 생성** — prepare의 부산물(`_funnel_steps` 메모리 적재)이라 **추가 비용 0**. prepare가 끝나면 funnel 메모리는 이미 채워짐. DB persist(`_auto_capture_funnel_snapshots`)만 별도이고 이건 수 초.

### 개장 전 시간 압박 리스크 (트레이더 시각)

개장 전 14분에 무거운 작업을 몰면 안 되는 이유 — **이 시간대는 시스템에서 가장 예민한 구간**이다:

- 07:50 KIS WebSocket 강제 리셋(사이클 92) 직후 재연결/재구독이 진행 중.
- 08:30~09:00 장전 동시호가 — 호가만 쌓이고 체결 0. stale watcher가 이 시간대를 "체결 없음 = 비정상"으로 오인하지 않도록 사이클 162가 `is_call_auction_now()` skip을 넣어둔 *바로 그 예민한 구간*.
- 08:59:10 KRX 채널 사전구독 시작, 09:00:05 시가확정 — 이미 빡빡하게 task가 줄 서 있다.

여기에 "~3,000종목 마스터 재적재 + KIS 일봉 prepare 재실행"을 더하면 Supabase 동시 부하 + KIS Rate Limit 경합 + 메모리 race가 겹친다. **사이클 158(stock_master 0건 race) / 152·160(wait_until 폭주) / 164(시가 미확정)가 전부 이 개장 전 구간의 race였다.** 새 task를 이 구간에 넣는 건 그 사고 패턴을 다시 부르는 일.

### 정량 권고 (의제 3)

- **마스터 재적재(a)만이라면 14분 윈도우에 안전하게 넣을 수 있다** (1~3분, KIS REST 무관, Supabase upsert만).
- **prepare(b)를 14분에 넣는 건 위험하다 — 단, DB 일봉 우선으로 전환했을 때만 안전**해진다. KIS fetch 유지 상태로 아침 prepare 재실행은 **금지 권고** (개장 미완 사고 재발).
- funnel(c)은 prepare 부산물이라 독립 비용 없음.
- **결론: 아침 윈도우에 무거운 prepare를 새로 넣지 말고, 의제 4의 2단계(저녁 잠정 + 아침 델타) 구조로 풀어라.**

## 4. 저녁 사전 생성 가치 (의제 4) — **권고 핵심 설계**

제안: 16:00 일봉 직후 *잠정* prepare/funnel(전일 마스터 기준) 미리 생성 → 밤부터 확인 + 아침 08:50 마스터 델타 재적재 + 최종 funnel 재캡처 = 2단계.

### 트레이더 시각 — 가치 평가

이게 **올바른 방향**이다. 이유:

1. **funnel은 D-1 일봉 기반이라 장중 불변** (사용자가 이미 확인, 사이클 170 일관성 시정 완료). 즉 "오늘 어떤 종목이 어느 단계에서 걸러졌나"는 **전일 밤에 이미 결정 가능**하다. 굳이 아침에 만들 필요가 없다.
2. **운영자 가치** — 트레이더 입장에서 "내일 후보가 뭔지" 밤에 미리 보는 건 실전에서 매우 유용하다. 장전에 후보 종목 뉴스/차트를 미리 보고 마음의 준비를 한다. 현재는 09:30 funnel 캡처라 *개장 후에야* 후보를 확인 — 너무 늦다.
3. **시간 압박 해소** — 무거운 작업(일봉 기반 prepare)을 한가한 저녁(16:00 직후)에 끝내면 개장 전 14분이 자유로워진다.

### 2단계 설계 (권고)

**1단계 — 저녁 잠정 prepare/funnel (16:00 일봉 적재 직후, 예: 16:20)**

- 16:00 일봉 task가 `stock_master_daily` 적재 완료 → 그 DB 일봉으로 prepare 실행 → `_funnel_steps` 메모리 채움 → DB persist (`잠정` 플래그).
- 이때 마스터는 *전일 08:45 발행분*(아직 당일 08:45분 없음, 정상) + 16:10 basics 갱신분 사용. 후보 풀은 "내일 장이 열린다면 이 종목들"이라는 잠정 후보.
- 운영자가 밤새 확인 가능.

**2단계 — 아침 마스터 델타 + 최종 확정 (08:46~)**

- 08:46 마스터 재적재(당일 08:45 발행분) → master_raw 갱신.
- **델타만 반영**: 새로 진입 차단된 종목(거래정지/관리 신규 지정)을 후보 풀에서 제거. 이건 `_is_master_blocked_for_entry` 재평가만 하면 됨 — **무거운 일봉 fetch 불필요** (일봉은 어제 밤 이미 prepare 완료, 변동 없음).
- 최종 funnel 재캡처(델타 반영분).

### 가치 vs 복잡도

| 항목 | 평가 |
|------|------|
| 운영자 가치 | **높음** — 후보를 전일 밤 확인 (실전 트레이더 니즈 정확히 충족) |
| 시간 압박 해소 | **높음** — 무거운 prepare를 한가한 저녁으로 이동 |
| 매매 정합 개선 | **낮음** — 의제 2 결론대로 17h lag 임팩트 자체가 작음 |
| 구현 복잡도 | **중간~높음** — "잠정/확정" 2-state 도입 + prepare DB일봉 전환 + 델타 재평가 로직. 새 silent 결함 면적 존재 |

**판정: 가치는 분명하나(특히 운영자 가치), 복잡도가 만만치 않다. 단계적으로 가라.**

- **우선순위 1 (선행 필수): prepare를 DB 일봉 우선으로 전환** (의제 3 병목 해소). 이게 안 되면 저녁 잠정 prepare도 KIS fetch로 느리고, 아침 델타도 못 만든다. *이 전환 자체가 별도 사이클 (HIGH, 회귀 위험 — 매수 target 계산 경로 직접).*
- **우선순위 2: 저녁 잠정 prepare/funnel (16:20)** — DB일봉 전환 후. 운영자 가치 즉시 실현.
- **우선순위 3: 아침 08:46 델타 재적재 + 최종 funnel** — 잔여 위험(하루 0~1종목) 방어 + 후보 풀 확정.

### 옵션 정렬 (의제 4)

- **옵션 A (권고): 2단계 도입하되 우선순위 1→2→3 순차 사이클 분할.** 한 사이클에 다 넣지 말 것 (회귀 면적 과대).
- 옵션 B: 1단계(저녁 잠정)만 도입, 아침 델타는 보류. 운영자 가치는 얻고 복잡도 절반. **현실적 절충안.**
- 옵션 C: 현행 유지(16:30 적재 + 09:30 funnel). 매매 정합 영향 없으니 "안 해도 안전"은 맞음 — 단 운영자 가치를 포기.

## 5. 사용자 제안 3안 평가 (의제 5) — 08:45 실측 기준 판정

### (가) 07:00 조기 부팅

**판정: 무의미 + 구조적 차단. 기각.**

- 07:00은 08:45 발행 *전* — 당일 마스터가 아직 없다. 07:00 적재해봐야 전일분을 받음 → "더 일찍 받자"는 목적 자체가 불성립.
- 게다가 07:50 KIS WebSocket 강제 리셋(사이클 92)이 있어 scheduler에 "07:50 이전 시작이면 07:50까지 대기" 가드가 있다 (`scheduler.py:396`). 07:00 부팅은 구조적으로 07:50까지 잠자므로 의미 없음.
- 단, 사용자 지적대로 **마스터 다운로드는 정적 HTTPS라 07:50 리셋과 무관** — 즉 "07:00에 마스터만 받는" 건 기술적으론 가능하나, *받을 게 없으니*(전일분) 무가치.

### (나) 23:00 적재

**판정: "그날 08:45분과 동일". 기각.**

- 사용자 본인이 정확히 진단함. 전일 23:00 시점엔 다음날 마스터가 미발행 → 받는 건 *그날 아침 08:45 발행분*과 동일한 파일(당일 08:45분). 즉 23:00 적재 = 16:30 적재 = 익일 새벽 적재 모두 "당일 08:45 발행분"을 받는 것. 시각만 다르고 내용 동일.
- 16:30(현행)이 23:00보다 나은 점: 16:10 basics와 시간적으로 가까워 데이터 일관성 유지 + EC2 부하 분산.

### (다) 07:50+ presubscribe만 + prepare/마스터/funnel은 별도 시각

**판정: 타당. 의제 3·4 결론과 정합. 권고 방향.**

- 07:55 boot의 현재 "마스터 4 task 즉시 재적재 + prepare"를 분리하자는 게 핵심인데, 이건 의제 3(개장 전 시간 압박)·의제 4(저녁 사전 생성) 결론과 정확히 맞는다.
- 07:55 boot는 **포지션 복구 + 잔고 교차검증 + presubscribe(보유/익일청산 시세 구독)** 같은 *경량·필수*만 하고,
- 마스터 적재는 16:30(또는 08:46 델타), prepare/funnel은 저녁(16:20)으로 빼는 구조.
- **단 주의**: 07:55 boot에서 prepare를 완전히 빼면, EC2 재기동 시 메모리 휘발된 `_targets`/`_funnel_steps`를 채울 게 없어진다. **저녁 prepare 결과를 DB에 영속화하고 boot가 그걸 복구**하거나, boot에 "후보 비었으면 prepare 재실행" 안전망(이미 사이클 158 VB hook 존재)을 유지해야 한다. 안전망까지 빼면 안 됨.

## 6. funnel 캡처 cadence (의제 6)

funnel이 D-1 기반이라 장중 불변. 그렇다면 다회 캡처가 의미 있나?

### 트레이더 시각

- **장중 불변이므로 "값이 바뀌어서" 다회 캡처할 이유는 없다.** 09:30이든 12:30이든 15:00이든 같은 funnel.
- **단, 다회 캡처가 의미 있는 *유일한* 경우 = "캡처 시점에 메모리가 비어있다 정상화되는" race 회복**:
  - EC2 재기동이 09:00~09:30 사이에 발생 → 09:30 단일 캡처 시점에 prepare가 아직 미완(`_funnel_steps` 비어있음) → funnel DB에 빈/부분 snapshot 영속 → 운영자가 "후보 0"으로 오인. 사이클 158/164가 정확히 이 race.
  - 이 경우 12:30/15:00 추가 캡처가 있으면 prepare 회복 후 정상 funnel로 **덮어쓴다** (사이클 145 UPSERT + 사이클 170 in-place upsert로 같은 step_no 교체 가능 — 인프라 이미 있음).

### (a) 수동 trigger 단계별 캡처 수정 (현재 step_no=99만)

**권고: 가치 있음 (LOW).** 현재 수동 trigger는 최종 단계(step_no=99)만 캡처. 운영자가 "지금 각 단계 후보를 보고 싶다"는 니즈에 단계별 전체 캡처가 맞다. 자동 캡처(`_auto_capture_funnel_snapshots`)는 이미 단계별 전체를 INSERT하므로, 수동 trigger도 같은 헬퍼 호출로 통일하면 됨. 저비용.

### (b) 09:30/12:30/15:00 다회 자동 캡처

**권고: 조건부 가치 (LOW~MEDIUM).** "값이 바뀌어서"가 아니라 "race 회복용 재캡처"로서만 의미. 정량 정렬:

- **옵션 A: 현행 유지 (09:30 1회)** + 사이클 158 prepare 자동 재시도 hook에 의존. 재시도가 funnel도 갱신하면 다회 캡처 불필요. **가장 단순.**
- **옵션 B (권고): 2회 캡처 (09:30 + 12:30).** 09:30 race로 빈 funnel이 영속돼도 12:30에 prepare 회복분으로 덮어씀. 1회 추가로 race 회복 대부분 커버. 15:00은 과함(이미 12:30에 회복됐을 것).
- 옵션 C: 3회(09:30/12:30/15:00) — 한계효용 낮음. 12:30이면 충분.

### 정량 권고 (의제 6)

- (a) 단계별 수동 캡처 수정 = **채택 권고 (LOW)**. `_auto_capture_funnel_snapshots` 헬퍼 재사용.
- (b) 다회 자동 캡처 = **옵션 B(09:30+12:30) 또는 옵션 A(현행+재시도hook 신뢰)**. team-leader가 "race 회복을 캡처로 풀까(B) 재시도hook로 풀까(A)" 선택. 트레이더 관점에선 **A(재시도hook 강화)가 더 깔끔** — funnel은 관찰성일 뿐이고, 근본은 prepare 회복이지 캡처 빈도가 아니므로.

## 9. 반례 / 한계

1. **08:45 발행은 관측 1회분.** 반차일/시스템 지연일에 08:50~09:00로 밀릴 수 있음 → 08:46 고정 적재는 발행 지연일에 전일분 silent 사용. **Last-Modified 가드 필수** (오늘자 확인 후 재시도). 이 가드 없으면 의제 1 옵션 A가 옵션 B로 전락.
2. **"17h lag 무시 가능"은 우리 이중 안전망(16:10 basics + H0UNMKO0) 전제.** 만약 16:10 basics가 어떤 사이클에서 폐기되면 lag 임팩트가 커진다 — basics task는 lag 방어의 핵심이므로 *함께 보존* 의무.
3. **저녁 잠정 prepare의 "잠정"이 운영자에게 오해를 줄 수 있다** — "밤에 본 후보"와 "아침 확정 후보"가 다를 수 있음(델타로 빠진 종목). UI에 "잠정/확정" 명시 필요. 안 그러면 "밤에 있던 종목이 왜 없어졌냐" 혼란.
4. **다회 funnel 캡처의 한계** — race 회복용일 뿐, 근본 해결은 prepare 회복. 캡처를 늘려도 prepare가 영영 미완이면 빈 funnel만 여러 번 찍힌다. 근본은 재시도 hook.
5. **prepare DB일봉 전환의 동등성 위험** — `fetch_daily_candles`(KIS)와 `get_recent_daily`(DB)의 일봉 데이터가 미묘히 다를 수 있음(수정주가 반영 시점, 당일봉 포함 여부 등). 전환 시 *동일 종목 동일 날짜 일봉 일치* 회귀 가드 필수. 불일치 시 매수 target이 달라져 매매 행위가 바뀐다.

## 10. 후속 검증 권고 (tdd-engineer / tester)

### tdd-engineer (Red 테스트 설계 시 결정적 입력)

1. **Last-Modified 가드** — `.mst` 응답 헤더 mock: (a) 오늘자 Last-Modified → 즉시 적재 (b) 어제자 → 재시도 후 graceful (c) 헤더 부재 → graceful 적재(보수적). freezegun으로 08:46 / 08:50 / 09:00 경계.
2. **prepare DB일봉 동등성** — 동일 종목 동일 날짜에 대해 `fetch_daily_candles`(KIS mock)와 `get_recent_daily`(DB mock)가 *동일 OHLCV* 반환 시 target_price 일치 회귀. 불일치 시 FAIL.
3. **아침 델타 재평가** — 저녁 prepare 후보 풀에서 08:46 마스터에 신규 `trht_yn=Y` 종목이 *제거*되는지 + 일봉 fetch 0건(델타만)인지 검증.
4. **저녁 prepare 순서 의존성** — 16:00 일봉 미완 시 16:20 prepare가 `count_active` polling으로 대기(사이클 163 패턴)하는지.
5. **funnel race 회복** — 09:30 빈 funnel 영속 후 12:30(또는 재시도hook) 캡처가 정상 funnel로 *덮어쓰는지*(in-place upsert, 사이클 170 인프라).

### tester (통합/안전성)

1. **매매 hot path diff 0 검증** — risk.on_tick / order_engine / realtime / auth 변경 0 (prepare DB일봉 전환 제외 — 이건 별도 HIGH 검증).
2. **개장 전 윈도우 부하** — 08:46 델타 적재 + 동시호가 시간대 Supabase 동시 부하가 stale watcher / 시가확정과 경합하지 않는지 (사이클 152/158/164 패턴 재현 가드).
3. **D+1 운영 실측** — Last-Modified emit 5영업일 누적으로 발행 시각 분포 확보 (의제 1 일관성 검증). 반차일 포함 권고.
