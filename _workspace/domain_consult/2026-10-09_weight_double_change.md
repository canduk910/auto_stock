# 같은 날 비중을 두 번 바꾸면 전략 예산이 부푼다 (리팩토링 검토 카드 #7)

## 질문 요약
`PUT /api/strategies/weights`(`src/routes/strategies.py:349`)가 재배분 기준 총액을 `Σ registry.all() 의 total_investment` 로 잡는다. 비중 0 으로 꺼진 전략의 옛 예산이 그 합에 남으면, 다음 변경 때 예산이 부푼다는 진단. (1) 진단이 맞는가 (2) 올바른 기준 총액은 (3) 고칠 자리와 회귀 시나리오.

근거로 읽은 코드: `strategy_registry.py:36-58`(allocate_funds·update_weights) · `routes/strategies.py:289-396` · `boot_manager.py:221-224`(부팅 배분 = `net_asset × cash_usage_ratio`) · `scheduler.py:3551`(`_reset_daily_state` 가 전부 0) · `routes/recommendations.py:248-272`(apply 는 `config.weight` 만 바꾸고 재배분 안 함). 운영 DB·서버는 보지 않았다 — 아래 숫자는 전부 **합성**이다.

## 트레이더 시각

### 1. 진단 — 맞다. 다만 범위를 좁혀야 한다
- 새는 것 = **섀도가 아닌 전략을 장중에 비중 0 으로 끈 경우 하나**다. `update_weights` 가 `enabled=False` 로 바꾸고, `allocate_funds` 는 `enabled()` 만 다시 채우므로 그 전략의 `total_investment` 가 그대로 남는다.
- **섀도 전략은 새지 않는다** — 비중 0 이어도 켜진 채라 `allocate_funds` 가 비율 0 으로 **0 을 써 준다**. 카드의 「(또는 섀도 유지)」 는 빼야 한다.
- **부팅 때 꺼져 있던 전략도 새지 않는다** — 21:30 `_reset_daily_state` 또는 새 프로세스가 0 으로 시작한다.
- 부풂은 **선형 누적**이다. 꺼진 전략 몫 x 가 남아 있는 한, 그 뒤 PUT 한 번마다 기준 총액이 x 씩 더 커진다(PUT 뒤 Σall = 직전 기준 + x).

### 재현 (합성, 기준 A = 순자산 × 비율 = 5,000,000)
| 시점 | 비중 (kojiro·donchian·VB·BFB · etf 섀도 0 · LTV 꺼짐 0) | 기준 총액 | 켜진 전략 예산 합 | 꺼진 VB 잔존 |
|---|---|---|---|---|
| 07:45 부팅 | .40 · .25 · .20 · .15 | 5,000,000 | 5,000,000 (2.0M·1.25M·1.0M·0.75M · etf 0) | — |
| 10:30 PUT#1 | VB→0(보유 0, 섀도 아님) · .50 · .25 · 0 · .25 | 5,000,000 | 5,000,000 | **1,000,000** |
| 13:00 PUT#2 | .45 · .25 · 0 · .30 | **6,000,000** | 6,000,000 (+20%) | 1,000,000 |
| 14:00 PUT#3 | 아무 미세 조정 | **7,000,000** | 7,000,000 (+40%) | 1,000,000 |

- PUT#2 뒤 BFB 의도 예산 = 0.30 × 5.0M = 1,500,000, 실제 1,800,000. 터틀 유닛(`예산 × risk_pct ÷ ATR`)·비중 랏(`예산 × position_ratio`)이 **같은 배율로 커진다** → 거래당 리스크 +20%.
- **세 캡이 못 잡는다** — K축(`K × 예산 × risk_pct ÷ ATR`)·ρ축(`K_ρ × position_ratio × 예산`)·명목(`Σ매수 ≤ 예산`) 전부 예산에 비례하는 상대 캡이다. 남는 하드 스톱은 KIS 주문가능금액뿐 → 늦게 온 신호가 「잔고 부족」 으로 거부되고, 어느 전략이 굶는지는 도착 순서가 정한다(성과 귀인 오염). `cash_usage_ratio < 1` 이면 남겨 둔 현금 완충을 먹는다.
- **하한선 검사도 같이 느슨해진다**(`:362`). donchian 보유 원금 1,000,000 일 때 참 하한 = 1.0/5.0 = 20%, PUT#3 시점 하한 = 1.0/7.0 ≈ 14.3% → 15% 가 통과한다. 그날은 7.0M × .15 = 1,050,000 이라 문제없어 보이지만, **다음 날 부팅 예산 = 5.0M × .15 = 750,000 < 보유 1,000,000** → 잔여 0 → 그 전략 매수가 보유가 빠질 때까지 막히고 「투자금 부족」 으로 오귀인된다.
- 부풂 자체는 21:30 리셋·재시작·다음 부팅에서 사라진다. 남는 것은 **그날 부푼 랏으로 산 보유**와 위 다음 날 잔여 0 이다.

### 실제 운영에서 언제 밟히나
- 조건 = **부팅(07:45)~21:30 사이에** ① 섀도 아닌 전략을 비중 0 으로 끄고 ② 같은 날, 재시작 전에 비중 PUT 을 한 번 더 한다.
- **10-06 VB 섀도 전환은 밟지 않았다** — 22:11 이후라 `_reset_daily_state` 뒤 Σ=0 → 재배분 자체를 건너뛰었고, `shadow_mode true` 를 먼저 켜서 VB 는 켜진 채 0 이었다. 「장외 21:35 이후 변경」 습관이면 지금도 안전하다.
- 밟는 길 = 「폐기 판정 전략(BFB·VB 등)을 장중에 섀도 없이 0 으로 내림 → 오후에 다른 비중 손질」. 섀도 순서를 어기고 비중 0 부터 내린 날도 같다.

## 정량 권고 — 기준 총액 3안
| 안 | 내용 | 위험 |
|---|---|---|
| (가) 부팅 기준액 저장 | 부팅의 `net_asset × ratio` 를 보관해 재사용 | 정확히 「하루 예산 고정」 계약 그대로. 단 보관 자리가 필요 — `allocate_funds` 안(8영역) 또는 `boot_manager` 가 scheduler 객체에 속성을 붙이는 꼴(`scheduler.py` 밖에서 새 속성 = 냄새). 21:30 리셋 뒤 무효화도 별도로 챙겨야 한다 |
| (나) 켜진 전략만 합산 | `Σ s.state.total_investment for s in registry.enabled()` (update **전**에 계산) | 라우트 한 줄. 직전 배분이 켜진 집합 위에서 했으므로 Σenabled = 기준액이 유지된다(섀도 0·apply 로 비중만 바뀐 켜진 전략도 그대로 합에 남아 맞다). 깨지는 곳 하나 = **섀도 아닌 켜진 전략의 비중 합이 0 이 되는 PUT**(전부 0/섀도) → 기준이 0 이 되어 그날 다시 켠 전략이 예산 0 → 「투자금 부족」 900초 오귀인. 정수 절사로 PUT 마다 몇 원 줄어드는 것은 무시 가능 |
| (다) 매번 잔고 조회 | PUT 때 KIS 잔고 + 현재 `cash_usage_ratio` 로 새로 계산 | **권하지 않는다.** 장중 순자산엔 평가손익이 섞여 비중 한 칸 손질이 전 전략 예산을 재기준한다 → 하락일엔 보유 많은 전략이 잔여 0(매수 막힘·오귀인), 상승일엔 확대. Settings 슬라이더의 「다음 영업일부터 반영」 계약도 깨진다. 라우트 안 KIS 호출·실패 처리 부담 |

**권고 = (나) + 꺼진 전략 예산 0 쓰기 + 건너뜀 경고**, 전부 라우트 안:
1. `total_asset = Σ enabled()` — `update_weights` 호출 **전**(지금 349행 자리). 하한 검사도 이 값.
2. `allocate_funds` 뒤, 이번 PUT 으로 꺼진 전략(`enabled=False`)의 `state.total_investment = 0`. 근거 = 비중 0 가드가 보유 있는 전략은 이미 막으므로 꺼지는 전략은 보유 0 → 예산 0 이 매수·청산에 주는 영향 0. 이것으로 `Σall`(화면 `invested_ratio`·`get_status` 투자금 합)도 정직해진다. 정산 `daily_performance` 의 그 전략 행은 0 이면 직전 영업일 값 폴백(`scheduler.py:3503`) — 부팅 때 꺼진 전략과 같은 길이다.
3. 기준이 0 인 **원인이 「직전 PUT 이 켜진 비중을 전부 0 으로 만든 것」** 일 때만 `[weight_realloc_skipped]` WARNING 1줄 — 판정 = update **전** 켜진 전략의 비중 합이 0 이고, update **후** 켜진 전략 중 비중 > 0 이 있다. 21:30 리셋 뒤·부팅 전은 update 전 켜진 비중 합 > 0 인데 예산이 0 인 정상 건너뜀이라 울리지 않는다.
- (가) 를 택할 이유 = 위 사각까지 막고 싶을 때. 그때는 `allocate_funds` 가 기준액을 기억하게 하는 게 가장 깨끗하고 8영역 승인이 붙는다.

## 현 코드와의 정합성
- **충돌 없음** — 안전 규칙(비중 0 = 끄기·보유 시 거부, 섀도 비중 0 + 켜짐, 비중 단위 계약, Σ 정규화)은 손대지 않는다. 바뀌는 것은 「장중 재배분의 기준액」 하나.
- **매매 행위 변경이다** — 결함이 발화하던 날의 예산·랏·하한 판정이 줄어든다(평소 날은 비트 동일). 사용자 승인 대상.
- 고칠 자리 = **`src/routes/strategies.py` 만**(8영역·`scheduler.py` 무접촉). 2번의 0 쓰기를 `allocate_funds` 안(「꺼진 전략은 0」)으로 넣으면 더 단단하지만 8영역이 된다 — 라우트만으로 충분하다.
- 문서 = `src/routes/CLAUDE.md:193` 「즉시 `allocate_funds`(Σ`total_investment` > 0 일 때)」 문장을 새 기준으로 고친다.

## 반례 / 한계
- (나) 는 「직전 배분이 켜진 집합 위에서 일어났다」 를 전제한다. 앞으로 `enabled` 를 배분 없이 바꾸는 새 경로가 생기면(예: 켜기·끄기 토글 API) 다시 어긋난다 — 그 경로가 같은 2번 규칙(끄면 0)을 따라야 한다.
- 이미 부푼 날의 보유는 이 수정으로 줄어들지 않는다. 다음 날 잔여 0 은 보유가 빠지면 풀린다.
- 기준액이 아침 순자산 고정이라 장중 큰 손익을 반영하지 않는다 — 결함이 아니라 「하루 예산 고정」 계약 그대로다.
- 운영에서 실제로 밟힌 날이 있었는지는 확인하지 않았다(DB 접속 금지). 확인법 = 같은 날 `system_logs` 의 `[cash_usage_ratio] available=` 값과, 그 뒤 `자금 분배:` 로그 금액 합이 어긋나는 날을 찾는다(tester).
