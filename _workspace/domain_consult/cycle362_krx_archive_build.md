## 검증 — KIS 수정주가 대조

**직접 겹치는 날짜가 없다** — 이 보관소는 2025-10-02 까지, 운영 `stock_master_daily`(KIS 수정주가)
는 2025-10-10 부터다. 방법론만 교차 확인하기 위해 KRX 를 검증 전용으로 **2025-10-10~2026-09-24**
추가 수집(500콜, 이 archive 산출물에는 포함하지 않음)해 같은 조정 방식을 적용한 뒤 대조했다.

**불일치 원인** — 상위 사례(예: 002780)를 확인한 결과, 불일치는 우리 조정 계산의 오류가 아니라
**`stock_master_daily` 자체의 알려진 한계**로 보인다. 그 테이블은 매일 증분 upsert 라 과거 봉이
"조회 시점의 값"으로 박제되고, 나중에 액면분할·병합이 나도 과거 행을 소급 재조정하지 않는다
(`src/db/CLAUDE.md` "락 게이트" 절이 이미 문서화한 결함 — "수정주가는 조회 시점에 달린 값이라
DB 에 박제된 과거봉과 KIS 재조정봉이 어긋난다"). 실제로 002780 은 사건(액면병합 추정, 2026-09-07
경계) 이후 날짜(2026-09-11 close=7200)는 KIS 와 원 단위까지 정확히 일치했고, 사건 이전 날짜만
10배 차이가 났다 — 즉 우리 보관소가 KIS 라이브 수정주가에 더 가깝고 DB 캐시 쪽이 stale 한
경우로 보인다. 전 종목을 사건 단위로 확인하지는 않았다(추정).

## 실행 중 발생한 일 — 컨테이너 재생성

수집 도중(elapsed ~390초 지점) 이 작업과 무관한 다른 커밋의 GitHub Actions 자동배포
(`Deploy — EC2 Direct Build`, 2026-09-25T01:21:56Z)가 backend 컨테이너를 재생성했다. 첫 방식은
컨테이너 로컬 `/tmp` 에 날짜별 파일을 썼는데, 컨테이너가 재생성되면서 `/tmp` 전체가 지워져
그때까지의 진행분(약 140일치, 280콜)을 잃었다(exit code 137). **매매·배포·운영 DB 에는 영향
없음**(우리 스크립트는 읽기 전용, 이번 재생성 자체가 우리와 무관한 정상 자동배포였다). 이후
컨테이너 로컬 디스크 대신 **stdout 스트리밍 + 로컬(맥) 리다이렉트**(`ssh ... stream ... >
로컬파일`)로 방식을 바꿔, 컨테이너가 다시 재생성되더라도 이미 흘러나온 데이터는 로컬 디스크에
안전하게 남도록 했다. 재시도는 전량을 처음부터 다시 돌려 60.8분 만에 오류 없이 완주했다(그
사이 추가 배포는 없었다).
