## ① 사용자 제안에 대한 직답

### **권고하지 않는다. 지금 `TIME_AUTO_START` 를 05:00 으로 옮기지 마라.**

애매하게 쓰지 않겠다 — **반대다.** 다만 반대의 이유는 앞선 자문들이 든 이유("07:50 KIS 강제 중단")와
**다르다.** 그 근거는 이번 조사에서 무너졌다(§②). 내가 반대하는 이유는 둘이다:

1. **제안이 목표를 달성하지 못한다.** "하루 한 번"은 기상 시각이 만드는 것이 아니다. immediate 발화가
   `기동 시각 + 240초`(부팅 상대 오프셋)이고 멱등 판정이 `today_kst()` **절대 비교**라, 시각을 옮기면
   헛일이 3시간 일찍 그대로 돈다. 의뢰서의 잠정 분석은 **맞다**(§①-B).
2. **알려진 안전 구간을 미관측 구간과 맞바꾼다.** 05:00~07:45 는 이 시스템이 KIS 로 REST 시세도
   WebSocket 도 **단 한 번도 보낸 적이 없는** 구간이고(전 테이블 07:45 이전 기록 0행), 그 구간에서
   실패하면 **무음**이며(§③), 그 무음의 대가는 **그날 하루치 손절 커버리지 전부**다.

### 사용자 직관에서 **맞은 부분** (셋 다 실질적이다)

| 사용자가 옳게 본 것 | 확인 |
|---|---|
| **"아침에 도는 그 실행은 헛일이다"** | 헛일 정도가 아니라 **유해**하다. 07:56 immediate 가 그날 껍데기 봉을 먼저 써서 그날 16:00 을 전 종목 skip 시킨다(09-03 `fetched=982 → 16:00 skipped_fresh=982`, 09-04 `1015 → 1015`). 사용자가 결함의 급소를 정확히 짚었다 |
| **"하루 한 번이면 깨끗하다"** | 목표로서 정확하다. 그리고 그 목표는 **달성 가능**하다 — (가) 신선도 게이트 인자 하나로 화~금 1회가 된다(월요일·사고 다음날만 2회). 이건 이미 basics·master·financial 세 task 가 매일 아침 프로덕션에서 하고 있는 일이다 |
| **"이르게 기동해 두면 여유가 생긴다"** | 사실이다. 지금 `_boot` 예산은 07:45 시작 → 07:59 사전구독 = **14분**인데, 그중 **6분 07초**를 보조 토큰 7개 직렬 발급이 먹는다(KIS 분당 1개 한도). 이건 우리 로직이 아니라 KIS 한도가 만든 절벽이고, **보조 계좌를 늘리는 만큼 직선으로 좁아진다**(계좌 12개면 07:59 사전구독을 놓친다 — 역할 A §4.3). 05:00 은 이 절벽을 없앤다 |

### **성립하지 않는 부분** (하나, 그러나 제안의 핵심)

> **"기동 시각을 옮기면 하루 한 번이 된다"** — 성립하지 않는다.

- immediate 실행 시각 = `기동 시각 + initial_delay_secs(240)`. 16:00 은 그 아래 `while` 루프 전용이다
  (`task_loop_helper.py:103-109` vs `:154-156`).
- 멱등 게이트는 `if not force and latest is not None and latest >= today: skip` — `today` 는
  `today_kst()` 1회 계산(`scanner.py:2178-2185`). 05:0x 이든 07:5x 이든 `latest = D-1 < D = today` 라
  **어느 쪽이든 fetch 로 진입**한다.
- 따라서 05:04 immediate → D 스텁 기록 → 그날 16:00 전 종목 skip. **결함 100% 재현.**
- 단 하나의 유보: 05:00 시점 KIS 가 아직 D 행을 만들지 않았다면(갈래 ②) 시각 이동만으로 주 경로가
  닫힌다. **이 갈래의 확률은 아무도 모른다**(0~6시 기록 0행). 그리고 갈래 ②여도 하루 2회 실행은
  그대로고 낮 재배포 구멍(07-13 실증 17행)은 남는다. **시정의 성패를 미검증 외부 동작에 거는 셈**이다.

> 한 줄 요약: **사용자는 병(病)을 정확히 짚었고 약(藥)을 하나 잘못 골랐다.** 병 = 아침 헛실행,
> 약 = 신선도 게이트((가)), 사용자가 고른 약 = 기상 시각. 시각은 병에 듣지 않는다.

## ② KIS 07:50 강제 중단과의 충돌 — **실재하지 않는다 (전제가 무너졌다)**

두 입력이 여기서 정면 충돌한다. 역할 B 는 이것을 **유일한 차단 사유**로 들었고, 역할 A 는 **반증**했다.
**역할 A 가 이긴다.** 근거의 등급이 다르다.

### 2.1 전제의 등급 — 처음부터 추정이었다

사이클 92 정본(커밋 `9e556ee`, 2026-06-10)에 **사용자 결정이 그대로 남아 있다**:

> **`Q31=C` KIS 공식 명문 생략 (사용자 보고 자체가 정본)**

즉 "KIS 가 07:50 에 API 를 재기동하며 모든 접속을 강제 중단한다"는 명제는 **KIS 문서 확인을 명시적으로

`docs/kis/` 25파일 전수 + KIS MCP 조회 결과 **07:50 관련 서술 0건**이었다.

### 2.2 실측 반증 — 우리는 이미 07:50 을 여섯 번 살아서 통과했다

`system_logs` 는 WARNING+ 를 30일 보존하고, WS 중단은 반드시 WARNING/ERROR 로 찍힌다
(`연결 닫힘` / `Heartbeat 타임아웃` / `WebSocket 끊김 n/5` / `최대 재연결 횟수 초과`).

- **07:50 대(帶) 중단 로그: 30일 0건.**
- WS 연결이 **07:48~07:49** 였던 거래일 6일(08-06/07/10/11/13/14) 전부 → **07:45~08:56 구간 중단 로그 0줄.**
- 같은 날들에 **08:57~08:58 `WebSocket 연결 닫힘` 은 정상적으로 찍혀 있다** → 그 시각까지
  `_receive_loop` 가 살아 있었다는 뜻 = "무증상 사망" 가능성까지 배제된다.
- **실재하는 KIS 일일 강제 종료는 08:57~08:58**(거래일 19/19, close code **1000** = KIS 측 정상 종료)이고,
  지금 시스템은 **매일 그것을 무해하게 통과**하고 있다(`_reconnect_count` 리셋 → 백오프 0초 즉시 재연결).
  05:00 기동이 **새로 떠안는 종료 이벤트가 아니다.**

### 2.3 사이클 92 의 자동 재기동이 이미 흡수하는가 — **아니다. 그건 흡수 장치가 아니라 킬 스위치다**

이 부분은 역할 B 가 옳고, 내가 코드로 재확인했다. 통설("60s cooldown + 시간당 3회 cap 이 있으니
세 번은 버틴다")은 **틀렸다.**

```python
# websocket.py:244-249
if self._reconnect_count > MAX_RECONNECT:            # 6회째
    logger.error("최대 재연결 횟수 초과, 종료")
    await self._trigger_auto_restart()               # ← 반환값 무시
    break                                            # ← 무조건 종료
```

빠른 실패(TCP 거부·타임아웃) 모드의 실제 타임라인:

| t | 사건 |
|---|---|
| 0s | 1차 실패 → 백오프 1+2+4+8+16 = **31초** 누적 |
| ~31s | 6회째 → `_trigger_auto_restart()` **1차 발화**(`_auto_restart_last_at = 31`) → `stop()` → `start()` → 새 task(카운터 0) → 구 task `break` |
| ~62s | 새 task 도 31초 소진 → `_trigger_auto_restart()` **2차** → cooldown 검사 `62-31 = 31s < 60s` → **`False` 반환** → 호출부는 반환값과 무관하게 **`break`** → **그 세션 그날 영구 사망** |

- **"시간당 3회 cap" 은 이 모드에서 도달조차 못 한다.** 실질 한계는 cooldown 60초이고, cap 과 cooldown 은
  둘 다 `False` 를 반환하는데 호출부가 그걸 **종료 신호로 쓴다.** 즉 설계 의도는 스로틀인데 **작동은
  킬 스위치**다. cap 3회에 도달하려면 실패가 60초 넘게 벌어져야 하고(= 중간에 한 번 붙었다 다시 끊기는
  경우), 그 경우 3회를 쓴 뒤에도 결과는 같은 `break` 다.
- **카운터는 세션 인스턴스별**(`self._auto_restart_last_at` / `self._auto_restart_history`)이다.
  공유 예산이 아니므로 **KIS 측 광역 장애면 메인 1 + 보조 7 이 각자 62초를 쓰고 동시에 죽는다.**
- **부활 경로 0.** `subscribe()` 는 `if self._ws:` 에서 막혀 SEND 자체를 안 하고,
  silent-inactive 강제 재연결은 `ws_obj is None` 이면 skip 하며, scheduler 는 `_ws_task` 의 done 여부를
  **어디서도 보지 않는다**(참조는 생성 1곳 + `finally` cancel 뿐 — grep 전수 확인).
  `quote_session_health` 는 죽은 세션을 **더 비활성화**할 뿐 되살리지 않는다.
  → **다음 날 `_boot()` 또는 컨테이너 재시작까지 tick blind.**
- **30일 로그에 `[ws_auto_restart*]` 0건** = 이 회복 코드는 배포 후 운영에서 **한 번도 발화한 적이 없다.**

### 2.4 07:50~08:00 이 왜 하루 중 가장 민감한 창인가 — 구체적으로

이 창에서 세션이 죽으면 다음이 **전부 무음으로** 사라진다(`_send_subscribe` 는 `_ws` 가 없으면 말없이 return):

| 시각 | 잃는 것 | 결과 |
|---|---|---|
| 07:59 | 사전구독(돌파 후보 + 보유 포지션 HIGH) | NXT 프리 08:00 시가를 **못 본다** |
| 08:00 | LTV `tradable_boards=("pre_nxt",…)` 프리장 매매 개시 | 시세 0 상태로 개장 — 진입도 청산도 평가 불가 |
| 상시 | `H0STCNI0` 체결통보 | **포지션 등록 불가 → 손절 불가**(CLAUDE.md "체결통보 구독 제거 금지" 가 지키려던 바로 그것) |
| 09:00~15:30 | 전 종목 tick | 손절·트레일링·익일청산 평가 정지 |

그리고 **그 시각의 4중 안전망은 구조적으로 전부 무력**이다 — 구독 종목이 0건이라
`_detect_silent_inactive_sessions`(전제 `subscribed>=5`)도, K stale watcher 도, `_resubscribe_stale_priority`
도 **순회 대상이 없다.** 사이클 92 커밋이 기록한 그 상태 그대로다.

### 2.5 그래서 ②의 결론

- **07:50 강제 중단은 05:00 이동을 막는 사유가 아니다** — 최근 30일 기준 존재하지 않는다.
- **그러나 그것이 노출시킨 재연결 규약의 결함은 실재하고, 05:00 이동은 그 결함의 노출 시간을
  8분에서 2시간 59분으로 늘린다.** 위험은 "07:50 이라는 시각"이 아니라 **"미관측 구간 × 무음 사망 코드"**
  의 곱이다.
- 한계(정직하게): 30일 로그는 **2026-06-10 당시를 덮지 못한다.** 그때 실재했다가 KIS 가 바꿨을 가능성은
  반증도 입증도 안 된다. 그리고 06-10 사고의 **진짜 원인은 여전히 미해결**이다 — 07:50 이 아니었다면
  무엇이었는지 모른다는 뜻이고, 그 미지가 05:00 구간에 다시 나타나지 않는다는 보장도 없다. (추측)

### 3.2 위험한 것 — 손절 커버리지, 단 하나의 축

**손절은 전적으로 WebSocket tick 에 실린다.** 그리고 폴백은 사실상 없다:

- `_swing_rest_poll_loop` 는 **donchian_swing 전용 · 09:05~15:20 · 60s** 다(내가 직접 확인,
  `scheduler.py:2825-2865`). 나머지 6 전략의 손절·트레일링·익일청산은 **tick 이 유일한 입력**이다.
- 체결통보(`H0STCNI0`)가 없으면 그날 체결이 **포지션으로 등록조차 안 된다** → 손절 대상에서 누락.

따라서 **"WS 세션이 조용히 죽은 하루" = 6 전략 손절 0 + 신규 체결 미등록**이다. 이건 우리가 종목당
0.42~2.09% 로 깎아 온 리스크 캡(cycle242/245/254)이 **전제부터 무효가 되는** 사건이다. 캡은
"청산이 작동한다"를 가정하고 계산된 값이다.

그 위에 05:00 이동이 얹는 세 가지 증분:

   성공했고, KIS 는 야간 해외주식 서비스를 운영한다. 그럼에도 **실패 시 손실이 "그날 손절 전부"** 라
   기대값이 아니라 최악값으로 판단했다.
2. **갈래 ②(05:00 에 오늘 행 없음)이면 내 §① 결론의 절반이 뒤집힌다.** 그 경우 (B) 단독이 주 경로를
   닫고, 게다가 **아침 재fetch 가 D-1 최종본(시간외 단일가 포함)을 덮는 자기 치유**까지 유지된다 —
   이건 (라)가 명시적으로 포기하는 것이다. 다만 그래도 하루 2회 실행은 그대로고 낮 재배포 구멍
   (07-13 실증 17행 — 거래량>0 비평탄 **진짜 장중 부분봉**이 확정봉 자리에 박혔다)은 남는다.
3. **"07:50 없음" 은 30일 창의 진술이다.** 2026-06-10 은 로그 보존 밖이고, 06-10 사고의 진짜 원인은
   **여전히 미해결**이다. 원인 미상의 사고가 한 번 있었던 시간대를, 원인을 모른 채 더 오래 점유하는
   선택이라는 점은 남는다.
4. **이 판정은 "보조 계좌 7개" 라는 현재 상태에 조건부다.** 계좌가 10개면 `_boot` 종료 ≈ 07:55,
   12개면 **07:59 사전구독을 놓친다**(토큰 61초 직렬화 × N). 그 시점엔 05:00(또는 06:30)이 선택이
   아니라 필수가 되고, 내 권고는 뒤집힌다.
5. **(라)가 못 고치는 것이 남는다** — `stock_master_daily.get_atr()` 의 오늘봉 가드 부재로 인한
   **VCP ATR 평균 6.3% 과소**(최악 29.3%)는 (라)로도 05:00 으로도 줄지 않는다. (다)가 스텁 유입을
   막으므로 신규 오염은 멎지만, **이미 쌓인 과거 스텁**과 `get_atr` 자체의 가드 부재는 별건이다.
   VCP/BFB 터틀 sizing 을 켜기 전에 반드시 닫아야 한다(D-8).
6. **(라) 도입이 낮 재배포 구멍의 노출 면적을 넓힌다** — 지금은 아침 스텁이 대부분 종목의 `latest` 를
   이미 D 로 만들어 놔서 낮 재시작 immediate 가 거의 전부 skip 되는데, (가)로 아침 스텁이 사라지면
   그 구멍이 **전 종목으로 열린다.** 그래서 (가)와 (다)는 **반드시 함께** 가야 한다 — (라)의 정의가
   이미 그렇지만, 분할 배포 유혹을 명시적으로 금한다.
