# 역할 A — 05:00 기동과 KIS 측 제약 (읽기 전용 조사)

- 작성: 2026-09-06 (일), 장 마감 후
- 범위: 사용자 제안 "기동을 07:45 → 05:00 으로 당겨 하루 한 번만 돌린다" 의 **KIS 측 제약** 판정
- 원칙: 코드·DB·설정·git **무수정**. 운영 DB 는 `ssh auto-stock` → psql **SELECT 만**. KIS 실호출 **0건**
  (일요일이라 오늘 호출은 05:00 질문에 답을 못 주고, "로컬과 EC2 동시 실행 금지" 규약도 걸린다)

## 0. 결론 (verdict)

**05:00 기동은 문서화된 KIS 제약과 충돌하지 않는다. 그리고 이번 조사에서 "07:50 KIS 강제 중단" 이라는
전제 자체가 무너졌다** — 그 명제는 애초에 KIS 공식 근거 없이 채택됐고(사이클 92 `Q31=C` 가 명문 확인을
*생략*하기로 한 결정이 커밋에 그대로 남아 있다), 최근 30일 로그에는 07:50 종료가 **0건**이며, 세션이
07:50 을 **살아서 통과한 날이 6일** 있는데 그중 어느 날도 07:45~08:56 구간에 WS 중단 로그가 **한 줄도**
없다. 반대로 **실재하는 KIS 일일 강제 종료는 08:57~08:58** 이고(30일 중 거래일 19/19 발생), 지금 시스템은
매일 그것을 이미 통과하고 있다. 즉 **05:00 기동이 새로 떠안는 KIS 리스크는 07:50 이 아니라, 우리가 한
번도 세션을 열어본 적 없는 05:00~07:45 구간의 KIS 행태 미지(未知)** 다.

그 미지 구간이 위험한 이유는 KIS 때문이 아니라 **우리 코드의 예외 처리 구멍** 때문이다:
`connect()` 의 `except (ConnectionClosed, InvalidURI, OSError)` 는 **TCP 계층 실패만** 잡는다. 점검
시간대의 전형적 응답인 **HTTP 상태 거부**(`/oauth2/Approval` 의 `raise_for_status` → `httpx.HTTPError`,
또는 WS 핸드셰이크 `websockets.InvalidStatus`)는 **어느 것도 `OSError` 가 아니어서**(운영 컨테이너에서
직접 확인) 백오프·자동 재기동·로그 **전부 없이** WS task 가 즉사하고, `self._ws_task` 가 참조를 붙들고
있어 asyncio 의 "Task exception was never retrieved" 조차 뜨지 않는다. **완전 무증상 사망**이다.

그러므로 판정은 이렇다 — **KIS 제약 충돌: 없음(문서 근거 기준) / 실측 반증: 07:50 전제는 틀렸다 /
잔여 위험: 05:00~07:45 미관측 구간 × 예외 처리 구멍 1개.** 05:00 기동은 KIS 때문에 막을 사안이 아니라,
그 구멍을 먼저 막고(또는 관측 후) 가면 되는 사안이다.

그리고 **의뢰자의 잠정 분석은 맞다** — §5. 05:00 으로 옮기는 것만으로는 스텁봉 결함이 그대로
재현될 **가능성이 높다.** 단, 그 결론은 §3 의 미관측 사실 하나(05:00 에 KIS 가 오늘 날짜 봉을 이미 주는가)에
전적으로 걸려 있고, 그 사실은 지금 **아무도 모른다.**

## 1. "KIS 07:50 강제 중단" 의 정체

### 1.1 무엇이 중단된다고 적혀 있나 — 그리고 근거는

정본은 커밋 `9e556ee` (2026-06-10, 사이클 92) 하나다.

> 사용자 보고: 장 초반 시세 미수신 + 전략 감시종목 미갱신 → 강제 재기동 후 정상.
> 우리 매일 기동 07:45 vs KIS API 재기동 07:50 (**모든 기존 접속 강제 중단**) 정확히 동일 시점 충돌.

중단 대상은 **WebSocket 접속**으로 서술돼 있다(REST·토큰이 아니라). 결함 chain 도 WS 전용이다
(`MAX_RECONNECT` 소진 → 4중 안전망 무력 → 수동 재기동만이 회복 경로).

**근거의 등급이 결정적이다.** 같은 커밋에 사용자 결정이 그대로 남아 있다:

> **Q31=C KIS 공식 명문 생략 (사용자 보고 자체가 정본)**

즉 사이클 92 는 KIS 문서를 확인하지 않기로 **명시적으로 결정**했고, 07:50 이라는 시각은 **증상 1건에서
역산한 추정**이다. 이번 조사에서 다시 확인해도 근거는 나오지 않았다:

### 1.2 30일 실측 — 07:50 은 아니고, 08:57~08:58 이 진짜다

`system_logs` 는 INFO 2일 / WARNING·ERROR·CRITICAL **30일** 보존(`src/db/system_logs.py:32-33`)이라
WS 중단 계열(전부 WARNING/ERROR)은 **2026-08-07 ~ 09-06 전 구간이 남아 있다.**

WS 수신 루프가 끊기면 반드시 넷 중 하나가 찍힌다 — `WebSocket 연결 닫힘`(ConnectionClosed) /
`Heartbeat 타임아웃`(30s 무수신) / `WebSocket 끊김 n/5`(connect 예외) / `최대 재연결 횟수 초과`+`[ws_auto_restart]`.

**분(分) 단위 집계 (30일, 2회 이상 발생한 시각만):**

```
08:57  7    15:01  8    15:26  8    15:36  9    16:02  21
08:58 12    15:18  4    15:27 12    15:38  3    16:25  2
09:00  5    15:22  8    15:28  7    15:39  5    20:10  19   (20:10 = 우리 정산 disconnect)
10:02  2    11:24 2  11:25 3  12:27 3  15:46 8
```

**07:50 대(帶)는 단 한 건도 없다.** 반면 `08:57~08:58` 은 **거래일 19일 전부**에서 발생한다
(08-06/07/10/11/12/13/14/18/19/20/21/24/25/26/27/28/31, 09-01/02 — 매일 1개 세션, 08-12·08-31 만 2개).
`WebSocket 연결 닫힘` = KIS 가 먼저 닫은 clean close다. 08-24 08:57:50 은 같은 사건이 예외 경로로도
새어 `WebSocket 끊김 (sent 1000 (OK); then received 1000 (OK)), 1/5 재연결 대기 1.0s` 로 찍혔는데,
**close code 1000 (정상 종료)** 이 KIS 측 의도적 종료임을 확증한다. 30일 전체에서 `[ws_auto_restart]`
**0건**, `최대 재연결 횟수 초과` **0건** — 08:57 종료는 매번 `_receive_loop` 즉시 재연결로 흡수된다.

### 1.3 결정적 반증 — 07:50 을 살아서 통과한 날 6일

지금 WS 연결 시각은 `_boot()` 소요 시간이 정한다. `start()` 는 `await self._boot()` → 곧바로
`_ws_task = create_task(kis_ws.connect(...))` (scheduler.py:588) 이고, 일봉 task 는 그 뒤에 만들어져
`initial_delay_secs=240` 후 첫 write 를 남긴다. 09-04 실측으로 보정하면
**WS 연결 ≈ (일봉 첫 write) − 240s** (실측 오차 3초: 연결 07:51:54 vs 07:55:57−240=07:51:57).

`stock_master_daily.created_at` 으로 역산한 아침 WS 연결 시각 (2026-08-06 ~ 09-04):

|---|---|---|---|

| 08-07 | 07:52:39 | **07:48:39** | ✔ |
| 08-10 | 07:52:57 | **07:48:57** | ✔ |
| 08-11 | 07:53:27 | **07:49:27** | ✔ |
| 08-12 | 07:54:00 | **07:50:00** | 경계 |

| 08-18 이후 | 07:54:59~07:57:01 | 07:50:59~07:53:01 | ✘ (07:50 이후 연결) |

그 6일(+경계 1일)에 대해 **07:45:00 ~ 08:56:30** 구간의 WS 중단 계열 로그를 전수 조회한 결과:

```
행 0건  (websocket / heartbeat / ws_auto_restart / 재연결 / 연결 닫힘 / 끊김 전부)
```

그리고 **같은 날들에 08:57~08:58 `WebSocket 연결 닫힘` 은 정상적으로 찍혀 있다**
(08-06 08:58:08 / 08-07 08:57:05 / 08-10 08:57:58 / 08-11 08:58:21 / 08-12 08:56:58 / 08-13 08:58:12 /
08-14 08:58:42). 08:57 에 close 가 찍혔다는 것은 **그 시각까지 `_receive_loop` 가 돌고 있었다** 는 뜻이므로,
"무증상 사망(§0 의 예외 구멍)" 가능성까지 배제된다.

> **판정: 2026-08-06~14 의 6개 거래일에서 메인 + 보조 8개 세션이 07:48~07:49 에 연결돼 07:50 을
> 무중단으로 통과했고, 최초 중단은 매번 08:57~08:58 이었다.** 07:50 강제 중단은 최근 30일 운영 기록상
> **존재하지 않는다.**

한계도 적는다: (a) 30일 밖(2026-06-10 당시)의 KIS 행태는 로그가 지워져 확인 불가 — 당시 실재했다가
KIS 가 이후 바꿨을 가능성은 반증도 입증도 안 된다. (b) 08:57 종료가 어느 세션인지는 로그 라인에
label 이 없어 미상(`websocket.py:637` `logger.warning("WebSocket 연결 닫힘")`). (c) 06-10 사고의 진짜
원인은 이 조사 범위 밖이다 — 다만 "아침 시세 미수신 + 수동 재기동으로만 회복" 이라는 증상은 §1.4 의
경로로 **07:50 이 아니어도** 얼마든지 만들어진다.

### 1.4 그래도 05:00 세션이 07:50 에 끊긴다면 — 코드 판정

`websocket.py` 실경로를 그대로 따라간다. **끊김의 종류가 결과를 완전히 가른다.**

**(a) clean close (= 실제 08:57 에 매일 벌어지는 일, close code 1000)**
`_receive_loop` 의 `except websockets.ConnectionClosed` → `return` → `connect()` 의 `async with` 이탈 →
`if monotonic()-connected_at >= MIN_STABLE_SECONDS(5): self._reconnect_count = 0` → **while 재진입 =
백오프 0초 즉시 재연결.** `_restore_subscriptions_after_reconnect()` 가 구독 복원, `_reconnect_count>0`
이 아니므로(리셋됨) F1 검증 task 도 안 뜬다. 비용 ≈ 1초 + `/oauth2/Approval` 1회.
**→ 폭풍 아님. 무해.** 30일 실측 `WebSocket 연결 닫힘` 139건이 전부 이 경로다.

**(b) 30초 무수신 (heartbeat timeout)**
`asyncio.wait_for(recv(), timeout=30)` → `TimeoutError` → WARNING → `return` → (a)와 **동일하게
백오프 0초 즉시 재연결 + 카운터 리셋**. 30일 실측 44건(대개 8세션 동시 = 시장 침묵 구간 15:01/15:46 등).
⚠️ **이 경로는 상한이 없다.** `_reconnect_count` 가 5초마다 0으로 리셋되므로 `MAX_RECONNECT` 에도,
`_trigger_auto_restart` 의 시간당 3회 cap 에도 **영원히 도달하지 않는다.** 프레임이 30초 넘게 안 오는
상태가 지속되면 **세션당 분당 2회 재연결이 무한**이다 → 8세션 × 2회/분 = **분당 16 재연결 =
시간당 960회**, 각각 `/oauth2/Approval` REST 1회 동반(`get_approval_key()` 에 **캐시 없음**,
token.py:183-197 이 매번 POST). 이것이 `docs/kis/rate-limits.md §6` 의 KIS 공지
*"무한으로 연결 접속·종료 반복 → IP/앱키 일시 차단"* 에 정확히 해당한다.
**→ 05:00 기동의 진짜 폭풍 시나리오는 07:50 이 아니라 이쪽이다** (§2.3).

**(c) TCP 거부·타임아웃 (OSError 계열, `asyncio.TimeoutError` 도 py3.12 에서 `OSError` 하위 — 컨테이너 확인)**
`connect()` 의 `except` 진입 → `_reconnect_count += 1` → 백오프 1+2+4+8+16 = **31초** 누적 → 6회째
`> MAX_RECONNECT(5)` → `최대 재연결 횟수 초과` ERROR → `_trigger_auto_restart()`.
- 1차 트리거: `_auto_restart_last_at == 0` 이라 cooldown 검사 통과 → `stop()` → `start()` → **새 connect task,
  `_reconnect_count = 0`** → 구 task 는 `break` 후 `self._ws = None`.
- 2차 라운드도 실패하면 ~31~60초 뒤 다시 트리거: `now - last_at < 60` 이면 `[ws_auto_restart_cooldown]`
  WARNING **후 return False → break → 세션 영구 사망.** 60초를 넘겼으면 2차·3차 발화 후
  `len(history) >= 3` 에서 `[ws_auto_restart_cap_exceeded]` ERROR → **역시 영구 사망.**
- 자기 복구 총 커버리지 = **최대 3회 재기동 ≈ 2~4분.** 그 뒤 부활 경로 **0**:
  `_scan_loop`·K stale watcher·`_resubscribe_stale_priority` 는 `subscribe()` 가
  `if self._ws:` 에서 막혀 **SEND 자체를 안 하고**(websocket.py:482), silent-inactive 강제 재연결은
  `if ws_obj is None: ... skip`(stale_session_recovery.py:369)에서 되돌아 나오며,
  scheduler 는 `_ws_task` 의 done 여부를 **아무 데서도 보지 않는다**(참조는 finally 의 cancel 루프뿐).
  풀은 `_available_quotes()` 가 `_ws is None` 세션을 영구 제외한다.
  **→ 다음 날 `_boot()` 또는 컨테이너 재시작 전까지 tick blind.** 사이클 92 커밋의 서술과 정확히 일치.
- 버스트 크기: 세션당 사망까지 연결 시도 12~24회 × 8세션 = **2~4분 안에 96~192회.** 폭풍이라기보다
  **짧은 버스트 후 영구 침묵**이고, 나쁜 쪽은 후자다.

**(d) HTTP 상태 거부 (점검 시간대의 전형)** — **잡히지 않는다.**
운영 컨테이너(python 3.12.14 / websockets 14.2 / httpx 0.28.1)에서 직접 확인:
```
asyncio.TimeoutError is TimeoutError : True      TimeoutError ⊂ OSError : True
websockets.InvalidStatus  ⊂ OSError : False      websockets.InvalidHandshake ⊂ OSError : False
httpx.HTTPError           ⊂ OSError : False
```
`connect()` 의 `except (ConnectionClosed, InvalidURI, OSError)` 는 이들을 **전부 놓친다.**
`get_approval_key()` 의 `resp.raise_for_status()`(token.py:193) 가 403/503 을 던지거나, WS 핸드셰이크가
HTTP 503 을 받으면 → **백오프 없음 / `_trigger_auto_restart` 없음 / 로그 없음** → task 즉사.
게다가 `self._ws_task` / `_quote_connect_tasks` 가 task 참조를 계속 붙들어 GC 가 안 되므로 asyncio 의
`Task exception was never retrieved` 조차 안 뜬다(실측: `system_logs` 에 해당 문자열 0건, docker logs 도 0건).
**05:00~07:45 는 우리가 KIS 의 HTTP 응답을 한 번도 못 본 구간이므로, 이 구멍이 정확히 그 구간을 향한다.**

## 2. 05:00 에 KIS API 가 살아 있는가

### 2.1 문서 근거 — 없음

`docs/kis/` 전수 + KIS MCP 조회 결과 **KIS 점검 시간대·서비스 운영시간을 명시한 문서는 발견되지 않았다.**
`/oauth2/tokenP`, `/oauth2/Approval`, FHKST03010100 어느 쪽도 시간대 제약 기재가 없다.
**"문서 근거 없음"** 이 정직한 표기이고, 아래는 전부 *운영 로그 실측*이다.

### 2.2 실측 — 토큰 발급(`/oauth2/tokenP`)은 새벽에 살아 있다

주말 자율 작업 중 backend 컨테이너가 여러 번 재시작했고, `src/main.py` 는 기동 시 무조건 KIS 토큰을
발급한다. 2026-09-05(토) KST 성공 기록:

```
00:28:58  01:51:20  02:26:30  03:33:53  04:28:07  06:39:35  08:00:05
(각각 "토큰 발급 완료(label=main), 만료: 2026-09-06 <같은 시각>")
```

**04:28 과 06:39 가 05:00 을 양쪽에서 감싼다.** 05:00 정각은 직접 관측되지 않았지만, 그 32분 전과
1시간 39분 후에 `/oauth2/tokenP` 가 정상 200 을 냈다. 09-04(목) 23:27:08 도 성공.
⚠️ **한계: 전부 토요일(비거래일)이다.** 거래일 새벽에 KIS 가 다른 점검 정책을 쓸 가능성은 반증되지 않았다.

### 2.3 실측 — REST 시세·WebSocket 은 새벽에 **한 번도 호출된 적이 없다**

| 테이블 / 지표 | 하루 중 최초 기록 시각 (전 기간) | 07:45 이전 건수 |
|---|---|---|
| `stock_master_daily.created_at` (FHKST03010100 일봉) | **07:50:13** | **0** |
| `stock_master.refreshed_at` (CTPF1002R) | 16:08:44 | 0 |
| `stock_master.master_raw_updated_at` (마스터 파일) | 08:04:18 | 0 |
| `stock_master_financial.refreshed_at` (재무 5 TR) | 16:40:00 | 0 |
| `WebSocket 접속키 발급 완료` (`/oauth2/Approval`) | 세션 기동 시에만 (07:51 / 17:30 / 18:41 / 19:21 관측) | 0 |

**즉 이 시스템 역사상 07:45 이전에 KIS 로 나간 호출은 `/oauth2/tokenP` 뿐이다.**
REST 시세와 WebSocket approval key 의 05:00 가용성은 **완전 미관측**이다. 추측하지 않는다.

간접 정황 하나만 덧붙인다: `run_daily` 가 새벽에도 `token_manager.get_token()` + `is_market_open()`
(KIS chk-holiday) 를 호출하는 구조인데, 휴장일 판정 실패 로그가 30일간 0건이므로 **적어도 07:45 직전의
REST 조회는 정상**이다. 05:00 으로 2시간 45분 더 당겼을 때도 같은지는 **모른다.**

### 2.4 05:00 세션이 08:00 까지 살아 있으려면 — heartbeat 30초 문제

`_receive_loop` 의 무수신 타임아웃은 **30초**이고, 장 시작 전에는 tick 이 없으므로 **PINGPONG 만이
세션을 살린다.** 09-04 07:52~07:56 실측(구독 0건 상태의 보조 세션):

```
[ws_heartbeat] label=ISA  window=302s pingpong_recv=28 avg_interval=10.8s
[ws_heartbeat] label=gold window=302s pingpong_recv=29 avg_interval=10.4s   (8세션 모두 유사)
```

**07:52 시점에 KIS 는 유휴 세션에도 ~11초마다 프레임을 보낸다** → 30초 타임아웃 여유 충분.
그러나 이것은 07:52 관측이다. **05:00~07:45 의 PINGPONG 주기는 미관측**이고, 만약 그 구간에 30초를
넘기면 §1.4(b) 의 **상한 없는 재연결 루프**(시간당 최대 960 연결 + 960 approval 호출 × 8세션 분산)가
2시간 45분 동안 돈다. 이것이 05:00 기동에서 **KIS 앱키/IP 차단을 실제로 부를 수 있는 유일한 경로**이며,
`_trigger_auto_restart` 의 cooldown·cap 은 **이 경로를 전혀 막지 못한다**(카운터가 5초마다 리셋되므로).

## 3. 05:00 에 그날 일봉을 요청하면 KIS 는 무엇을 주는가

### 3.1 답: **모른다. 관측 자료가 존재하지 않는다.**

`stock_master_daily` 전 기간에서 하루 중 가장 이른 write 는 **07:50:13** (2026-07-16), 07:45 이전 **0건**.
따라서 05:00 시점 응답을 보여주는 기록은 **없다.** 못 찾았다고 적는다.

### 3.2 확실한 것 — 07:55 시점의 응답 형태 (실측)

2026-09-04 07:55:57 에 기록된 행의 `raw` (KIS 원문):

```json
{"mod_yn":"Y","acml_vol":"0","prdy_vrss":"0","prtt_rate":"0.00",
 "stck_clpr":"18560","stck_hgpr":"18560","stck_lwpr":"18560","stck_oprc":"18560",
 "acml_tr_pbmn":"0","flng_cls_code":"00","prdy_vrss_sign":"0","stck_bsop_date":"2026-09-04"}
```

**개장 전인데도 KIS 는 오늘 날짜(D) 행을 이미 준다.** OHLC 4값 전부 전일 종가, 거래량·거래대금 0,
전일대비 0. 이것이 자문 문서가 말하는 "껍데기 봉" 이다. 즉 KIS 의 일봉 시리즈는 **거래 발생 여부와
무관하게 영업일이 열리면 그 날짜 행을 선(先)생성**한다.

### 3.3 확실한 것 하나 더 — 비거래일에는 행을 주지 않는다 (실측)

오늘(일요일) 15:07~15:15 에 일봉 refresh 가 한 번 돌았고(`stock_master_daily.updated_at` 최대값
09-06 15:15, 보조 토큰 7개 재발급 15:07:40~15:13:48 동반), **그 결과에도 `bas_dd = 2026-09-05(토)`·
`2026-09-06(일)` 행은 0건**이다. 최신 `bas_dd` 는 여전히 2026-09-04(금).
**→ KIS 는 휴장일 날짜 행을 만들지 않는다.** 스텁은 거래일에만 생긴다.

### 3.4 왜 이 미지가 결정적인가

05:00 응답이 두 갈래 중 어느 쪽이냐에 따라 **사용자 제안의 결과가 정반대**가 된다.

| 05:00 에 KIS 가 주는 것 | 05:04 immediate 결과 | 그날 16:00 | 사용자 제안 단독 효과 |
|---|---|---|---|
| **(가) D 날짜 스텁을 이미 준다** (07:55 와 동일) | D 스텁 기록 → `max_bas_dd = D` | **skip**(멱등 게이트) | **결함 그대로 재현** — 의뢰자 잠정 분석과 일치 |
| **(나) 아직 D-1 까지만 준다** (영업일 롤오버가 05:00 이후) | D-1 확정봉만 기록 → `max_bas_dd = D-1` | `D-1 < D` → **정상 실행** | **코드 변경 0으로 결함 소멸** |

(가)일 확률이 높다고 본다 — KIS 가 07:55 에 이미 D 행을 주고 그 값이 순수히 *영업일 달력*에서 나온
것(거래량 0, 전일종가 복사)이므로 롤오버는 자정 부근일 개연성이 크다. 하지만 이것은 **추론이고, 이
조사에서 근거를 대지 못했다.** (나)일 여지는 남아 있고, 그 값어치가 크므로 §6 에 확인 방법을 적는다.

## 4. 토큰 수명(24h) × 05:00 기동

### 4.1 현재 실태 (실측)

`_ISSUE_GAP_SECS = 61.0` — `/oauth2/tokenP` **분당 1개 / 전역 한도**(token.py:47-52)에 맞춘 **클라이언트
측 자체 직렬화**다(KIS 가 강제하는 건 한도이고, 61초 간격은 우리 구현). 활성 보조 계좌는 현재 **7개**
(ISA / RIA / fire / gold / 44606571 / 71513056 / 1004) + 메인 1 = 매니저 8.

2026-09-04 아침 실측:

```
07:45:01  매매 시스템 시작 / [boot_preissue] label=ISA
07:46:02  RIA   (대기 60.9s)      07:47:03  fire      07:48:04  gold
07:49:05  44606571                07:50:07  71513056  07:51:08  1004
07:51:13  자금 분배 / cash_usage_ratio      07:51:16~07:51:52  7전략 prepare
07:51:54  pool_start 7세션 + "WebSocket 연결 성공" + [pool_start_ready] ready=7/7
```

`_boot()` 소요 ≈ **6분 13초**, 그중 **6분 7초가 토큰 직렬화**다. 오늘 15:07:40~15:13:48 보조 7개
재발급도 **6분 8초**로 동일(메모리의 "5계좌 6분" 과 정합).

**주목: 토큰 발급이 07:50:07 과 07:51:08 에 성공했다.** 즉 07:50 정각 전후로 `/oauth2/tokenP` 는
정상 응답했다 — §1 의 07:50 전제에 대한 또 하나의 반증이다(대상이 WS 라 직접 반증은 아니지만,
"KIS API 전면 재기동" 이라는 서술과는 충돌한다).

### 4.2 05:00 기동이 바꾸는 것

| 항목 | 07:45 기동 (현재) | 05:00 기동 | 판정 |
|---|---|---|---|
| 보조 토큰 발급 창 | 07:45~07:51 | 05:00~05:07 | 동일 비용. `/oauth2/tokenP` 는 §2.2 로 그 시각 가용 정황 |
| 토큰 만료 | 익일 07:45~07:51 | 익일 05:00~05:07 | 정상 순환. `_is_token_valid` 가 만료 10분 전 갱신(token.py:222)이라 **당일 세션 중 재발급 0회** 유지 |
| 세션 길이 | 07:45~20:10 = **12시간 25분** | 05:00~20:10 = **15시간 10분** | 24h 토큰 안에 여전히 들어감. 단 **KIS 세션 최대 유지 시간 정책은 문서 미확인** |
| `.token_cache` 재사용 | 컨테이너 재시작 시 캐시 hit → 0초 | 동일 | 변화 없음 |
| 장중 재시작 시 재발급 | 캐시 hit 이면 0초, miss 면 최대 8분 | 동일 | 변화 없음 |

**토큰 축에서는 05:00 기동에 걸림돌이 없다.**

### 4.3 오히려 05:00 이 해소하는 실재 병목 (KIS 한도가 만든 것)

현재 `_boot()` 는 **07:45 시작 → 07:51:54 종료**이고 사전 구독 마감은 **07:59** 다. 남는 여유는 **7분**뿐인데
그 안에 잔고 조회·레짐·자금 분배·7전략 prepare 가 들어간다. 그리고 6분 7초를 먹는 것은 우리 로직이
아니라 **KIS 의 분당 1개 토큰 한도**다 — 즉 **보조 계좌를 늘리는 만큼 아침 예산이 직선으로 줄어든다.**
계좌 8개면 boot 종료 ≈ 07:53, 10개면 ≈ 07:55, **12개면 07:59 사전 구독을 놓친다.** 05:00 기동은 이
절벽을 **완전히 없앤다**(05:00~07:59 = 2시간 59분 여유). KIS 제약 관점에서 이것이 사용자 제안의
가장 확실한 이득이다.

## 5. 의뢰자의 잠정 분석에 대한 판정 — 반박 없음, 단 조건부

> "기동만 05:00 으로 옮기면 일봉 결함은 그대로 재현된다. 05:04 immediate 가 max_bas_dd = D-1 < D 를
> 보고 fetch → 그 시각 KIS 오늘봉은 여전히 껍데기 → D 스텁 기록 → 그날 16:00 skip."

**KIS 측 사실관계로 반박할 근거를 찾지 못했다.** 코드도 이 서술과 정합한다 —
`_stock_master_daily_load_once` 는 `max_bas_dd == 오늘 → skip` 이 유일한 멱등 게이트이고
(scanner.py:2077-2084), 일봉 task 는 `initial_delay_secs=240` 로 **기동 +4분에 1회**, 예정 시각은
16:00 하나뿐(data_load_tasks.py:109)이다. 시각을 옮겨도 이 구조는 그대로다.

**따라서 "하루 한 번"을 만드는 것은 시각 이동이 아니라 (가) 신선도 게이트 또는 (다) 오늘봉 필터가 맞다.**

**단 하나의 유보** = §3.4 의 (나). 05:00 에 KIS 가 아직 D 행을 만들지 않았다면 시각 이동만으로 결함이
사라진다. 이 가능성은 낮다고 보지만 **배제할 근거가 없고, 확인 비용은 KIS 호출 1회다.**

**그리고 시각 이동에는 KIS 축의 독립적 이득이 실제로 있다** (스텁 결함과 무관하게):
1. §4.3 — KIS 분당 1개 토큰 한도가 만드는 아침 07:45~07:59 예산 절벽 해소. 보조 계좌 확장 가능.
2. 아침 일봉 적재 완료가 05:12 → **07:59 사전 구독까지 2시간 47분 여유.** 지금은 07:57:55 완료 →
   07:59:00 사전 구독까지 **65초** 뿐이고, 자문 §1.1 이 지적한 "360초 여유에 기댄 우연" 이 여기서도
   가장 얇다. (가)/(다) 시정과 **경쟁하지 않고 겹쳐서 두껍게 만든다.**
3. `_boot` 실패·KIS 5xx 시 재시도할 시간이 생긴다. 지금은 07:51 에 실패하면 09:00 까지 8분뿐이다.

즉 **의뢰자 분석은 맞고(시각 이동 ≠ 결함 시정), 사용자 직관도 버릴 게 아니다(시각 이동 = 마진 확보).**
둘은 배타적이지 않다.

## 6. 부수 발견 — 07:55 "5분 마진" 은 코드에 존재하지 않는다

**`TIME_BOOT = time(7, 55)` 는 소비처가 0인 dead 상수다.** `src/` 전체에서 `TIME_BOOT` 를 읽는 코드는
없다(정의 1줄 + `websocket.py:46` 주석 + `engine/CLAUDE.md` 서술이 전부). 실제 `_boot()` 는
`run_daily → start()` 가 **`TIME_AUTO_START = 07:45`** 에 호출하고 `start()` 는 곧바로
`await self._boot()` 한다(scheduler.py:582). 운영 로그가 그대로 확증한다 — `매매 시스템 시작 (현재 07:45:01)`.

**그럼 WS 가 07:51 에 붙는 진짜 이유는?** §4.1 의 **토큰 직렬화 6분 7초**다. 사이클 92 가 설계했다고
믿은 "07:50 + 5분 마진" 은 코드에 없고, 지금의 마진은 **보조 계좌가 7개라서 생긴 우연**이다.
계좌를 4개로 줄이면 boot 종료 ≈ 07:49 → WS 가 07:50 **이전**에 붙는다 — 실제로 2026-07~08 초에
그랬다(§1.3 표). 관련 문서도 전부 스테일이다:
`engine/CLAUDE.md:713` 표("TIME_BOOT 07:55 = `_boot()`"), `boot_manager.py:50` docstring
("07:50 라 KRX 영향 0"), 커밋 45e99c3 이 프론트 5곳에 심어 놓은 "07:55".

이 발견은 05:00 논의의 전제를 바꾼다 — **"07:55 로 옮겨 마진을 뒀다" 는 방어는 애초에 작동한 적이
없다.** 05:00 으로 옮겨 그 마진을 "잃는다" 는 손실도 그만큼 실체가 없다.

## 7. verdict — 05:00 기동이 KIS 제약과 충돌하는가

**충돌하지 않는다.** KIS 문서 어디에도 05:00 기동을 막는 운영시간·점검창 규정이 없고(전수 조회 결과
"문서 근거 없음"), 이 결정을 지탱해 온 "07:50 KIS 강제 중단" 은 KIS 공식 근거 없이 증상 1건에서
역산된 추정(사이클 92 `Q31=C` 가 명문 확인을 생략하기로 한 결정이 커밋에 남아 있다)인데다, 최근 30일
운영 기록으로 **반증된다** — 07:50 대 중단 0건, 세션이 07:50 을 살아서 통과한 6개 거래일(08-06/07/10/11/13/14)
모두 07:45~08:56 구간 WS 중단 로그 0줄, 그리고 실재하는 KIS 일일 강제 종료는 **08:57~08:58**(거래일 19/19,
close code 1000)로 **지금도 매일 통과 중**이라 05:00 기동이 새로 떠안는 종료 이벤트는 아니다. 토큰 축도
막지 않는다(24h 수명·10분 전 갱신·61초 직렬화 전부 05:00 에서 동일하게 성립하고, `/oauth2/tokenP` 는
04:28·06:39 KST 성공이 실측됐다). **오히려 KIS 의 분당 1개 토큰 한도가 만드는 아침 07:45~07:59 예산
절벽을 05:00 기동이 없앤다.** 다만 05:00 을 켜기 전에 반드시 알아야 할 것이 둘 있다 — 첫째, **05:00~07:45
는 이 시스템이 KIS 로 REST 시세도 WebSocket 도 단 한 번 보낸 적 없는 완전 미관측 구간**이고(전 테이블
07:45 이전 기록 0건), 둘째 그 구간에서 KIS 가 TCP 거부 대신 **HTTP 상태로 거부하면 우리 `connect()` 는
그것을 잡지 못해**(`InvalidStatus`·`httpx.HTTPError` 모두 `OSError` 아님 — 운영 컨테이너 확인)
백오프·자동 재기동·로그 전부 없이 WS task 가 **무증상 사망**하며, 반대로 KIS 가 그 시간대에 PINGPONG
주기를 30초 너머로 늦추면 `_receive_loop` 의 30초 타임아웃이 **상한 없는 즉시 재연결 루프**(세션당
분당 2회 × 8세션, 각 `/oauth2/Approval` 동반, cooldown·cap 우회)를 2시간 45분 돌려 KIS 공지가 경고한
앱키 차단을 부를 수 있다. **결론: KIS 가 05:00 을 막는 게 아니라, 우리 재연결 코드가 미지의 05:00 을
감당할 준비가 안 돼 있다.** 이 둘은 8영역(`realtime/**`) 변경이므로 승인 사안이며, 그 전에 §8 의
관측 1회로 위험을 거의 전부 걷어낼 수 있다.
