## 0. 결론 한 줄

**의뢰자의 잠정 분석은 "조건부로 맞다"** — 결정적 변수 하나(05:00 시점 KIS 가 오늘 날짜 봉을 주는가)가
실측 불가라 두 갈래인데, **어느 갈래로 가든 (B) 단독은 부족하고, 어느 갈래로 가든 (라)는 목표를 달성한다.**
그러므로 시각 이동은 목표 달성의 **필요조건도 충분조건도 아니다**. 권고 = **(A) 현행 유지 + (라)**.

## 1. 의뢰자 잠정 분석의 검증

> 검증 대상: "기동만 05:00 으로 옮기면 05:04 immediate 가 그날 껍데기를 쓰고 16:00 이 또 skip 된다"

### 1.1 발화 시각은 시계가 아니라 **기동 시각 + 240초**다 — 맞다

`src/engine/data_load_tasks.py:84~111` 이 `run_periodic_task_loop(... initial_delay_secs=240)` 로
호출하고, `src/engine/task_loop_helper.py:103~109` 가 `immediate_first_run` 블록 **맨 앞**에서
`await asyncio.sleep(initial_delay_secs)` 를 건다. `wait_time`(16:00)은 그 아래 `while` 루프
(`:154~156`)에서만 쓰인다. 즉 immediate 실행 시각은 **오직 기동 시각에 종속**이고, `TIME_AUTO_START` 를 05:00 으로
옮기면 immediate 도 그대로 05:0x 로 따라 이동한다.

라이브 실측 (`system_logs`, 09-03):

```
07:45:00  매매 시스템 시작
07:51:54  기동 완료 (_boot 종료)          ← 이 시점에 create_task
07:55:58  [stock_master_daily_load_begin] candidates=982 force=False   ← 07:51:54 + 244s
07:57:54  [stock_master_daily_load_summary] total=982 fetched=982 upserted_rows=7790 skipped_fresh=0
```

### 1.2 멱등 판정은 `today_kst()` **절대 비교**라 시각 이동에 면역이다 — 맞다

`src/engine/scanner.py:2178~2185`:

```python
if not force and latest is not None and latest >= today:
    summary["skipped_fresh"] += 1
    continue
```

`today` 는 `today_kst()` 로 함수 진입 시 1회 계산된다. 05:0x 이든 07:5x 이든 `today` 는 같은 D 이고,
`latest` 는 D-1 이다 ⇒ **어느 쪽이든 fetch 로 진입한다.** 시각 이동이 이 분기를 바꾸지 못한다.

### 1.3 `prepare` → `daily load` 순서도 그대로 유지된다 — 맞다

`scheduler.start()` 는 `await self._boot()`(`scheduler.py:582`) 를 **먼저** 끝내고 그 뒤에 데이터 task 를 `create_task`
한다(일봉 = `scheduler.py:678`). immediate 는 다시 +240s 다. 따라서 **prepare 는 어떤 기동 시각에서도
항상 daily load 보다 최소 4분 앞선다.** 05:00 기동이면 prepare ≈ 05:06, load ≈ 05:10 이다.
자문이 지목한 오염 경로("아침 prepare 가 *어제* 스텁을 전일봉으로 읽는다")는 **시각과 무관하게 보존**된다.

### 1.4 단 하나의 미검증 변수 — 05:00 에 KIS 가 "오늘 봉"을 주는가

이것만은 코드로 결정되지 않는다. 실측 가능한 범위를 전수 확인했다.

`stock_master_daily.updated_at` 의 KST 시각대별 분포 (전체 테이블):

| 기록 KST 시 | 기록 행수 | 그중 `updated_at::date == bas_dd` | 그중 스텁(vol 0 ∧ H=L) |
|---|---|---|---|
| 07시 | 140,020 | 1,179 | **1,179 (100%)** |
| 08시 | 10 | 1 | 1 |
| 09시 | 36,073 | 9 | 0 |
| 10시 | 13,248 | 7 | 0 |
| 13시 | 8,684 | 1 | 0 |
| 15시 | 6,916 | 0 | — |
| 16시 | 14,074 | 41 | 0 |
| 17~19시 | 11,323 | 39 | 0 |

- **0~6시 기록이 한 건도 없다.** 이 시스템은 07:45 이전에 적재를 돌린 적이 없으므로 05:00 KIS 응답에
  대한 라이브 근거가 **존재하지 않는다**. KIS 문서(`docs/kis/domestic-stock-quote.md:1677~1683`)에도
  FHKST03010100 상세 명세가 없다("원본 엑셀에 상세 명세 시트 없음").
- 우리가 가진 스텁 증거는 **전부 07:5x 이후** = KIS 가 매일 07:50 에 시스템을 재기동한 *뒤*의 응답이다.

따라서 두 갈래로 갈린다.

| 갈래 | 05:0x KIS 응답 | (B) 단독의 결과 |
|---|---|---|
| **갈래 ①** (오늘 스텁이 이미 존재) | 헤드 = D 스텁 | **결함 100% 재현.** 05:10 이 D 스텁 기록 → 그날 16:00 전 종목 skip → D+1 05:06 prepare 가 D 스텁을 전일봉으로 읽음. 의뢰자 분석 그대로 |
| **갈래 ②** (07:50 롤오버 전이라 오늘 행 없음) | 헤드 = D-1 실봉 | **주 경로는 닫힌다.** 05:10 이 D-1 최종본만 기록 → 16:00 이 `latest=D-1 < D` 로 fetch → D 실봉 기록 ✅. 단 **하루 2회 실행은 그대로**고, 낮 재배포 구멍은 **남는다**(§1.5) |

**정직한 판정**: 갈래 ②를 지지할 정황(07:50 KIS 재기동 = 일자 롤오버 가능성)과 갈래 ①을 지지할 정황
(스텁은 "장이 안 열렸다"의 표현이므로 자정부터 있어도 이상하지 않다)이 **대등**하다. 어느 쪽인지
모른 채로 (B)를 채택하면 **시정의 성패를 미검증 외부 동작에 건다.** 이 자체가 (B)를 단독 채택하지
않을 충분한 이유다.

> 값싼 확인 방법(참고): 평일 07:50 **이전** 아무 시각에 종목 1개로 `fetch_daily_candles` 를 1회
> 호출해 `stck_bsop_date` 헤드가 오늘인지 보면 5초 만에 갈린다. 운영 조치라 승인 사안이다.

### 1.5 갈래 ②여도 (B) 단독은 부족하다 — 낮 재배포 구멍은 실제로 발생한 적이 있다

자문이 "12:00~15:30 재시작이 부분봉을 확정봉인 척 기록한다"고 경고했는데, **이미 일어난 일이다.**
`updated_at::date == bas_dd` 인 행을 08~15시대에서 뽑으면:

| bas_dd | 기록 KST | 행수 | 스텁 |
|---|---|---|---|
| 2026-07-13(월) | 09:57~10:01 | 16 | 0 |
| 2026-07-13(월) | 13:09 | 1 | 0 |
| 2026-08-03(월) | 08:48 | 1 | 1 |

07-13 의 17행은 **거래량 > 0 · 비평탄인 진짜 장중 부분봉**이 확정봉 자리에 박힌 것이다.
지금은 아침 스텁이 대부분 종목의 `latest` 를 이미 D 로 만들어 놔서 재시작 immediate 가 거의 전부
skip 되고 **신규 진입 종목 17개만** 새는데, **(가) 신선도 게이트를 넣어 아침 스텁이 사라지면 이 구멍의
노출 면적이 전 종목으로 커진다.** 그래서 (가)와 (다)는 반드시 함께 가야 하고, 시각을 05:00 으로
옮겨도 이 구멍은 그대로다(배포·재시작은 시계와 무관하다).

### 1.6 검증 결과 요약

> 의뢰자 분석은 **갈래 ①에서 정확히 맞고, 갈래 ②에서는 "주 경로는 닫히지만 하루 한 번도 아니고
> 재시작 구멍도 남는다"로 부분적으로 빗나간다.** 어느 갈래든 **"하루 한 번"은 시각 이동이 만들지
> 못한다** — 그건 (가) 신선도 게이트만이 만든다. 이 대목은 의뢰자 분석이 전면적으로 옳다.

### 2.1 (D) 규모 산정의 근거 (실제 코드 확인)

- 이동 대상 task 는 7개다 — `scheduler.py:2968~3060` 에 `_full_universe_load_task_loop` /
  `_stock_master_daily_load_task_loop` / `_basics_refresh` / `_master_load` / `_financial_load` /
  `_evening_funnel_capture` / `_daily_purge` wrapper 가 나란히 있다.
- 이들의 본체 `run_periodic_task_loop` 는 `while scheduler._running` 과 `scheduler._wait_until()`
  두 곳에서 세션에 매여 있다(`task_loop_helper.py:154~156`). 다행히 이미 `_SchedulerLike` **Protocol**
  로 추상화돼 있어(`task_loop_helper.py:33~43`) *세션이 아닌 다른 객체*를 주입하는 것 자체는 가능하다.
  ⇒ (D)의 기술적 난도는 낮다. **문제는 난도가 아니라 계약**이다.
- `scheduler.py` 는 현재 **3,864L** 로 상한(4,000L)에 가깝다. (D)는 오히려 라인을 줄인다(장점).

  (휴장)이 비영업일엔 세션을 아예 열지 않는다.
  ⇒ **18:10 은 세션 안이다.** 즉 자문 D-9(16:00 → 18:10 이동)는 **(D)를 전혀 필요로 하지 않는다.**
  (D)가 필요한 유일한 경우는 **세션 밖 시각(23:00 / 05:00)을 고집할 때**뿐이다.

## 3. (B) 를 채택할 때 실제로 감수하는 것 (표의 "트레이딩 lifecycle 위험" 상세)

### 3.1 07:50 KIS 강제 중단 — 사이클 92 사고의 정면 부활

`docs/HARNESS_CHANGELOG.md:144` (사이클 92, 2026-06-10) 원문:

> 사용자 보고 chain = **우리 매일 기동 07:45 vs KIS API 재기동 07:50 (모든 기존 접속 강제 중단)**
> 정확히 동일 시점 충돌. 결함 chain = `MAX_RECONNECT=5 + BACKOFF_BASE=1.0` = 1+2+4+8+16=31초 누적
> → "최대 재연결 횟수 초과, 종료" → WS 영구 종료 → **4중 안전망 전부 무력** → 사용자 수동 재기동만
> 유일한 회복 경로. 증상 = **장 초반 시세 미수신 + 전략 감시종목 미갱신**.

그 시정이 `TIME_BOOT = time(7, 55)` 였다 — "KIS 07:50 강제 중단 **후** 5분 마진".

**05:00 기동은 WebSocket 연결을 05:0x 로 당겨 매일 07:50 강제 중단을 정면으로 맞게 만든다.**
현재는 09-03 실측 `07:51:55 WebSocket 연결 성공` 처럼 항상 07:50 **이후** 연결이라 이 충돌이 구조적으로
불가능하다. 남는 방어는 사이클 92 가 *추가*로 넣은 자동 재기동뿐인데, 그건 60초 cooldown + **시간당
3회 cap**(`websocket.py:48~51` `_AUTO_RESTART_COOLDOWN_SECS`/`_HOURLY_CAP`)이라 KIS 재기동이 몇 분 걸리면 메인 + 보조 7세션이 각자 cap 을 소진하고
08:00 NXT 프리 개장을 **시세 없이** 맞을 수 있다. 이건 "가능성"이 아니라 **이미 한 번 일어난 사고의
전제 조건을 복원하는 것**이다.

**부수 발견 — 지금의 방어는 상수가 아니라 우연이다.** `TIME_BOOT` 는 정의만 되어 있고 **런타임에서
한 번도 참조되지 않는다**(grep 전수: `scheduler.py:56` 정의 + `websocket.py:46` 주석 + 테스트 2파일이
전부). 실제로 07:50 을 넘겨 주는 것은 `_boot()` 안의 **보조 계좌 토큰 사전 발급이 KIS 분당 1건 한도
때문에 7×61초 = 6분 07초 걸린다**는 사실이다(09-03 실측 07:45:00 → 07:51:07). 보조 계좌를 줄이거나
토큰 캐시가 살아 있으면 이 6분이 사라져 지금도 07:50 이전에 연결될 수 있다. **(B)와 별개로 점검할
가치가 있는 잠복 결함이다.**

### 3.2 05:00 의 KIS REST 신뢰도가 검증되지 않았다

`_boot()` 는 **KIS 잔고 조회로 순자산을 읽어 그날 전 전략의 예산을 확정**한다
(`[cash_usage_ratio] net_asset=2582132 ratio=1.00 available=2582132` → `allocate_funds`).
`run_daily` 는 그 직전에 **휴장일 API**(`is_market_open`)를 부르는데, 실패하면
`"휴장일 체크 실패 — 영업일로 가정하고 진행"` 으로 **fail-open** 한다(`scheduler.py` run_daily 휴장 체크 `except` 분기).

증권사 야간 정산 배치가 도는 새벽 시간대에 잔고 API 가 무엇을 돌려주는지, 휴장일 API 가 응답하는지에
대해 **우리는 데이터를 갖고 있지 않다**(05:00대 호출 이력 0건). 07:45 는 그 배치가 끝난 시각으로
경험적으로 검증된 자리다. 잘못된 순자산으로 `allocate_funds` 가 돌면 **그날 하루 전 전략의 매수
금액이 통째로 틀어지고**, 보유가 있으면 D6 때문에 장중 되돌릴 수도 없다.

### 3.3 배경 루프 3시간 조기 가동 + 운영 창 축소

- `start()` 는 `_boot` 직후 세션 루프·stale watcher·헬스 루프·스윙 폴 등 배경 task 를 전부 띄운다.
  05:00 기동이면 이들이 **2시간 59분 일찍** 돌기 시작한다(구독은 07:59 이후이므로 대부분 무해하나,
  KIS 세션·로그·metric 창이 전부 3시간 길어진다).
- **배포 창이 줄어든다.** CLAUDE.md 운영 가이드의 야간 창 `20:20~익일 07:45` 가 `20:20~04:55` 로
  **2시간 50분 짧아진다.** 최근의 자율 작업이 실제로 이 창의 새벽 구간을 쓰고 있으므로 실질 비용이다.
- `docs/architecture.md:252,347` · CLAUDE.md 배포 창 문구 · 영속 가드 `test_cycle92_time_auto_start_persistence.py`
  가 모두 동행 개정 대상이다.

### 3.4 (B) 가 **깨지 않는** 것 (공정하게)

- **하루 시각표는 안 밀린다.** `start()` 는 배경 task 생성 직후 `now = datetime.now().time()` 을
  **한 번** 잡고(`scheduler.py:719`), `if now < TIME_PRESUBSCRIBE: await self._wait_until(TIME_PRESUBSCRIBE)`
  로 07:59 까지 기다린 뒤 08:00/09:00:05/15:20/… 를 그대로 탄다. 05:00 기동이어도 매매 시각표는 동일하다.
- `start()` 의 `now >= TIME_SETTLEMENT` 거부 가드, `run_daily` 의 주말·휴장 분기도 그대로 성립한다.
- 토큰 24h 캐시 만료 정렬도 07:45 → 05:00 으로 통째로 평행 이동할 뿐 구조는 같다.

## 4. 사용자 제안의 **고유 이득** — 있는가

정직하게 나눈다.

### 4.1 "이것만이 준다"고 말할 수 있는 것 — **하나 있다 (2차적)**

> **`_boot` 의 시간 예산이 14분 → 3시간으로 늘어난다.**

현재 예산은 `07:45 기동 → 07:59 사전 구독 마감` = **14분**이고, 그중 6분 07초를 토큰 사전 발급이,
40초를 7전략 prepare 가, 116초를 일봉 적재가 쓴다. 자문이 근본 해법인 **안 (E)("prepare 를 daily load
*뒤*로 옮긴다")를 기각한 이유가 정확히 이 예산**이었다("07:45~07:59 = 14분에 119초짜리 적재를 끼워
넣게 된다"). 05:00 기동은 그 제약을 없애 **(E)를 실행 가능하게 만든다.**

그리고 (E)는 (라)가 못 하는 일을 한다 — (라)는 아침 prepare 의 *입력*을 고칠 뿐 **"prepare 가 적재보다
먼저 돈다"는 순서 자체는 그대로 두므로**, 16:00 적재가 실패한 다음날에는 다시 08:02 우연 복구에
의존한다(자문 §8-5 가 스스로 인정한 잔여). 순서를 뒤집으면 그 의존이 사라진다.

다만 이건 **간접 이득**이다. 05:00 기동이 (E)를 *가능하게* 할 뿐 (E)를 *구현해 주지는* 않는다.
그리고 §3 의 비용을 치르고 얻는 것치고는 대가가 크다 — 같은 목적을 **`initial_delay_secs` 를 240 →
0 으로 낮추고 prepare 를 그 뒤로 미루는 방식**으로도 접근할 수 있고, 그건 기동 시각을 안 건드린다.

### 4.2 "이것도 준다"고 흔히 오해되는 것 — **셋 다 아니다**

| 기대한 이득 | 판정 |
|---|---|
| **"prepare 가 D-1 최종본을 읽는다"** | **아니다.** `_boot`(prepare) → `create_task` → +240s → load 순서는 기동 시각과 무관하게 고정이다(§1.3). 05:06 prepare 는 여전히 05:10 적재보다 앞선다. 이 이득은 **(E) 순서 변경만**이 준다 |
| **"07:51 prepare / 07:56 적재 경합의 소멸"** | **아니다.** 그 둘의 간격(4분)은 `initial_delay_secs=240` 이 만든 상수이고, 시각 이동은 둘을 **같이** 옮길 뿐이다. 경합은 05:06/05:10 으로 이사할 뿐 그대로다 |
| **"하루 한 번"** | **아니다.** immediate + 16:00 두 발화는 그대로다. 갈래 ①에서 16:00 이 skip 되는 것은 "한 번"이 아니라 **잘못된 한 번**이다. 진짜 "한 번"은 (가) 신선도 게이트만이 만든다 |

### 4.3 갈래 ②일 때만 성립하는 이득 하나

갈래 ②(05:00 에 오늘 행 없음)라면, **아침 재fetch 가 D-1 **최종본**(시간외 단일가 포함)을 덮는 자기
치유가 유지된다** — 이건 (라)가 명시적으로 포기하는 것이다(자문 §A-1 "(라) 가 잃는 것"). 즉 갈래 ②에서
(B)는 "결함도 닫고 시간외 물량도 안 잃는" 조합이 된다.
**단 그 대가가 §3 전체이고, 전제는 미검증이며, 같은 이득을 D-9(16:00 → 18:10 이동, 상수 1줄, 세션 안)이
비용 없이 준다.**

## 5. (라)만으로 사용자의 목표가 이미 달성되는가

**달성된다. 정직하게, 예 다.**

`task_loop_helper.py:111~131` 의 신선도 게이트는 마커가 `immediate_skip_if_fresh_hours` 이내면
immediate 를 **건너뛴다**. daily load 에 20.0h 를 주면:

| 요일 | 마커(직전 성공) | 아침 immediate 경과 | 결과 | 그날 실행 횟수 |
|---|---|---|---|---|
| 화~금 | 전일 16:0x | 15.8h < 20h | **skip** | **1회 (16:00)** |
| 월 | 금 16:0x | 63.9h > 20h | 실행 | 2회 (주 1회 무결성 재fetch) |
| 16:00 실패 다음날 | 전전일 16:0x | 39.9h > 20h | 실행 (안전망 부활) | 2회 |

즉 **"하루 한 번"은 시각 이동 없이 인자 하나로 성립한다** — 화~금 1회, 월요일과 사고 다음날만 2회다.
이 메커니즘은 상상이 아니라 **이미 프로덕션에서 돌고 있다**. 09-03 실측 로그:

```
07:59:58  [stock_master_basics_refresh] immediate run skip — fresh last_success=2026-09-02T16:11:16+09:00
08:03:57  [stock_master_master_load]    immediate run skip — fresh last_success=2026-09-02T16:30:13+09:00
```

basics·master·financial 세 task 는 이 인자를 이미 갖고 있고 매일 아침 정확히 그렇게 건너뛴다.
daily load 만 사이클 193 이 "`max_bas_dd` 멱등을 믿어서" 뺐고(`data_load_tasks.py:110` 주석),
**지금 깨져 있는 것이 정확히 그 멱등**이다.

그리고 사용자의 표현 "**미리 05:00에 기동해서**"의 진짜 동기 — *"아침에 도는 그 실행이 전일자 내역만
가져오는 헛일이니 없애자"* — 는 **(가)가 실행 자체를 없애는 방식으로 더 완전하게 달성한다.**
05:00 으로 옮기면 헛일이 3시간 일찍 도는 것이고, (가)를 넣으면 헛일이 **사라진다.**

## 7. 권고

### verdict = **(A) 현행 유지 + (라)** — 명세 `cycle263` 원안 그대로 간다.

사용자의 문제 인식("아침 실행은 전일자 내역만 가져오는 헛일이니 하루 한 번으로 줄이자")은 **정확하고,
이번 사이클 설계의 방향을 정한 판단**이다. 다만 그 목표를 이루는 것은 **기상 시각이 아니라 신선도
게이트**다 — 코드가 immediate 발화를 `기동 시각 + 240초`로, 멱등 판정을 `today_kst()` 절대 비교로
묶어 두었기 때문에 시각을 옮겨도 아침 실행은 3시간 일찍 그대로 돌 뿐이고(§1.1~1.3), 05:00 에 KIS 가
오늘 껍데기를 주는지는 테이블 전체를 뒤져도 근거가 0건이라(F-5) 시정의 성패를 미검증 외부 동작에
걸게 된다. 반대로 (가) 한 인자는 basics·master·financial 세 task 가 매일 아침 실제로 건너뛰며
프로덕션에서 검증 중이고(09-03 로그), 그것이 화~금 실행을 **1회로 만든다** — 사용자가 원한 "하루 한 번"
그 자체다(§5). 그 대가로 (B)가 요구하는 것은 사이클 92 가 사고 한 번을 겪고 세운 "07:50 KIS 강제 중단
이후에 붙는다"는 방어의 해체(§3.1), 검증된 적 없는 새벽 잔고·휴장 API 신뢰(§3.2), 야간 배포 창 2시간
50분 반납과 사용자 결정 기반 영속 가드 은퇴(§3.3·F-3)인데, 그 셋을 치르고 얻는 고유 이득은
"`_boot` 예산이 14분→3시간이 되어 안 (E) 순서 변경이 가능해진다"는 **간접적 한 줄뿐**이다(§4.1).
사용자 취지 중 (라)가 유일하게 못 담는 것 — **당일 확정본(시간외 단일가 포함)을 그날 안에 잡는 것** —
은 (B)가 아니라 **D-9(`TIME_STOCK_MASTER_DAILY_LOAD` 16:00 → 18:10, 상수 1줄, 세션 안, (D) 불필요)**
가 다음 사이클에서 깨끗하게 준다(F-4). 그러므로 **이번엔 (라)를 배포하고 D+1 두 prepare 수렴을 확인한
뒤, "밤에 한 번 확정본으로"는 D-9 로 잇는다**가 사용자 의도에 가장 충실하면서 위험이 가장 낮은 경로다.

### 후속 제안 (별건, 우선순위 순)

1. **D-9 (16:00 → 18:10)** — (라) D+1 확인 후. 사용자의 "밤에 한 번" 취지를 상수 1줄로 실현하고,
   (라)가 포기한 시간외 물량까지 회수한다. `scheduler.py` 상수 변경이므로 승인 사안.
2. **F-1 (`TIME_BOOT` 죽은 상수 + 07:50 방어가 우연에 얹혀 있음)** — 관측 1행이라도 붙여 두거나,
   `_boot` 안에서 `TIME_BOOT` 까지 명시 대기하는 방향을 검토. (B)를 안 해도 잠복 위험이다.
3. **갈래 판정 프로브(선택)** — 평일 07:50 이전 1종목 `fetch_daily_candles` 1회. 5초짜리 확인으로
   §1.4 의 두 갈래가 영구히 갈린다. 지금 결정에는 불필요하지만 기록해 둘 값어치는 있다.
