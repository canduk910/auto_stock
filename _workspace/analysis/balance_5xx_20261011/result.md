# D6 — 잔고 조회 API(TTTC8434R) 5xx 원인

- 작성 2026-10-11 (일) · 읽기 전용 · 코드/설정 변경 0 · DB 쓰기 0 · KIS 호출 0
- 사용자 원문: 「D6 : 잔고조회 오류 원인 확인해보자.」
- 배경: 주간 자문 10-08 §5.1·§6 D6(`_workspace/domain_consult/weekly_advice_2026-10-08.md`)

## 한 줄 결론

**원인 = 유력: KIS 쪽 「원장 유량 제한」(잔고조회 TR 전용, 전 고객 합산 초당 120건).** 우리 호출 빈도와 무관하게, KRX 정규장 시간에 이 TR 에 전체 고객 트래픽이 몰리면 KIS 가 거부한다.

- 같은 호출자(계좌 위험 감시, 5분마다 혼자 1회)가 **09:00~15:30 에는 12.2%(105/858회) 실패**하고 **15:30~21:30 에는 0%(0/792회)** 실패한다. 호출 방식·파라미터·간격이 똑같은데 시간대만 다르다.
- 4개월(06-01~10-08) 동안 메인 경로 5xx 는 **전부 이 한 경로**(`inquire-balance`)였다. 주문·체결조회 등 다른 메인 TR 은 5xx 0건(metrics `top_5xx_paths` 상위 5개에 늘 이 경로 하나뿐). 시세 풀(다른 앱키)도 파일 로그 3주간 5xx 0건(네트워크 끊김만 있다).
- KIS 공식 문서(`docs/kis/domestic-stock-order.md` 잔고조회 개요 ※중요 2): 「이 TR 은 원장 유량정책에 따라 **개인 고객 유량 무관하게 초당 120 TPS 로 제한**된다. `EGW00215 원장에서 허용 가능한 초당 거래건수를 초과하였습니다` 는 이 사유이니 **재시도**하라. 조회가 느린 TR 이라 주문 준비에는 매수/매도가능수량 조회 TR 을 권장한다.」
- 「확정」 이 아닌 이유: 우리 코드가 5xx 응답 **본문을 버린다**(`src/api/base.py::_request` 가 `raise_for_status()` 에서 바로 예외로 넘어가 `msg_cd` 를 읽지 않는다). 그래서 실제 거부 코드가 `EGW00215` 인지 로그로 확인할 수 없다. 본문 한 줄을 남기면 확정된다(제안 1).

### 2.1 동시 호출·직전 간격

- 실패한 감시 호출은 **혼자 부른 것**이다 — 동기화와는 위상이 수십~수백 초 떨어져 있고, 감시 사이 간격은 늘 ≈300초다. 「여러 경로가 같은 초에 겹쳐서」 는 실패의 주된 모양이 아니다.
- 우리 메인 경로 전체가 하루 수백 회(평균 1분에 1회 미만)이고 래퍼가 초당 20건으로 막는다(`_rate_limit`). 개인 유량 초과(`EGW00201`)라면 다른 TR 도 같이 걸려야 하는데 4개월간 0건이다.
- 화면 10초 폴링은 실패율을 바꾸지 않고 **실패 횟수(노출)**를 늘린다 — 열어 둔 동안 분당 6회 × 12% ≈ 분당 0.7회 실패, 60초 묶음 로그로 1~2분에 1줄. 실제 묶음 간격(70~120초)과 맞는다.

## 4. 부수 발견 — 계좌번호가 로그에 남는다

`[account_risk_watch_failed]` 와 `[balance] get_balance 실패` 경고는 httpx 예외 문자열을 그대로 싣는데, 그 문자열에 **요청 URL 전체(쿼리의 `CANO=` 계좌번호 포함)**가 들어 있다. 이 줄은 파일 로그와 `system_logs` 에 모두 저장되고, `system_logs` 는 리포터 키로 GET 할 수 있다. 이 보고서에는 그 값을 옮기지 않았다.

## 5. 개선 제안 (제안만 — 코드 변경은 별도 사이클)

1. **5xx 응답 본문 한 줄 기록 (원인 확정용, 먼저)** — `src/api/base.py::_request` 의 `HTTPStatusError` 분기에서 `e.response.text` 앞 200자(또는 JSON 의 `msg_cd`·`msg1`)를 남긴다. 하루만 모아도 `EGW00215` 인지 확정된다. `base.py` 는 8영역이 아니다(`src/api/order.py` 만 8영역).
2. **이 TR 전용 재시도 예산 늘리기** — KIS 가 「재시도하라」 고 한 거부다. 지금 3회·총 ≈1.5초. 잔고 경로(`inquire-balance`)만 시도 횟수나 간격을 늘리면(예: 5회, 1~2초 간격) 소진(현재 월 15건)이 대부분 사라질 것으로 본다. 주문 경로(`_ORDER_RETRY_RESTRICTED_PATHS`)와는 무관하다. 본문으로 `EGW00215` 를 판별할 수 있게 되면 그 코드에만 적용할 수 있다.
3. **잔고 조회 결과 공유(짧은 캐시)** — 감시·동기화·화면·리스크 카드가 각자 부른다. 10~30초 TTL 로 마지막 성공 결과를 공유하면 장중 호출 수, 곧 실패 노출이 준다. 특히 화면 잔고표 10초 폴링이 열어 둔 시간 동안 최대 호출원이다(폴링 간격 완화 또는 캐시 재사용).
4. **게이트의 실패 처리를 차단선 켜기 전에 정하기** — 지금은 한 번 소진되면 바로 fail-open 이다. 게이트에 이미 있는 신선도 한도(`_GATE_STALE_MAX_SECS=900`) 안이면 직전 평가값을 유지하는 쪽으로 바꾸면, 차단선을 켠 뒤에도 이 5xx 가 게이트를 뚫지 않는다(감시 1회 실패 ≠ 판정 불가).
5. **15분 동기화 실패를 보이게** — 지금은 DEBUG 한 줄이라 재대조가 건너뛰어진 것을 아무도 모른다. INFO/WARNING 1줄(+ 다음 주기 즉시 재시도 여부)을 검토.
6. **주문 쪽 수량 확인은 매도가능수량 TR 로** — KIS 가 주문 준비에는 잔고조회 대신 가능수량 조회 TR 을 권장한다. `order_engine.py:2395`·`:2635` 의 매도 거부 재대조가 해당한다. ⚠️ `order_engine.py` 는 8영역이라 승인 대상.
7. **계좌번호 마스킹** — 위 §4 의 두 경고 문자열에서 `CANO=` 를 가린다.
8. **집계 보강** — 경로별 총 호출 수(`by_path_total`)를 metrics 에 추가하면 「실패율」 을 바로 낼 수 있다. 재시작 리셋은 `since` 로 이미 보이게 됐다(10-07~).

## 6. 방법·한계

- 출처: EC2 파일 로그 `~/auto_stock/logs/auto_stock.log.2026-09-21 ~ 10-10`(09-24·25·10-03·05·09 는 휴장일 소용량), `system_logs`(09-09~), `daily_log_reports.metrics.api_metrics`(06-01~). 모두 SELECT·grep 만.
- 5xx 로그는 같은 경로·같은 상태코드 60초에 1줄로 묶인다(`_record_request_5xx_for_dedupe`). 그래서 「건수」 는 「실패한 호출 수」 의 하한이다. 감시(300초)·동기화(15분)는 간격이 60초보다 길어 1줄 = 1회 실패 호출로 봐도 된다. 화면 폴링 구간은 실제 실패가 더 많다.
- 호출자 판정은 시각 위상으로 했다. 재시작한 날(09-29·10-02·10-07)은 재시작 뒤 감시 위상이 바뀌어 일부가 「미분류」 로 갔다(장후 0% 결론에는 영향 없음 — 장후 5xx 자체가 평일 2건뿐).
- 응답 본문이 없어 KIS 거부 코드는 문서와 정황으로만 추정했다(→ 제안 1).
- 오늘 16:35 배포로 컨테이너가 재생성되어 docker 표준출력 로그(nginx 접근 로그 포함)는 남아 있지 않았다 — 화면 호출 수의 분모를 못 낸 이유다.
