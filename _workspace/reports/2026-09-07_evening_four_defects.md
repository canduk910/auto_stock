## 4. cycle267 (TLS 2단계 HSTS 검사식 시정) — 켜려다 실패, 원인 규명

### 4.1 가동 시도와 결과

- **선결 확인** — 20:20 클라우드 루틴이 **https 정식 주소로** 성공한 것을 로그로 확인했다
  (예비 http 주소를 쓰지 않았다). 이것이 런북의 사람 게이트 `ROUTINE_HTTPS_CONFIRMED=1` 의 근거다.
- 런북 1단계 = 루틴 프롬프트에서 http 예비 주소 문장 제거 + `/api/health` → `/health` 404 버그
  동반 시정(런북 밖 1건, 메인 세션 판단으로 시정하고 공개).
- **21:0x 가동 → 사후 검증 미통과 → 스크립트가 자동 원복.**
  사이트는 정상 유지(80·443 모두 401), 백엔드 무접촉.

### 4.2 원인 [실측]

`grep -E` 는 패턴 안의 `\r` 을 캐리지 리턴이 아니라 **리터럴 알파벳 `r`** 로 해석한다.
HTTP 헤더 줄은 **CRLF** 로 끝나므로 `...max-age=86400\r?$` 는 **정상 응답에도 절대 매치되지 않는다**.
실패 로그의 나머지 넷(80=301 · acme=404 · 443=401 · state=running)이 **전부 정답**이었던 것이 방증이다.
이 결함은 cycle260(TLS 2단계 준비)이 "접두 매치라 `max-age=0` 도 통과" 하는 뮤테이션 ESCAPED 를 막으려
정확 값 매치로 조이면서 심었다.

### 4.3 ⚠️ 이 결함은 개발기에서 은폐된다 [실측 — 전부 직접 실행]

| 구현 | `\r` 해석 | 결과 |
|---|---|---|
| GNU grep 3.11 (EC2 · CI) | 리터럴 `r` | **결함 발현** |
| BSD grep (macOS) | 캐리지 리턴 | 은폐 |
| ugrep 7.8.4 (개발기 PATH 실제 값) | 캐리지 리턴 | 은폐 |
| busybox grep (nginx:alpine) | 캐리지 리턴 | 은폐 |

**`\r` 해석에서 GNU 가 소수파다.** 메인 세션의 로컬 `grep` 이 실제로는 ugrep 7.8.4 였다.
"로컬 초록 · CI 붉음" 계열(cycle256 `ast.dump` sha, caplog 레벨과 같은 함정)이라
가드에 **GNU 의미론 심**을 세워 호스트 무관하게 운영과 같은 판정을 내게 했다.

### 4.4 기존 가드가 못 잡은 이유 (추정 아님, 소스 실측)

`test_cycle260` 의 가짜 curl `_FAKE_CURL` 이 헤더를 **LF 로만** 조립해 `\r?` 의 `?` 가 항상
"없음" 으로 매치됐고 뮤테이션 10개가 전부 초록이었다.
**단언이 약했던 게 아니라 입력이 현실과 달랐다** — cycle266 의 목 결함과 같은 계열이다.
→ `_FAKE_CURL` 을 **기본 CRLF** 로 바꿨다(`FAKE_HEADER_EOL=lf` 로 옛 동작 복원 가능,
다른 손잡이·기존 48 테스트 함수는 무변경).

### 4.5 시정

`HSTS_VALUE` 상수 + `hsts_ok()` 헬퍼. **`tr -d '\r'` 로 CR 을 먼저 제거**해 셸·grep 의
이스케이프 해석에 **전혀 의존하지 않게** 했다. 끝 `$` 앵커를 남겨 cycle260 이 지키려던 정확 값 매치
(`max-age=0` · `max-age=864000` · `includeSubDomains` 차단)는 유지된다.

**운영 GNU grep 3.11 직접 검증(EC2)** — CRLF·LF 정상 헤더 통과, 위 셋 + 헤더 부재 차단,
**옛 패턴은 같은 CRLF 에서 실패** = 09-07 실패의 완전한 재현.

## 18. 배운 점
