## 1. 🔴 성공의 정의 — 줄 수가 아니다

리팩토링 지침 0계명(이 지시로 명문화)의 순위를 그대로 쓴다.

| 순위 | 목표 | 측정 |
|---|---|---|
| 1 | 수정 시 누락 위험 ↓ | 한 규칙을 바꿀 때 **손대야 하는 파일 수** |
| 2 | 이해 비용 ↓ | CC · 중첩 · **한 함수가 다루는 관심사 수** |
| 3 | 변경 위험 ↓ | 커버리지 · 결합된 `self` 상태 수 |
| 4 | 중복 ↓ | 3회 이상 반복 패턴 |
| 5 | 줄 수 | 위 넷의 **결과로만** |

**보고 금지 문구** — 「N줄 줄였다」.
**보고할 문구** — 「이 규칙은 이제 한 곳에서만 고치면 된다」 · 「관심사 4개가 각각 제 이름을 갖게 됐다」.

하나라도 "확인 못 함"이면 그 단계는 **되돌리고** 회귀 테스트를 먼저 세운다.

## 3. 단계 규약

- **1단계 = 1커밋 = 1의도.** 묶으면 회귀 추적이 불가능하다.
- 각 단계 후 **전체 스위트**(11,100+)와 **AST 가드**(1,797)를 돌린다.
- `order_engine.py` 는 8영역이라 sha 핀 재핀이 따라온다 — 단계마다 1회.
- **되돌리기 = 그 단계 커밋 하나 revert.** 그래서 단계를 작게 자른다.

## 4. 절대 건드리지 않는 것 (「절대 깨지 말 것」)

- **주문번호 매핑 5종** 등록은 `place_order` 응답 직후 **동기 영역**, `await insert_trade` **전**
- **체결통보 선행 race 가드**(`_completed_orders` + UPDATE 0건 보정 INSERT)
- **NXT 좀비 차단** — `is_market_closed_rejection` 이면 positions 보존 + `_selling` **discard**
- **시장가 거부 → 지정가 5호가 폴백 1회** 규약
- `_selling` 의 add/discard **전 경로** — 하나라도 빠지면 stale `_selling` = 손절 마비

## 5. 중단 기준

다음 중 하나라도 나오면 **그 단계에서 멈추고 사용자에게 보고**한다.

- 미커버 구간을 건드려야 하는데 회귀 테스트를 못 세운다
- 행위 보존을 증명할 수 없다(리뷰어 셋 중 하나라도 "확인 못 함")
- 추출이 위 4절의 순서·생명주기를 바꾼다
- 월요일 07:45 가 가까워진다 — **부팅 전에 끝나지 않으면 되돌리고 중단**

## 🔴 진행 중 발견 — 리팩토링보다 먼저 고칠 결함 (cycle327)

`execute_sell` 구조를 조사하다 **실제 결함**을 찾았다. 리팩토링은 이것 뒤로 미룬다.

### 재현 (실측, 추측 아님)

```
매도 주문이 2회 나갔다 — INSERT 도중 체결이 착지했는데 재발사했다.
발사 내역: [SELL 10주, SELL 10주]
```
`tests/unit/engine/test_cycle327_sell_fill_during_insert.py`

### 사슬

```
_handle_sell_fill:2486  UPDATE affected == 0
        :2494           _completed_orders.add(order_no)
        :2497           COMPLETED 직접 INSERT
        :2471           del state.positions[ticker]      ← 전량 체결이면
execute_sell:1557       insert_trade → UniqueViolationError

```

`pos` 는 `:1377` 의 **지역 참조**다. 포지션이 삭제돼도 옛 수량을 들고 있다.

### 비대칭

| 경로 | INSERT | cycle271 흡수기 |
|---|---|---|
| 매수 주(`:1192`) · 폴백(`:1306`) | `_insert_pending_buy_or_absorb_race` | **있음** |
| 매도 주(`:1557`) · 폴백(`:1896`) | 맨 `insert_trade` | **없음** |

정본 `src/engine/CLAUDE.md` 는 "매수·매도 양쪽"이라 적지만, 양쪽에 있는 것은
**발사 직후 선행 체크**(`:1538`/`:1877`)뿐이다. **INSERT 도중 착지 흡수**는 매수 전용이다.

### 🔴 정정 — 부분 체결은 이 race 를 만들지 않는다 (자문 검증 + 실측)

앞선 기록은 "부분 체결이 더 위험" 이라 적었는데 **이 race 에 한해 틀렸다.**
매도 부분 체결 분기는 **보정 INSERT 를 하지 않는다**(`grep -c insert_trade` = 0).
UNIQUE 위반이 생기는 것은 **전량 체결 분기뿐**이다.

대신 자문이 더 큰 축을 짚었다 — **진짜 위반은 UNIQUE 가 아니라
「주문이 나간 뒤의 실패를 발사 실패로 오인해 재시도한다」** 이다.

| 접수 후 실패 | 체결통보 | 포지션 | 재발사하면 |
|---|---|---|---|
| UNIQUE 위반 | 이미 왔다 | 삭제됨 | 같은 수량 중복 매도 |
| **DB 타임아웃·페일오버** | **아직** | **살아 있다** | 🔴 수량 재확인마저 통과 → 확실한 중복 매도 |

즉 ⓒ(포지션 재확인) 하나로는 부족하다. **ⓑ(접수 후 경계를 닫는 것)가 본체다.**

### 🔴 피라미딩 관점 (사용자 지적)

> "나중에 피라미딩으로 매수/매도가 진행되는 경우 이 결함은 의도와 다르게 동작할 수 있어."

피라미딩이 들어오면 **부분 체결이 예외가 아니라 정상 경로**가 된다.
사다리로 나눠 사고 나눠 파는 구조에서는 「한 종목 = 단일 `Position` = 단일 수량」 전제가
무너지는데, 재시도는 그 낡은 단일 수량을 들고 발사한다.

2. **결함 수정** — 행위가 바뀌므로 리팩토링 커밋과 **섞지 않는다** ✅ 완료
3. **그 뒤 리팩토링 재개** ← 여기

### 수정 내용 (한 커밋, 자문 권고대로)

| | 조치 | 코드 |
|---|---|---|
| ⓐ | 흡수기 일반화 | `_insert_pending_buy_or_absorb_race` → `_insert_pending_or_absorb_race(side=…)`, 마커 표 `_FILL_DURING_INSERT_MARKER` 2종. 호출 4곳(매수 주/폴백 · 매도 주/폴백) |
| ⓑ | 재시도 경계를 `place_order` 성공에서 닫기 | 매도 주 경로·폴백 경로의 접수 후 구간을 각각 `try/except Exception` 으로 감싸고 `[sell_post_send_error]` 후 종료 |
| ⓒ | 발사 직전 포지션 재확인 | 재시도 루프 진입부에서 `strategy.state.positions.get(ticker)` 재조회, 부재 시 `[sell_position_gone]` + `_selling.discard` + return |

**판별기가 실제로 판별하는 것을 확인했다** — ⓑ의 `except Exception` 을 `except UniqueViolationError`
로 좁히자(=ⓐ만 남은 상태) `test_sell_does_not_refire_on_generic_insert_error` 가 붉어지며
**3회 발사**(시도 1/2/3)가 그대로 재현됐다. 원복 후 다시 초록.

**피라미딩 관점** — 자문 확인: 세 조치 모두 피라미딩에서 **그대로 산다**. ⓒ가 수량을
재조회 값에서 가져오므로, 사다리로 나눠 파는 구조에서도 옛 참조의 수량을 쓰지 않는다.

**남은 것(이번 사이클 밖)** — `_handle_sell_fill` 의 전량 판정이 `ordered_qty` 기준이라
**부분 청산 주문이 전량 체결되면 남은 보유까지 지운다**(자문 지적). 지금은 한 종목 = 단일
`Position` 이라 무해하고, 피라미딩 착수 사이클의 선결 과제다.
