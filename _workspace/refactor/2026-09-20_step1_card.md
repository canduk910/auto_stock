## 왜 이것이 첫 수인가

**0계명 1순위(수정 시 누락 위험)를 직격한다.** 이 규칙은 지금 **4곳**에 복제돼 있고

| 축 | 위치 |
|---|---|
| 매수 주 경로 | `order_engine.py:1186-1208` |
| 매수 지정가 폴백 | `order_engine.py:1301-1320` |
| 매도 주 경로 | `order_engine.py:1570-1602` |
| 매도 지정가 폴백 | `order_engine.py:1923-1956` |

**그 흩어짐이 cycle327 실사고의 원인**이었다 — 흡수기가 매수 2곳에만 달려 있었고 매도 2곳에는
없어서, 한 번의 INSERT 실패가 **이미 판 것을 다시 팔았다**(실측 3회 발사). cycle327 이
`_insert_pending_or_absorb_race` 로 **INSERT 축만** 모았고, 그 위의 **선행 체크·경계 닫기**는
여전히 4곳에 손으로 복제돼 있다. 즉 같은 종류의 누락이 다시 가능하다.

1단계에서 매도 2곳을 모으면 **매도 축은 한 곳에서만 고치면 된다.**
2단계에서 매수 2곳을 같은 헬퍼로 올리면 4→1 이 된다. 매수를 1단계에 섞지 않는 이유는 매수 쪽에
`llm_buy_gate.observe_order` 훅 순서 계약(cycle276 C7/C8)과 `_pending_buy_orders` 등록이 얹혀 있어
**의도가 둘**이 되기 때문이다.

### 0계명 순위별 기여

1. **수정 시 누락 위험** — 매도 접수 후 규칙 **2곳 → 1곳**(전체 4곳 → 3곳, 2단계에서 1곳)
2. **이해 비용** — `execute_sell` 이 다루는 **19개 관심사 중 2개가 하나의 이름**을 갖는다.
   폴백 경로 최심 블록 중첩 **7 → 5**(`:1946` 은 함수 본문 기준 7단, 헬퍼 호출로 바뀌면 5단)
3. **변경 위험** — 그 구간이 결합한 `self` 상태가 **2개**뿐(`_completed_orders`,
   `_insert_pending_or_absorb_race`). 미커버 줄이 있었으나 **선행 회귀로 닫혔다**(아래)
4. **중복** — 4회 반복 패턴(3회 규칙 충족)
5. 줄 수 — 위 넷의 결과로만. **보고하지 않는다**

## 행위 보존의 근거

- **주문번호 매핑 5종이 `place_order` 응답 직후 동기 영역에 남는가** — **남는다.**
  매핑 블록(`:1557-1563`, `:1913-1919`)은 한 줄도 움직이지 않고, 새 `await` 는 매핑 **뒤**(현재
  `try:` 가 있던 자리)에 놓인다. `place_order` 반환 ~ 매핑 사이 `await` 는 여전히 0건이며,
  `test_cycle291_ast_scope.py::test_a10c` 의 `self._order_exchange[` / `self._order_division[`
  **5곳 카운트도 불변**이다. (양보점 이동 여부는 아래 「추가 확답 2」에서 따로 따진다.)
- **`_selling` add/discard 전 경로가 보존되는가** — **보존된다.** 대상 구간에 `_selling` 참조가
  **0건**이다(`:1363` add / `:1381`·`:1387`·`:1393`·`:1426`·`:1543`·`:1620`·`:1988`·`:2053`
  discard 전부 구간 밖·무접촉).
- **접수 후 경계(cycle327 ⓑ)가 보존되는가** — **보존된다.** `try/except Exception` 이 헬퍼 안으로
  통째로 옮겨갈 뿐이고, 헬퍼가 `Exception` 을 밖으로 내보내지 않으므로 호출부에서 본 "이 문장은
  예외를 던지지 않는다" 가 두 경로 모두 그대로다.
  🔴 **두 경로는 경계가 없을 때의 피해 모양이 다르다** — 주 경로에서 새면 `except Exception as e`
  (`:2043`)가 받아 **재시도 루프로 되돌아가 이미 판 것을 다시 팔고**(cycle327 실측 3회 발사),
  폴백 경로는 `except KisApiError as fb_err` **안**에 있어 그 핸들러가 non-`KisApiError` 를 못 받으므로
  예외가 `execute_sell` 을 통째로 뚫고 **`risk.on_tick` 으로 전파된다**(피해 = 틱 처리 중단 = 그 순간
  다른 종목의 손절 평가도 함께 사라진다). 추출 뒤에도 **두 경로 모두 안전한 이유는 하나다** —
  경계가 호출부의 문맥(어느 핸들러 안인지)에 의존하지 않고 **헬퍼 자신의 `except Exception`** 에
  있기 때문이다. 즉 호출부가 어디로 옮겨가도 "이 문장은 예외를 던지지 않는다"가 유지된다.
  (`asyncio.CancelledError` 는 `BaseException` 이라 변경 전후 모두 흡수되지 않는다 — 동일.)
- **거부 분류 검사 순서(market_closed 먼저)가 보존되는가** — **보존된다.**
  `except KisApiError as e:`(`:1610`) 이하 분류 블록 전체가 무접촉이고, 이 단계는 `try` **본문**만
  건드린다. `is_market_closed_rejection` → `is_sell_qty_exceeded` → `is_insufficient_quantity` →
  `is_market_order_disallowed` 순서와 각 분기의 `return`/`break`/`continue` 가 전부 그대로다.
- **예외 전파 경로가 같은가** — **같다.** 변경 전후 모두 `Exception` 은 같은 자리(현재는 인라인
  `except`, 이후는 헬퍼 안의 `except`)에서 흡수되고, `BaseException`(`CancelledError` 포함)은
  양쪽 다 `execute_sell` 밖으로 전파된다. 헬퍼가 `KisApiError` 를 새로 던질 길이 없으므로 폴백
  호출부의 형제 핸들러 `except KisApiError as fb_err` 가 오작동할 여지도 없다.

**값 동등성 보충** — `pos.buy_price`/`pos.quantity` 를 읽는 지점이 `:1584-1585` → 호출부로 약 20줄
앞당겨지지만 **그 사이에 `await` 가 0건**이다(매핑 `:1557` 이 이미 `pos.quantity` 를 읽는다).
폴백도 같다(`:1913` ↔ `:1940`, `await` 0건). cycle327 ⓒ 의 "재조회된 `pos` 가 수량의 유일한
진실원"은 호출부에 그대로 남는다.

## 추가 확답

### 1. `_SELL_PENDING_SKIP_*` 과 `_FILL_DURING_INSERT_MARKER` 의 규약을 어떻게 맞추는가

**"미지값이면 전파" 로 맞추지 않는다. 두 표는 ⓑ 경계의 반대편에 있어 안전 방향이 서로 반대다.**

| 표 | 위치 | 미지값의 안전 방향 | 근거 |
|---|---|---|---|
| `_FILL_DURING_INSERT_MARKER` | 경계 **안쪽**(`_insert_pending_or_absorb_race`) | **전파** | 거기서의 전파는 바깥 ⓑ 경계가 받는다. "증거 없는 `UniqueViolationError` 는 그대로 전파"(다른 원인 은폐 금지)가 정본 계약이고, 전파해도 경계 밖으로 나가지 못한다 |
| 선행체크 로그 | 경계 **바로 위**(헬퍼의 `try` 본문) | **전파 금지** | 전파하면 자기 `except Exception` 이 삼키거나(= 지적하신 대로 PENDING INSERT 통째 skip = 주문은 나갔는데 `trade_history` 행이 없다), 경계를 없애면 `risk.on_tick` 까지 간다. **둘 다 불가** |

따라서 맞출 것은 "전파 여부"가 아니라 상위 규약 — **관측이 행위를 바꾸지 않는다**(정본이
`_apply_budget_limit` 관측 3종에 이미 적어 둔 것과 같은 규약: "관측 emit 은 전부 예외를 흡수하고
**행위는 cap 밖**이다"). 그 답은 조회가 **구조적으로 실패할 수 없게** 만드는 것이다.

- 제안 채택: 문구를 통째로 담은 표(`[path]` 인덱싱) 대신 **수식어 표 + `.get(path, "")`**.
  `str.__mod__` 에 `""` 가 들어가면 주 경로 문구가 그대로 나가므로 **어떤 `path` 값에도 raise 하지
  않고 행위가 동일**하다. 그리고 출력은 두 알려진 경로에서 현재와 byte 동일하다.
- 미지 `path` 가 **묻히지 않는가** — 묻히지 않는다. 같은 `path` 값이
  `_insert_pending_or_absorb_race(path=path)` 를 거쳐 `[sell_fill_during_insert] … path=%s` 에,
  실패 시에는 `[sell_post_send_error] … path=%s` 에 **원문 그대로** 실린다. 별도 경보 채널을
  새로 만들 필요가 없다.
- 리뷰어가 원하면 값싼 봉인 1줄 — "이 헬퍼 본문에 dict 의 `[...]` 인덱싱 0건"(AST) 을 걸 수 있다.
  필수는 아니다.

### 2. 매핑 5종과 새 헬퍼 호출 사이에 `await` 가 새로 생기는가 — 「동기 영역」 금기와의 관계

**새로 생기지 않는다. 그리고 실제 양보점(suspension point)도 앞당겨지지 않는다.**

금기의 문구는 "등록은 `place_order` 응답 직후 동기 영역, **`await insert_trade` 진입 전**"이다.
지금 매핑(`:1557-1563`) 뒤의 실행 순서는 이렇다.

```
:1557-1563  매핑 5종 대입            (동기)
:1570       try:                      (동기)
:1572       order_no in _completed_orders 판정   (동기)
:1573-1577  discard + WARNING        (동기)
:1580-1590  TradeRecord(...)          (동기)
:1593       await _insert_pending_or_absorb_race(...)   ← 최초 양보점
```

추출 후에는 `await self._persist_sell_pending_after_send(...)` 라는 **`await` 토큰**이 약 28줄
앞으로 온다. 그러나 `await coro` 는 코루틴을 만들어 **첫 진짜 suspension 까지 동기로 구동**한다.
새 헬퍼는 본문 맨 위부터 `_completed_orders` 판정 → discard/WARNING → `TradeRecord` 조립까지
`await` 가 하나도 없고, **최초 suspension 은 여전히 `_insert_pending_or_absorb_race` 안의
`await insert_trade(record)`** 다. 즉

- 이벤트 루프에 제어를 넘기기 **전에** 실행되는 문장 집합이 변경 전후 **동일**하다.
- 매핑 등록 ~ 최초 양보점 사이에 끼는 문장도 **동일**하다.
- 금기가 말하는 "`await insert_trade` 진입 전"이라는 경계도 **같은 자리**에 남는다.

⚠️ **이 성질은 헬퍼 앞부분에 `await` 가 없다는 사실에 의존한다.** 장래에 헬퍼 맨 위에 비동기
관측 호출 한 줄이 들어가면 양보점이 앞당겨져 금기가 깨진다. 그래서 아래 **선행 의뢰 ②** 의 AST
가드를 두 조항으로 적는다.

1. `execute_sell` 안에서 `self._order_qty[...]` 대입 lineno < `_persist_sell_pending_after_send`
   호출 lineno **(2쌍 모두)** 이고 그 사이 `ast.Await` **0건**
2. 헬퍼 본문에서 `_completed_orders` 판정(`ast.Compare` / `ast.In`)보다 **앞**에 `ast.Await` **0건**

②가 이 카드가 의존하는 "최초 양보점 불변"을 구조로 봉인한다.
