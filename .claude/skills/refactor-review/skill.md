# Refactor Review — 행위 보존 리팩토링 검토 흐름

기능을 바꾸지 않고 구조만 개선한다. 매매 시스템에서 *섣부른 추상화* 는 사고로 직결되므로, 권고는 항상 *회귀 가드 + 위험 등급 + 카드 단위 분할* 로 산출된다.

## 검토 트리거

- **주기**: 사이클 5 회 누적 (오케스트레이터의 Phase 4.5)
- **수동 요청**: 사용자가 "리팩토링", "코드 정리", "중복 제거", "구조 개선" 키워드
- **드리프트 신호**: tdd-engineer 가 같은 패턴 코드가 3 군데 이상 등장한 것을 보고
- **모듈 비대화**: 단일 파일 > 800 라인 또는 단일 함수 > 80 라인

## 5 계명 (refactor-expert 의 작업 원칙 재확인)

1. **테스트 없는 리팩토링 금지** — 회귀 가드 부재 영역은 tdd-engineer 에 회귀 테스트 선행 의뢰
2. **CLAUDE.md "절대 깨지 말 것" 우선** — 체결통보 구독 / uvicorn 단일 워커 / 주문번호 매핑 / 15:20 일괄청산 / NXT 좀비 차단 / WebSocket 4 중 안전망 / KST 강제 — 리팩토링으로도 깨면 안 됨
3. **3 회 반복 = 추상화 후보, 2 회 이하 = 두기** — 미래 가정으로 추상화 만들지 않음
4. **주석 정책 보존** — 의미 없는 주석 추가 금지
5. **권고는 작은 단위로 분할** — 카드 1 장 = 변경 1 의도

## 검토 흐름

```
[트리거] → refactor-expert 가 검토 범위 확정 (team-leader 와 합의)
       → 코드 정독 + grep 통계 + 모듈 라인 수 분석
       → KIS API 영역이면 KIS MCP 로 스펙 재확인 (kis-mcp-query 스킬)
       → 카드 후보 식별 + 위험 등급 분류
       → HIGH 카드는 domain-expert 에 행위 영향 평가 의뢰
       → 회귀 가드 부재 영역은 tdd-engineer 에 회귀 테스트 선행 의뢰
       → 리뷰 메모 작성 (`_workspace/refactor/{YYYY-MM-DD}_review.md`)
       → team-leader 에 SendMessage 한 줄 요약 + 메모 경로
       → team-leader 가 카드별 채택 / 보류 / 폐기 결정
       → 채택 카드는 Red→Green 사이클로 흡수 (backend-dev / frontend-dev)
       → tester 가 카드 적용 후 통합/경계면 회귀 0 검증
```

## 권고 카드 구조

```
### 카드 #N — {1 문장 의도}
- **위험 등급**: LOW / MEDIUM / HIGH
  - LOW: 순수 명명/주석/dead code — 회귀 위험 거의 0
  - MEDIUM: 모듈 *내부* 구조 변경 (헬퍼 추출 / 함수 분할) — 단위 테스트로 회귀 가드 가능
  - HIGH: 모듈 *간* 경계 변경 / 행위 영향 가능 (예: scheduler 분할 / 주문 매핑 흐름 정리) — domain-expert 자문 + 통합 테스트 필수
- **현 상태**: 코드 사실 (file_path:line, grep 통계, 모듈 라인 수)
- **권고**: 변경 의도 + 변경 후 모습 (의사 코드 또는 diff 스케치)
- **회귀 가드**: 기존 테스트 N 개 / 추가 필요 N 개 (tdd-engineer 의뢰 항목)
- **선행 의뢰**: HIGH 등급만 — domain-expert 행위 영향 평가
- **예상 효과**: 코드 라인 감소 / 다음 변경 비용 감소 / 가독성 / 회귀 위험 감소
```

## 빈출 카드 유형

### LOW — 명명 일관성
- 동일 개념의 다른 명명 정렬 (예: `ticker` vs `symbol` vs `stock_code`)
- 표준명 확정 → 전 모듈 grep replace_all → Green 확인

### LOW — Dead code 제거
- grep 호출 0 회 함수 / import / 플래그
- *최소 1 사이클 비활성화 보장* 후 제거 권고 (단기 비활성화 가능성 배제)

### MEDIUM — 중복 패턴 추출
- 3 곳 이상 동일 패턴 → 공통 헬퍼 / 베이스 메서드로 흡수
- 예: 6 전략의 `_fallback_one_share` 같이 이미 베이스로 흡수된 패턴이 또 등장하면 카드 발의

### MEDIUM — 함수 분할
- 단일 함수 > 80 라인 → *책임 식별* 후 헬퍼 분할
- 분할 단위는 *호출 순서가 결정적* 인 영역 — 시간 의존 / 외부 호출 / 상태 변경의 경계

### HIGH — 모듈 분해
- 단일 파일 > 800 라인 + *명확한 책임 분리 가능* (예: scheduler 의 보드 전환 / 사전 구독 / silent inactive 감지 등)
- 분해 시 import 경로 변경 → frontend-dev 영향은 없음 (백엔드 내부) 이지만 tester 의 경계면 검증 필요

### HIGH — KIS 응답 처리 통일
- N 곳의 응답 파싱 패턴이 *서로 다른* 경우 KIS MCP 로 공식 응답 구조 재확인 후 통일
- 위험: KIS 가 빈 필드 / null / "0" 등 변형 응답을 줄 가능성 → domain-expert + tester 협업

## 산출물 — 리뷰 메모

`_workspace/refactor/{YYYY-MM-DD}_review.md`

```
# 리팩토링 리뷰 — YYYY-MM-DD

## 검토 범위
- 검토 사이클 / 검토 디렉토리 / 변경 통계 (git log)
- 검토 시 활용한 도구 (grep / KIS MCP / 라인 수 통계)

## 권고 카드 목록

(카드 N 장)

## 비권고 사항
- 사유: 2 회 이하 반복 / 미래 가정 / 안전 규칙 우선 / 회귀 가드 부재 + 비용 과도

## 후속 의뢰
- tdd-engineer: 회귀 가드 추가 영역 N 개
- domain-expert: HIGH 카드 행위 영향 평가 N 개
- team-leader: 카드별 채택/보류/폐기 결정 요청
```

## KIS MCP 활용

KIS API 호출 코드 영역의 리팩토링은 *KIS 스펙* 을 정본으로 재확인한다.

- `kis-mcp-query` 스킬 참조
- 응답 파싱 분기 통일 카드는 반드시 KIS MCP 의 공식 응답 구조 인용

## 안전 규칙

- **CLAUDE.md 안전 규칙 위반 가능성 시 카드 미발의** — 메모에 "검토했으나 안전 규칙 우선으로 제외" 명시
- **회귀 가드 부재 영역 권고 시 회귀 테스트 선행 의뢰** — 단순 권고 보류
- **카드 채택 후 *Refactor 중 RED 발생 시 즉시 되돌림*** — TDD 사이클의 표준 절차
- **운영 시간 (KRX 메인 09:00~15:30) 중 push 권고 자제** — CLAUDE.md 운영 가이드 따름. NXT 애프터 / 익일 boot 전 권장
